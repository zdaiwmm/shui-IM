# Security model

## Sender-initiated webpage previews (2026-10-28)

The confirmed [link-preview V1.1](docs/requirements/2026-10-28-chat-link-preview/README.md) explicitly allows a narrow exception to server ignorance of message URLs: after the sender types or pastes a previewable address, an authenticated, same-origin POST discloses that URL (including ordinary query parameters) and fetches its public metadata before the message is sent. Cancellation or never sending the message cannot recall this disclosure. The remainder of the draft is not submitted. The endpoint does not log targets, cache results, persist plaintext metadata, forward cookies/device authorization to websites, execute scripts, or render remote HTML. This is not an anonymity claim: the service can associate the request with its active device and sees fetched public content.

Every page, redirect and image validates HTTP(S), credentials, standard ports and all DNS answers, rejects non-public/reserved addresses and HTTPS downgrade, and pins the checked address into a fresh socket. Redirects, headers, response bytes, image dimensions, total time, source/device quotas and global concurrency are bounded. Known secret-bearing query keys, application capability routes and fragments are not automatically fetched; this cannot recognize every sensitive query. Remote image data is limited to recognized JPEG/PNG/WebP with bounded raster dimensions; SVG, page scripts, cookies and ambient proxy credentials are not used.

The sender decodes and compresses a preview image into a validated JPEG of at most 16 KiB and 640px per side. The URL, bounded title/description, image bytes and chosen layout are a capability-gated text-v3 payload inside the existing authenticated message encryption, with no cryptographic construction or ratchet change. The ciphertext bounds remain unchanged. Recipients check the JPEG frame header against the declared bounded dimensions before passing snapshot bytes to the browser image decoder; missing, truncated or mismatched frame headers fail payload validation. No remote image URL is rendered. Recipients and history views do not refetch metadata or images. Card bytes are independent snapshots and are not Safe attachments. Known old clients receive ordinary text; an already-encrypted queued snapshot encountering a newly joined incompatible device uses the existing immutable-outbox wait rule rather than changing generated ciphertext or advancing MLS twice.

All website strings are rendered with text nodes. New-tab anchors are HTTP(S)-validated and use noopener, noreferrer and no-referrer. Runtime object URLs are revoked when the row disconnects, privacy concealment starts, or the runtime aborts; resuming an otherwise authorized retained runtime reconstructs only its authenticated local snapshot. Preview requests are canceled and generation-guarded on draft changes, navigation, concealment and lock; late results cannot repopulate a stale surface. A restored draft alone never initiates a request until fresh input. Existing encrypted history, device-join and private-archive boundaries remain authoritative.

## Current scope and abuse-control contract

Current room formats and product behavior are summarized in [PRODUCT.md](PRODUCT.md#当前格式与适用规则). New `room-archive-v2` rooms follow [NEW_ROOM_ARCHIVES.md](NEW_ROOM_ARCHIVES.md); preserved mnemonic Chamber and earlier recovery-card rooms retain their own contracts. Invitation expiry is not a new authorization to delete stored rooms or archives. Manual safety-code UI in a compatibility path does not apply to new admission-secret device links.

The six-digit application lock has a 10^6 offline search space. An archive recovery card instead requires its own 12–128-character password at creation; its encrypted wrapper and password are not uploaded as part of the cloud archive. Password length alone does not establish entropy. MLS serialization is part of the encrypted local vault payload; writable IndexedDB is not equivalent to possession of an unlocked vault or a compromised executing origin.

The [V1 hardening](docs/requirements/2026-10-27-audit-abuse-hardening/README.md) accepts forwarding only from explicitly trusted immediate peers and only as one syntactically valid IP. The public nginx configuration overwrites XFF with its connection address. Untrusted, malformed, multi-value or chained forwarding falls back to the socket address; equivalent IPv6/mapped-IPv4 addresses are canonicalized. Deployment must verify the actual proxy/container peer and installed configuration; repository changes alone do not prove production enforcement.

Application rate-limit buckets are process-local, expire lazily and have fixed capacity. Saturation rejects new keys instead of evicting active limits. Existing limits keep their budgets. Four authenticated writes additionally have source and room/device/operation budgets per minute:

| Operation | Source | Device |
| --- | --- | --- |
| MLS membership event | 720 | 60 |
| Initial MLS welcome | 240 | 12 |
| Attachment completion | 1440 | 120 |
| Push unsubscribe | 240 | 12 |

Source admission precedes device lookup; device admission precedes body parsing, signature verification or completion work. A rejection returns 429/RATE_LIMITED and Retry-After; rejected attempts do not extend the fixed window. Device limits persist across source-address changes. Duplicate valid operations retain their existing idempotency semantics. These are request budgets, not a new ciphertext quota or a replacement for edge/DDoS controls.

Administrator login and fresh-factor deletion share an eight-attempt/minute budget per trusted source, with at most 1024 active sources. Expensive password verification remains single-flight. Source exhaustion returns 429/RATE_LIMITED; global verifier contention returns 503/AUTH_BUSY with a short retry interval. Password parameters, persistent TOTP replay protection, same-origin checks, CSRF and cookies remain required. Shared NAT users still share source admission; distributed traffic or capacity saturation can still affect availability, and process restart resets these limits. No additional raw IP/request-body logging is introduced.

Malformed percent-encoded HTTP paths return 400/INVALID_PATH without an internal-error stack. Full security validation, physical-device evidence, trusted-client distribution and off-host immutable backup/alert gates remain independently open in [PRODUCTION_SECURITY_GATE.md](PRODUCTION_SECURITY_GATE.md).

## 2026-10-27 Atomic restore originals and conservative collection

Unpublished imports allocate a fresh random original namespace per run/source; other restores, including legacy clients, cannot borrow it. Original ciphertext is written once to privateMedia with a small run ownership witness in the same vault-CAS transaction. The witness hashes the complete ciphertext record; originals retain the existing authenticated format. Messages, deletion events, catalog revision and witness retirement publish atomically without copying large originals. Failure removes only unchanged witnessed originals in the run's unpublished namespaces. Published copies reuse their recorded sourceScope, including legacy origin-based scopes; repairs of published originals and records replaced by another writer survive cancellation. No plaintext content index, cryptographic construction or database-version change is introduced.

Namespace isolation is required for safe cleanup, including without Web Locks. Raw original bytes remain inaccessible to product rendering and backup until their message references publish. New readers/retries preserve existing source scopes; an old writer may reject reimport of a newer local copy and must retain data on conflict.

Legacy orphan collection requires the caller's exclusive restore lock, the global vault mutation lease, a usable Web Locks inventory without any other held restore lock, authenticated complete raw-history references and the current vault CAS. It retains all published references including hidden/deleted raw events, non-private namespaces and unknown key layouts. Unknown scope formats or unavailable lock inventory skip collection; corrupt history fails closed before deletion. Legacy lock names remain compatible. Logical deletion does not guarantee immediate browser backing-store reclamation. Native quota cases use isolated persistent profiles and separately observe actual reclamation; they do not establish physical-device or real-disk exhaustion evidence; see [R2](docs/requirements/2026-10-27-restore-failure-validation/README.md).

## 2026-10-27 Private-history runtime and derived catalog

Each room opening owns a distinct runtime token and cancellation signal, including reopening the same VaultSession. Results are checked after asynchronous boundaries and before projection. Locking invalidates ownership synchronously; a completed WebCrypto call may still return internally but cannot repopulate the next runtime. This is reference/resource release, not physical memory erasure.

Private raw records and imported originals retain their authenticated encrypted namespaces. IndexedDB v16 adds only an encrypted, rebuildable private catalog: bounded ciphertext cursors, metadata-only encrypted external-sort runs, complete per-source deletion projection, and atomic adoption bound to the published import revision. No plaintext time/type/body index is added. Missing/corrupt catalogs fail closed for the private segment; raw data remain. Shared history's existing strict integrity scan is unchanged. Old-schema tabs must reload; rollback uses the v16-compatible strict reader, never database downgrade or deleting originals.

Backup completion binds archive identity, local scope, shared sequence, private import revision and verified committed head. Preference/credential success and object uploads alone do not prove latest coverage. Previous authenticated batches survive partial failure. Cross-tab task leases do not replace withVaultMutation, immutable vault slots, CAS or MLS/message atomic commits. No cryptographic construction, membership/history permission or server architecture changes; browser tests and synthetic measurements are not physical-device evidence or independent audit.

## 2026-10-26 Own-device room admission

The `own-admission` mailbox is separate from metadata in both SQL table and authenticated purpose. It reuses the existing pairwise P-256 ECDH / HKDF / AES-GCM and ECDSA, binding carrier room, sender, recipient, revision and purpose. Server access requires active, same-role members of the carrier room and grants no membership in the target room. The metadata payload remains compatible.

Decrypted requests bind random ID, carrier room, target room, both devices, bounded device name and a fixed ten-minute expiry. A response must match a locally persisted request; terminal states cannot roll back and expired messages cannot authorize. The original device explicitly approves in the target room after operation authentication, verifies its same-role carrier peer is still active, and sends internal single-use enrollment material only to that requester. Existing join-proof validation and MLS add, three-device limits, independent keys and pre-join history boundaries remain authoritative. Lifecycle cancellation rejects late writes. Compromised already-trusted devices remain within the existing endpoint threat boundary; this is not an independent security audit.

The macOS host fixes the HTTPS origin, exposes no native JavaScript bridge and never relaxes TLS. Deliberate HTTP(S) links leave through the default browser; camera, microphone and file operations retain system/user permission. Backgrounding adds a native visual shield without replacing the webpage lock lifecycle. Without Associated Domains, new embedded protection uses the existing password path; existing browser passkey wrappers never downgrade. Ad-hoc signing is not Developer ID signing or notarization.

## 2026-10-25 Own-device metadata directory and media lifecycle

The [confirmed V1](docs/requirements/2026-10-25-experience-reliability/README.md) exchanges only allowlisted names, bounded avatars, room identifiers, creation/waiting metadata and removal records. Each envelope uses independent device P-256 ECDH keys, HKDF-SHA-256 with a purpose/room/sender/recipient/version context, random AES-GCM IV and authenticated context, plus the sender's P-256 ECDSA signature. Clients select keys only from their trusted active same-role roster; server reads/writes require active device tokens and a same-role active recipient. No private keys, room tokens, recovery material, message previews, history or unread capabilities are included. Discovery grants no membership or historical access. Long-term device keys protecting directory metadata do not provide MLS-style forward secrecy for that metadata; copied directories cannot be remotely erased. Offline logical revisions and retained removals reject older snapshots, without claiming protection from an origin that replaces the executing client.

The opaque mailbox keeps only the latest per-sender/recipient envelope, rejects version rollback/conflicts and bounds envelopes to 2 MiB. Retired device rows are pruned; the three-device-per-role limit bounds active pairs. Local records use encrypted collection storage and the lifecycle lease, separate from recovery exports. Hiding/locking aborts synchronization. HTTP waits do not hold local storage leases. Signed MLS admission, raw attachment integrity and atomic history/outbox semantics remain unchanged.

Concealment derivatives occupy a distinct authenticated local media-cache variant bound to the complete source manifest and history scope. They share existing quota, eviction, abort and stale-vault checks, are never uploaded, and do not replace original files or playable video. Re-entry reuses authenticated posters/derivatives; privacy cleanup still releases plaintext. Source teardown also clears browser media-session metadata, position and action state. Native iOS lock-screen card removal and browser toolbar rendering require physical-device verification; clearing metadata does not guarantee removal of browser-owned UI.

## Administrator metadata workspace, 2026-10-25

Authenticated admin read models return explicitly selected room, device and archive metadata, never ciphertext envelopes, archive descriptors, capability hashes, invitation secrets, recovery material or device-private data. New archive timestamps are committed with registration/new object insertion; retries do not create false freshness and legacy timestamps remain unknown. Room deletion preserves independent v2 archives and existing card-authorized reads. The disaster receipt is published to a separate status-only volume every 30 seconds, read-only in the app, bounded at 4 KiB and projected through an allowlist. Samples older than 120 seconds or in the future are unavailable; no snapshot directory or arbitrary file path is exposed. Diagnostics distinguish configuration, sampled application checks and independently verified disaster receipts. Existing exact-origin, host cookie, CSRF, password/TOTP and fresh-factor deletion remain required. Resource audit events exclude request bodies, keywords and credentials; legacy deletion events do not prove filesystem cleanup completion.

## Pending cancellation and browser chrome, 2026-10-24

The confirmed [thirteen-item V1](docs/requirements/2026-10-24-ui-13-fixes/README.md) changes pending-message deletion into durable cancellation. One lifecycle/CAS-protected IndexedDB transaction removes the encrypted outbox record, saves an encrypted local deletion projection and refreshes the stored vault snapshot. The [2026-10-27 fix](docs/requirements/2026-10-27-cancel-accepted-validation/README.md) additionally preserves an existing MLS envelope/payload in a separate receive-only encrypted preference record in that same transaction. Its authenticated record key binds local scope, original device and message ID; reads also check room, sender, message ID and payload shape, and receive still requires an exact canonical envelope match. It is never loaded by the outbox, sent, or exported independently to archives; old clients ignore the separate preference key. Normal atomic history/MLS persistence retires this material only after an authenticated own echo commits, while local hiding remains. Unresolved material is retained locally, bounded by the existing local deletion limit, and removed by explicit local-data clearing. No schema version or wire protocol changes. Old clients cannot reconcile this new material themselves, and already deleted pre-fix material cannot be reconstructed by this change. Transport submission rechecks the durable outbox under that same lease; late preparation cannot resurrect cancelled work. MLS state never rewinds. Ciphertext already accepted by the server cannot be recalled by cancelling later retries; confirmed deletion and Safe copies retain their existing semantics. A device admission URL may open a fresh slot while an earlier invitation-code task remains stored; original verification, independent key material, membership approval and join-history bounds still apply. The favicon uses only the existing current-room count-only observer, including its established locked count visibility. It contains no names or message data. Only shipped public Fluent/avatar assets enter the release-versioned shell cache; authenticated catalog and chat resources remain excluded.

## 2026-10-21 MLS Curve25519 生成兼容

Ed25519 签名也使用已锁定 Noble 实现：32字节种子直接签名，旧48字节 PKCS#8 仅在完整匹配 RFC 8410 固定头后读取种子；其他编码继续交给原解析器，损坏编码不作为种子处理。此修复针对主分支 CI 捕获的原生私钥 importKey DataError。签名验证器、成员认证与身份绑定保持原样；原生签名结果一致性、篡改拒绝、旧编码及强制导入失败由回归覆盖，不重写持久密钥。

X25519 HPKE 使用已锁定的 `@hpke/dhkem-x25519` 及 ts-mls 原有适配器，避免同样失败的原生 X25519 生成（含临时密钥）。DHKEM(X25519, HKDF-SHA256)、AES128GCM、32字节原始公私钥与报文格式保持。回归覆盖与旧原生 HPKE 的双向互通、AAD 篡改拒绝、两种原生生成器同时拒绝及安全随机源失败关闭。

MLS 签名身份采用锁定依赖 `@noble/curves` 的 Ed25519 种子生成路径，使用系统安全随机源；不再依赖 Linux WebKit 偶发抛出 OperationError 的原生 Ed25519 generateKey。密码套件、签名验证、成员认证与身份绑定不变。ts-mls 1.6.4 原已支持的32字节种子用于新身份，旧保险库的 PKCS#8 私钥继续可读、可签名，无迁移或重新绑定。随机源不可用时创建失败，不使用可预测随机数或旧身份补位。新旧格式跨端 MLS welcome、双向消息与重放拒绝由回归覆盖；自动化不构成独立密码学审计。

## Participant invitation reentry, 2026-10-19

An old participant URL is a navigation target, never evidence of current membership. Existing encrypted local vaults and the encrypted room directory remain behind normal application-lock verification; matching the room also checks the original creator fingerprint. Reentry uses the existing device credential and normal lifecycle/membership checks, without reactivating the consumed invite or generating a replacement endpoint. ## Cryptographic construction

- Each device generates separate P-256 ECDH and ECDSA identity key pairs in Web Crypto and an RFC 9420 MLS key package using `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- The MLS credential embeds the device ID and MLS signature public key. The device's P-256 identity key signs that binding; clients validate it against the public bundle authenticated by the invitation proof.
- The one-time participant invite pins the creator public-key fingerprint and carries a random pairing secret in a strictly validated `#invite` URL fragment. Additional-device links use a distinct, strictly validated `#device` fragment and exact schema; the client never reinterprets a valid device capability as a participant invitation merely because another device was already authorized.
- The joining device authenticates its public bundle with HMAC-SHA-256 under that pairing secret.
- New rooms create an initial two-member RFC 9420 MLS group. The creator signs the opaque welcome envelope with its P-256 identity key. Additional devices enter through a signed MLS Add commit and their own welcome; removals use signed MLS Remove commits. MLS advances the application-message secret tree on every message and the group epoch on membership change.
- Each device has a distinct random server access token. A new-device link carries a short-lived capability in its URL fragment, requires a manually compared six-digit safety code, and cannot activate the claimant without an existing same-participant device signing the MLS Add commit. The service sees the raw link capability while verifying link requests but stores only its hash; expired links and never-approved pending members are deleted.
- Activation records the room's current message and receipt sequences as the device's lower synchronization bounds. A late receipt for a pre-activation message is projected to a sequence-only skip marker for that device, so it cannot reveal an old message ID and cannot block later receipt processing. The service also parses the public MLS epoch field and rejects validly signed application ciphertext from an obsolete epoch, forcing the sender to process the membership change and re-encrypt. The new welcome contains current group state, not prior epoch secrets.
- The sender additionally signs each complete outer envelope with ECDSA P-256/SHA-256. The server verifies this signature before persistence, and recipients verify it again before MLS processing.
- Legacy rooms retain the original per-message random AES-256-GCM content key and ephemeral P-256 ECDH wrapping construction. They do not acquire forward secrecy automatically and must be replaced with a new room.
- Media read acknowledgements are separate encrypted `media-read` application events. Only an exact locally known media target and an authenticated opposite participant role count. They use the ordinary atomic MLS/outbox/history path and capability gate; hidden, blurred, away and unfocused surfaces do not emit them. Read targets and payload timestamps remain ciphertext; the service still observes envelope timing and size. These events are not chat rows or unread-countable content and do not change the sender's explicit media reveal state.
- After a recipient verifies, decrypts, and persists a message, it signs a receipt that binds the room ID, message ID, server sequence, receiver device ID, and receipt time. Only that receipt promotes the sender UI from server-stored to peer-delivered.
- Images are encrypted in 2 MiB AES-256-GCM chunks. A unique eight-byte random prefix plus a four-byte chunk counter forms each nonce. The authenticated data binds the blob ID, index, total chunk count, and original size.
- The encrypted image manifest contains the file key and SHA-256 digest. A receiver accepts a reconstructed image only when its exact byte length and digest match.
- Imported video and other file attachments retain the same original-byte encrypted chunk transport and length/digest verification. Videos remain `file` or `gallery-file` payloads, including previously stored compatible videos; display does not add a message kind or change the `file-message-v1` compatibility gate. A filename extension is used to classify video only when MIME is empty or `application/octet-stream`; an explicitly typed document is not made playable by its filename.
- User selections have no nine-image cap. Chat groups originals in order within the existing nine-image and 256 MiB per-message limits; each multi-image group is a strictly validated `image-album` payload with unique encrypted manifests. Gallery multi-selection creates individual gallery-only payloads. The sender requires every active device to have refreshed its `image-album-v1` capability before sending an album, preventing an old client from being advanced past an unknown payload. Grouping, order, and reply relation remain inside MLS ciphertext even though the service observes separate blob reservations and transfer sizes. Visible reply excerpts are derived only from encrypted local history, so a newly linked device does not receive copied pre-join text through a later reply.
- A random 256-bit AES-GCM master key encrypts the local vault, history, outgoing-message queue, pending-receipt queue, upload-resume plans, reading anchor, unsent text draft, recovery-reminder preferences, local-only hidden message IDs, and creator-Safe pin/hide projections. Version-3 device-key vaults derive the key-encryption key with HKDF-SHA-256 from WebAuthn PRF output after authenticator user verification, then wrap the master key. Registration requires a resident credential, user verification and PRF, and does not set `authenticatorAttachment: platform`, so a PRF-capable platform passkey or hardware security key can both complete setup. Both single-device and syncable passkeys are accepted; the immutable backup-eligibility flag is recorded and checked on later assertions. PRF output and derived keys are not persisted.
- New password fallback uses a version-3 `password` wrapper over a separately random 256-bit master key, not the legacy password-derived payload key. Argon2id parameters are fixed at 64 MiB, three iterations, one lane and a random 16-byte salt; the nonextractable AES-256-GCM wrapping key is memory-only. Wrapper AAD binds the format, immutable local slot and all KDF parameters; payload/history encryption remains under the master key. New user-facing setup uses exactly six ASCII digits, including leading zeros, with an authenticated `numeric-6` format marker appended to wrapper AAD. Existing unmarked 12–128-code-point Unicode password wrappers retain their original AAD and exact input; they are not automatically converted. Passwords are never normalized or trimmed, uploaded, or persisted. Six digits provide only 1,000,000 combinations and do not have iPhone Secure Enclave hardware-enforced guessing protection; the confirmed usability tradeoff reduces the password space. Removing or changing the numeric marker fails wrapper authentication. Older clients that do not understand this AAD need an update to open new numeric wrappers. Offline guesses remain possible if an attacker obtains the encrypted wrapper; the local delay is not offline protection. Existing wrappers are never silently downgraded. Only missing WebAuthn APIs (including missing credential create/get methods), an explicit negative client `extension:prf` capability, an explicitly unavailable built-in verifier under the confirmed 2026-10-14 new-protection policy, an identifiable embedded WebView under the confirmed 2026-10-15 new-protection policy, an unsupported new-setup ceremony, or `prf.enabled === false` permit new-password fallback; unknown extension results, cancellation, timeout, transient failures and insecure contexts do not. Sensitive operations freshly authenticate the target’s original wrapper and reject cancelled, expired, locked, switched or stale results. IndexedDB version 12 keeps old clients from writing over the new format. Password spaces do not obtain PRF browser-directory discovery authority. Legacy v1/v2 and recovery packages keep their existing explicit migration/binding paths. This added wrapper has automated tests, not an independent security audit.
- The optional WebAuthn client-capability probe runs before activation and is never an authentication proof. Missing keys and probe failures remain unknown; platform-authenticator availability alone cannot exclude PRF-capable hardware keys. The confirmed new-protection policy nevertheless selects password setup on an explicit negative built-in-verifier result; this preference does not alter existing platform wrappers or treat unknown/failed probes as negative. All browser shells use the same capability checks, including the current platform-capability key and explicit recognized permissions-policy denials; UA matching is presentation-only. An ambiguous failed new ceremony (cancellation, timeout, native restrictions or transient native errors) may offer an explicit choice to retry, set a new six-digit password, or cancel; it never silently selects a password or authenticates an existing wrapper. Existing passkey wrappers still require their original verifier. Invalid credential data and insecure contexts continue to fail closed, and hidden/pagehide/freeze, navigation and cancellation retire the pending choice. New password setup separately checks a secure context, WebCrypto and an atomic nonsecret IndexedDB write/delete. Returning password pages own their cancellation signal and pending state per render, so a replaced page cannot block or install a late proof in its successor. See [WebAuthn client capabilities](https://www.w3.org/TR/webauthn-3/#sctn-getClientCapabilities).
- Automatic joint recovery signs each endpoint’s own authenticated rebuild/helper result. The initiator’s scope is never inherited as proof of the receiving endpoint’s loss; incoming offers are signature- and target-bound before their flags are used. Both approvals bind the final signed offers and replacement proposal. A usable helper retains its original master key and local history; unknown or unsynchronized local state stops. Two usable endpoints require no replacement. This changes the frontend decision flow while keeping the existing signed v1 wire schema and final dual-approval protocol.
- “仅为我删除” and Safe Pin/Delete are encrypted endpoint projections. They never alter server order, message ciphertext, the peer's state, or the chat bubble represented by a Safe-only action. “为所有人删除” is instead a strict `message-delete` payload inside the ordinary signed MLS message/outbox path. The target must be an exact locally available confirmed chat message, both target and deleting devices must map to the same role in authenticated membership history, the delete event must follow the target in server order, and every active device must advertise `message-delete-v1`. The server can observe another opaque message envelope but not its delete target or scope.
- QR3 recovery uses a random 128-bit locator plus a random 256-bit secret. Domain-separated HKDF derives independent retrieval and AES-256-GCM encryption keys. Each random archive key is inside the encrypted recovery checkpoint; authenticated archive indexes bind ciphertext digests, room, archive and part. The server stores ciphertext and scoped capability hashes, never codes or decrypting keys. The local code is encrypted under the device master key. See `RECOVERY_BACKUPS.md` for exact domains, formats, rotation and limits. Legacy password/gesture vaults and already-imported old recovery formats remain migration inputs.
- Joint recovery is a separate, dual-confirmation MLS rebuild. Each participant authenticates with their own recovery code and signs the same recovery scope, target devices and `retireOtherDevices` proposal. The server only commits after both signatures, then atomically revokes every previous active/pending member, push subscription, unread observer, device/repair link and pending single-device recovery request, and installs the two replacement members. This stops leftover devices from silently using old tokens; it does not remotely erase ciphertext already stored on those devices or in backups. A helper who is not in the recover scope keeps local history after catching up messages in their pre-reset permission range, then switches to the new identity and token. Recovered devices start without old chat rows until they import their own local file. The recovery-link capability is not an identity proof.
- An explicit history-restore task retains the submitted codes inside the device’s master-key-encrypted vault until completion or explicit cancellation. It never enters cloud checkpoints or recovery exports. Navigation, locking and privacy teardown abort network work and release UI references without deleting the encrypted task; reauthentication is required before retry. This convenience state provides no background execution or additional protection against an already compromised unlocked endpoint.

## Real-time call construction

Two-person calls use browser-to-browser DTLS-SRTP, including when coturn relays
the encrypted packets. There is no media decoding, transcoding or recording on
the application server. SDP fingerprints and ICE candidates are carried inside
separately encrypted AES-256-GCM signaling envelopes, derived with domain-separated
P-256 ECDH/HKDF-SHA-256 and signed in full with the device ECDSA identity. Strict
recipient/room binding, expiry, replay checks and membership fencing apply.

Before creating a peer connection, requesting call media or publishing local
SDP, the client verifies the actual local MLS tree and a device-signed attestation
of the complete public bundle and role. The attestation signing key must match
the MLS-bound device identity; an unverified server roster or server-supplied
verified-device list is insufficient. Signed membership history also pins prior
identities. This attestation is required again for answering and refreshing ICE.

Signaling derives from long-term device ECDH keys and does not claim forward
secrecy after device-key compromise. Media keys use a separate ephemeral DTLS
exchange. The server observes routing and call timing; TURN sees traffic and
address metadata, while direct peers may learn each other's public IP. TURN has
short-lived authenticated credentials rather than an anonymous relay. Background
or privacy teardown stops capture and invalidates the unlocked runtime on every client. Capture ownership includes granted streams still awaiting native handoff or sender replacement; teardown stops them before those asynchronous operations settle. An unselected invited endpoint leaving cannot end an already selected call; pre-accept cancellation remains bound to its authenticated invitation. Calls do not remove the endpoint, malicious-served-JavaScript
or independent-audit limitations below. See `CALLS.md` for operational details.

## Explicit limitations

The document reader has no external window, cloud conversion or native blur exemption.
PDF.js code, worker, font/CMap and decoder resources are bundled with the application.
Worker resource requests resolve through a fixed build-owned asset map, with worker
fetch disabled; no document-provided URL is fetched. Font outlines are rendered locally
without relaxing the application's CSP. PDF parsing is limited to 64 MiB and 2,000 pages,
text to 4 MiB and 2,000,000 decoded characters; the visible canvas is capped at six million
pixels and 4,096 pixels per edge. Load/render deadlines dispose failed PDF workers.
PDF pages are rendered serially. Vertical scrolling retains at most the current page and its two neighbors,
each subject to the same canvas limits; horizontal reading retains one. Closing, runtime replacement, navigation and
the existing privacy curtain cancel work, terminate the worker, clear text and zero the
visible canvas. This is best-effort reference/resource cleanup, not guaranteed memory
zeroization by the JavaScript engine. No plaintext document or search index is persisted;
the existing opaque ciphertext cache and original encrypted attachments are unchanged.
Password-protected documents and OCR are unsupported in this first version. Read errors
remain local and do not automatically export the file. Other exports retain their strict policy.

EPUB 2/3 is also allowlisted after full original-file verification. Bundled epub.js parses
package/spine/navigation XML; its XML dependency is pinned to a repaired version via an
override. zip.js runs in a dedicated, terminable worker with a bundled fallback decoder,
strict local-header comparison and CRC checks. Reject encrypted entries/resources, unsafe

16 MiB per entry. Streamed extraction independently caps actual output; XML/chapters are
limited to 2 MiB, 30,000 nodes and depth 64, with entity declarations/internal DTDs rejected.
DOMPurify applies a semantic tag/attribute allowlist to detached chapters. Publisher style,

do not establish decoder safety or memory zeroization. Other active files remain download-only.

Visible EPUB file rows may decrypt and verify the entire original before extracting a declared manifest cover.
Extraction uses the same bounded ZIP worker and PNG/JPEG/GIF/WebP allowlist, with at most two concurrent cover tasks.

covers retain the format icon. A cover does not expand device history access or substitute for attachment verification.

New rooms use the standardized RFC 9420 MLS protocol, but the selected browser-capable `ts-mls` implementation states that it has not undergone a formal security audit. The integration must pass independent cryptographic review before high-risk production claims. Legacy rooms have no forward secrecy.

Per-message MLS secret-tree advancement provides forward secrecy for deleted generations. Full post-compromise recovery requires authenticated epoch updates after the attacker loses endpoint access, clean endpoints, and an audited incident procedure; that complete mechanism is not implemented or claimed here.

Removing the application gesture does not change MLS, message/attachment encryption, the 256-bit local master key, or AES-GCM. It does remove one independent knowledge factor from local vault access: version-3 unlock security is the PRF secret plus the authenticator and operating system's biometric/device-password policy. A syncable passkey is not strictly bound to one physical device, so deployments requiring that property must mandate a compatible single-device authenticator or hardware security key. Recovery is protected separately by its independent random 256-bit code. A legacy version-2 gesture is requested once only because it is cryptographic input needed to unwrap that existing vault, and is discarded after migration.

A fully malicious server can replace the JavaScript it serves and attempt to steal plaintext or keys on a later visit. CSP, pinned dependencies, HTTPS, and a separate static release channel reduce this risk but do not eliminate it. Strong protection from an actively malicious hosting server requires a signed client distributed from a separate trust root.

The server observes metadata needed for operation: room identifier, device pseudonyms/names and public keys, roles, device-link creation/claim/activation times, MLS key-package/welcome/commit sizes and epochs, per-device history boundaries, connection IP, ciphertext and encrypted-blob sizes, message and upload counts, acceptance time, delivery-receipt time, total order, registered push endpoints, and each live authenticated socket's reported `chat` or `away` view. It does not see encrypted reply references or encrypted album membership. A push provider observes endpoint and timing/volume metadata even though the request carries no payload. The service can delay, drop, or deny delivery. Cryptography cannot force delivery or make a disconnected network instantaneous.

Chat-page presence is deliberately separate from WebSocket connection state. A socket starts `away`; the client reports `chat` only on the chat surface, caches the desired view, and replays it after reconnect authentication. The service computes each role as online when any active socket for that role reports `chat`, holds this per-socket state only in process memory, and clears/recomputes it on `away`, close, membership changes, or ping/pong timeout. This is behavioral metadata visible to and asserted through the service. It is not signed inside MLS, is not end-to-end verifiable, does not prove that the named person is attending the page, and must not be used as a safety-code or delivery guarantee. As confirmed in [presence persistence V1](docs/requirements/2026-10-28-presence-last-seen/README.md), only the latest server-observed chat timestamp per room/role is persisted. Entry/departure update it immediately and authenticated chat pong observations refresh it at most once every 30 seconds per role; pending, revoked and recovery-suspended devices cannot advance it. A crash retains the last durable observation, not an inferred exact departure time; restart starts every socket away. The additive table is included in database backups and cascades on room deletion, subject to existing backup retention. Old missing times are not reconstructed from authentication metadata. Neither ephemeral state nor bounded persistence prevents infrastructure, proxy, or process telemetry from observing timing.

The encrypted reading anchor and recovery-reminder preference are device-local convenience state. They are not synchronized, cannot establish peer behavior, and remain readable to an attacker who compromises the unlocked endpoint. Expression favorites and user-added sticker packs are also endpoint-local: authenticated encrypted indexes and independent encrypted originals are atomically committed under the vault lifecycle lock. Source-message deletion does not remove these copies; they do not enter backup archives or device-join history. The expression picker has no search input. Privacy concealment synchronously disposes the half-screen panel, full-screen sticker catalog, pending loads, preview and object URLs. Emoji combines bundled Unicode and the existing 64 Fluent avatar animations; installed collection indexes remain encrypted locally. The add page reads only the published server sticker catalog through authenticated same-origin APIs with an empty keyword. Only explicit administrator acquisition accesses the public Signal Stickers directory and fixed media hosts; upstream receives those requests and the server IP, not keywords, room identifiers, device tokens or chat content. This public-media proxy is outside the end-to-end message channel. Only fixed HTTPS catalog and image hosts are allowed, redirects are rejected, DNS answers are pinned to public IPv4 addresses, and device-bound media IDs expire. Public Signal payloads are MAC-verified before their separate transport decryption. Requests, downloads and concurrency are bounded. The server stores public originals, attribution and moderation state separately from encrypted chat attachments, while raw keywords are not persisted or logged. Public catalog originals are absent from the code bundle and are held only in bounded picker memory on the client; the explicit Fluent group reuses existing bundled avatar resources. Service Worker upgrades delete the legacy public-asset cache. See [MEMES.md](./MEMES.md). Message reactions remain a separate encrypted feature.

Page-level double-tap/gesture zoom suppression, transparent application bars, and transition timing are interface behavior rather than cryptographic controls. Safari and Chrome retain control of their native toolbars; `theme-color`, edge-to-edge viewport settings, and installed-PWA display hints cannot guarantee a transparent browser-owned bottom bar. These best-effort hints must not be represented as a privacy or anti-spoofing boundary.

An endpoint compromise, malicious browser extension, screen recorder, operating-system compromise, or unlocked physical device can read plaintext. The hidden long-press entry is a privacy curtain, not an authentication boundary.

User-opened native pickers, microphone/camera requests, clipboard/share/confirmation, notification permission and exports retain bounded session/epoch ownership. Visible blur has no privacy effect regardless of ownership. Their operation deadlines reject/cancel stale results and release resources without locking an otherwise valid runtime. Hidden/hard lifecycle, manual lock, unified idle expiry and safety invalidation override operations. The same original room/device/generation checks remain; no late file or permission can enter a newer runtime. No new plaintext persistence or server protocol is introduced.

The browser-load-failure cover is visual concealment. A website cannot guarantee when the operating system captures a task-switcher or tab thumbnail, remove an already cached snapshot, or prevent screenshots. Synchronous blur/visibility concealment minimizes the time sensitive content remains visible after lifecycle notification; it does not provide native screenshot-protection APIs. Native text selection remains browser-owned as well: selecting the inline read-only control cannot guarantee that every iOS version immediately opens its edit toolbar.

## Local media upload drafts

### Device-local text checkpoints

Text input uses a synchronous AES-256-GCM ciphertext checkpoint in origin-local Storage, separate from debounced IndexedDB UI preferences. HKDF-SHA-256 derives its key from the existing device master key, with canonical origin/immutable slot/room/device salt and `quiet-room-composer-draft-v1` info. Each changed input uses a fresh random 96-bit nonce; AAD additionally binds its unique writer. Text and its random revision are encrypted; storage exposes room/device/slot/writer identifiers and ciphertext length, never the key or text. Derived bytes are held only in the unlocked runtime and filled with zero on disposal; JavaScript reference cleanup is not a guarantee of engine memory zeroization. A replaced/cancelled unlock cannot claim a writer. A new owner supersedes old tabs; an old runtime cannot publish into the new owner's record. A failed write retains the last successful checkpoint and reports failure, without plaintext downgrade.

The encrypted submitted-revision record commits in the same IndexedDB transaction as the outbox and, for MLS, its next ratchet state. Unlock suppresses only that exact checkpoint revision; editing away and back produces a different revision. Late preference writes cannot override a checkpoint. Explicit local-data clearing replaces prior text with an authenticated empty checkpoint so an older preference snapshot cannot restore it; removing a vault removes its scoped checkpoints. Damaged authenticated records fail closed instead of restoring old text. Checkpoints and commit markers are not included in recovery/history exports or uploaded. This mechanism preserves local draft intent; it adds no identity, membership or server authority and has automated validation, not an independent cryptographic audit.

### Media upload drafts

Complete user-selected images, albums, expressions and videos may generate bounded, memory-only previews before upload; these are not partially downloaded remote attachments. Photos, videos and auto-hidden expressions paint only concealed derivatives from the first frame, while explicitly non-hidden expressions may paint their complete local original. File references and original/poster/derived object URLs remain in the unlocked runtime and are cleared on teardown, including late callbacks. At most three drafts totaling 256 MiB are retained. Only the normal committed encrypted outbox item becomes a message, using the same client ID across upload completion and retries. Chunk acknowledgements drive progress; the existing content-bound resume plan, original-byte encryption, hash validation and capability gates remain unchanged. Received media still require full authentication and original-length/hash verification before decoding.

Legacy registrations recover the assertion userHandle; credentialId is never substituted for user.id. Naming signals only rpId, the original userId, name and displayName. It never re-registers or mutates PRF salts, vault wrapping keys, room identities or history boundaries.

Names and registration user IDs are public authenticator metadata, not authentication capabilities. Initial labels are stored with platform registration metadata; later labels live in the existing local security store indexed by credentialId, so renaming does not rewrite vault wrappers or invalidate concurrent space sessions. The app displays labels only after verification, warns against sensitive names, and does not send this metadata to room/catalog services. This is UI access control, not encryption of the public label against local disk inspection. WebAuthn cannot read back provider labels; a resolved signal is not proof that every provider applied or synchronized the update. Unsupported APIs and missing legacy user handles disable editing. A successful signal followed by local failure is a partial result, never a claimed rollback.

Management verification retains its bounded foreground-only native ceremony and actual focused result consumption. Hidden visibility, pagehide, manual lock, freeze and idle expiry invalidate the session and late results. Visible blur and rename-input keyboard geometry no longer create an independent privacy hold or lock timer. Save still checks the live abort signal and expected durable vault in an abortable transaction; once dispatched, a system rename signal cannot be retracted and failure never claims rollback.

## Waiting-space deletion consistency

All room-deletion paths durably queue attachment cleanup in the deletion transaction. Pending blob reservations continue to count against the global quota until pre-delete writers have drained and physical removal succeeds; failed cleanup remains retryable across restart. Deleted room IDs cannot be recreated while their directory cleanup is pending. Cleanup does not discover or erase pre-existing unindexed directories from older versions; those require separately reviewed maintenance.

Deleting an unjoined room may include an opaque browser-catalog update in the same database transaction. The server authenticates the target room device and catalog write capability, checks the catalog revision, and rejects sealed rooms before either mutation. Directory contents remain encrypted; a lost success response can be reconciled from the authenticated catalog tombstone. Browser approval alone does not grant room deletion. Online unlocked catalog views poll for updates; offline views retain confirmed state until reconnection. Deletion markers suppress stale local rows and republishing; this is not remote erasure of historical exports.

## Bounded online message history and media cache

The [storage contract](docs/requirements/2026-09-24-storage-calls/storage-contract.md) defines the capability-gated message window. MLS self-updates bound each epoch to 128 accepted messages; signed continuous boundaries authorize skipping only classified ordinary-message gaps. Clients interleave retained application messages and commits and persist each step atomically. Lost controls or membership-chain history require repair, never unauthenticated checkpoints. The outer signature and inner ciphertext bind the sender sequence and ordinary/control classification; this adds server-visible metadata. Per-device durable accepted-sequence watermarks reject expired retries, including late unsent lower sequences, rather than resurrecting an evicted logical message. New-member history boundaries and original attachment retention remain in force. This protocol extension has automated coverage, not an independent cryptographic audit.

Disposable media cache shares a 1 GiB origin budget with a 64 MiB reserve for durable data when quota estimates are available. Static image/video display copies use HKDF-separated AES-GCM keys and full-manifest AAD; verified voice and opened files retain original encrypted bytes, with a 128 MiB ordinary-file admission limit. Original downloads/exports remain exact. Cache is excluded from recovery bundles, evicted by whole asset, and cleared on actual quota pressure without clearing history or keys. Browser eviction and device loss can remove it. Locking revokes plaintext resources; encrypted cache survives for later authenticated unlock.

It changes display geometry only, not original bytes, visibility, receipts, keys or access. ## Interaction task boundaries (2026-10-08)

Unsubmitted recovery read retries retain validated material only in the current foreground dialog, for at most two minutes. Closing, navigation, hiding or locking aborts reads and releases input, capability and decrypted choice references; stale responses cannot install another space. Submitted recovery continues only from its original encrypted durable task. Device-link polling shares one check/install operation for the same session and identity, honors server cooldowns, and does not treat approval presentation as MLS installation.

Terminal WebSocket access feedback suspends new send/encryption and transport retry; it never changes trusted membership, restores access or moves an encrypted outbox to another endpoint. Unknown denial cannot establish a remover or replacement cause. Existing local history and pending ciphertext remain in their original browser vault. Ordinary new-browser admission still uses independent keys, existing-device approval, and the existing post-join history boundary.

New `room-archive-v2` local masters receive independent encrypted record namespaces, including fresh slots for an existing live room. After normal browser unlock, repair may recover an orphaned local history owner only by authenticating its stored wrapper, room/creator/role and complete strict history projection. A live admission link is not a history capability. Discovery is bounded to 256 local slot identifiers, decrypts one envelope at a time, ignores other active endpoints, and does not persist a plaintext room/key index. An authenticated owner is forked into a fresh slot with compare-and-swap guards on the owner, current checkpoint and browser protection; lifecycle cancellation aborts the transaction. Both source slots and all encrypted records remain. Conflicting owners fail closed, and an older checkpoint cannot mask another authenticated checkpoint's missing tombstone under the same key and namespace. Existing admission boundaries, strict corrupted/missing history rejection and old-identity outbox suppression remain in force. This also handles already-installed legacy repair sessions when an intact local owner can be verified; it is not a promise to recover missing keys or actual damaged data. See [the requirement and evidence](docs/requirements/2026-10-22-repair-history-scope/README.md).


### Device-local notification management

Notification switches contain only device-local booleans and opaque room IDs, never keys, room names or content. A persistent service-worker gate suppresses queued wakes after master opt-out and survives shell-cache upgrades. The browser subscription is origin-wide: room opt-out removes only the authenticated room/device row, while master opt-out closes the gate and unsubscribes that browser endpoint. The server may associate room/device subscriptions sharing an endpoint; no payload, room ID or message content is added to provider requests.

User-authored fixed notification title/body are a separate, explicit exception to the switches-only data model: they are stored as one plaintext versioned record in the same durable local cache so the locked service worker can read them without opening the vault. They are never uploaded, inferred from chat content, or interpolated with private names. The editor explains lock-screen exposure and rejects oversized/control-character copy; malformed records fall back to generic text. Saving is atomic and shares the cross-tab notification lock; storage failure preserves the previous record. Privacy abort clears unsaved fields and prevents stale UI completion. Master opt-out still suppresses all copy. Clearing site data removes these preferences.

New-message wakes exclude authenticated send frames marked `countUnread=false`, covering read/reaction/delete/gallery-only events. This is transport metadata already used by unread counting, not an MLS-signed proof of the encrypted message kind; omitted values remain countable for older clients. Presence remains notification-free and duplicate commits cannot reclassify themselves into a wake. Browser-access authorization requests retain their separate wake path.

A read-only push-status query requires the exact active device bearer token and returns only its endpoint or null. Mutations retain endpoint-bound device signatures and final active-device checks. Managing another locally joined space uses the existing credential-bound local vault verification, without selecting the space or reading its chat history; catalog entries do not grant membership. Cross-tab notification writes are serialized, permission/worker/network waits are cancelled or bounded, and late work cannot enable a replacement privacy runtime. Master enable opens delivery only after server confirmations; failures keep the delivery gate closed. The push table upgrade atomically preserves rows and changes endpoint uniqueness to the room scope, retaining device keys and foreign-key cascades.

## Explicit user feedback, 2026-10-28

User feedback is a separate, intentionally administrator-readable channel, not encrypted private chat. Only an explicit submit sends an email address and feedback body with a random idempotency UUID. No room/device identity, chat history, keys or recovery materials are automatically attached. Drafts remain in the current page and clear on navigation/lock; runtime invalidation rejects late UI results. UI language resources are bundled static data and do not send user content to translation services.

The feedback endpoint requires a matching Origin host, a JSON content type, bounded 32 KiB input, an email of at most 254 characters and 1–5,000 Unicode code points of body text. Unknown fields and control characters are rejected. A source budget of five requests per ten minutes uses the existing trusted-proxy address resolver; capacity saturation fails closed. The separate SQLite table is bounded to 10,000 rows and refuses further new submissions when full, without silently deleting feedback. Exact same-ID/same-payload retries are idempotent; mismatched reuse returns conflict. Feedback is covered by existing database backups and currently has no automatic retention deletion. It is not joined to chat metadata or written to audit logs. Listing, full-text reads and read-state mutations require the existing administrator host/session boundary, with Origin and CSRF checks on mutations. Admin renders feedback as text, never HTML. Email and feedback are the explicitly submitted plaintext exception to the encrypted-chat storage contract; this does not grant administrators access to private chat.
