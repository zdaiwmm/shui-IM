# Security model

Quiet Room is a two-person, multi-device encrypted chat. Each participant may authorize up to three independent devices. The browser encrypts message, reply metadata, album membership, and image content before upload. The Node service stores public device keys and MLS key packages, opaque signed MLS welcome/Add/Remove messages, opaque message envelopes, per-device token hashes, device activation boundaries, signed delivery receipts, ordering metadata, push subscriptions, and encrypted image chunks. It also temporarily processes each authenticated socket's chat/away view for presence, but does not persist that state in the application database. It does not receive WebAuthn PRF output, vault master keys, recovery codes, pairing secrets, MLS private state, plaintext messages, reply targets or previews, album ordering, filenames, MIME types, or original image hashes.

## Cryptographic construction

- Each device generates separate P-256 ECDH and ECDSA identity key pairs in Web Crypto and an RFC 9420 MLS key package using `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- The MLS credential embeds the device ID and MLS signature public key. The device's P-256 identity key signs that binding; clients validate it against the public bundle authenticated by the invitation proof.
- The one-time invite pins the creator public-key fingerprint and carries a random pairing secret in the URL fragment.
- The joining device authenticates its public bundle with HMAC-SHA-256 under that pairing secret.
- New rooms create an initial two-member RFC 9420 MLS group. The creator signs the opaque welcome envelope with its P-256 identity key. Additional devices enter through a signed MLS Add commit and their own welcome; removals use signed MLS Remove commits. MLS advances the application-message secret tree on every message and the group epoch on membership change.
- Each device has a distinct random server access token. A new-device link carries a short-lived capability in its URL fragment, requires a manually compared six-digit safety code, and cannot activate the claimant without an existing same-participant device signing the MLS Add commit. The service sees the raw link capability while verifying link requests but stores only its hash; expired links and never-approved pending members are deleted.
- Activation records the room's current message and receipt sequences as the device's lower synchronization bounds. A late receipt for a pre-activation message is projected to a sequence-only skip marker for that device, so it cannot reveal an old message ID and cannot block later receipt processing. The service also parses the public MLS epoch field and rejects validly signed application ciphertext from an obsolete epoch, forcing the sender to process the membership change and re-encrypt. The new welcome contains current group state, not prior epoch secrets.
- The sender additionally signs each complete outer envelope with ECDSA P-256/SHA-256. The server verifies this signature before persistence, and recipients verify it again before MLS processing.
- Legacy rooms retain the original per-message random AES-256-GCM content key and ephemeral P-256 ECDH wrapping construction. They do not acquire forward secrecy automatically and must be replaced with a new room.
- After a recipient verifies, decrypts, and persists a message, it signs a receipt that binds the room ID, message ID, server sequence, receiver device ID, and receipt time. Only that receipt promotes the sender UI from server-stored to peer-delivered.
- Images are encrypted in 2 MiB AES-256-GCM chunks. A unique eight-byte random prefix plus a four-byte chunk counter forms each nonce. The authenticated data binds the blob ID, index, total chunk count, and original size.
- The encrypted image manifest contains the file key and SHA-256 digest. A receiver accepts a reconstructed image only when its exact byte length and digest match.
- Selecting 2–9 images creates one strictly validated `image-album` application payload containing ordered, unique encrypted manifests with a 256 MiB aggregate-original limit. The sender requires every active device to have refreshed its `image-album-v1` capability before sending, preventing an old client from being advanced past an unknown payload. The grouping, order, reply relation, and generic non-content reply labels remain inside the MLS ciphertext even though the service necessarily observes separate encrypted blob reservations and transfer sizes. Visible reply excerpts are derived only from encrypted local history, so a newly linked device does not receive copied pre-join text through a later reply.
- A random 256-bit AES-GCM master key encrypts the local vault, history, outgoing-message queue, pending-receipt queue, upload-resume plans, reading anchor, and emoji/meme favorites. Version-3 vaults derive the key-encryption key with HKDF-SHA-256 from WebAuthn PRF output after authenticator user verification, then wrap the master key. Both single-device and syncable passkeys are accepted; the immutable backup-eligibility flag is recorded and checked on later assertions. PRF output and derived keys are not persisted.
- Recovery wraps the master key to a separate random 256-bit recovery code and stores only the encrypted wrapper beside the encrypted vault payload. Recovery creates a new passkey-only wrapper before the conversation opens. Legacy password and gesture-based vault formats remain read-only migration inputs.

## What this protects

- Database, filesystem, object-volume, and backup disclosure does not reveal message or image contents without an endpoint key.
- The service cannot forge a valid participant message or silently modify ciphertext.
- A device with only the room ID cannot join or decrypt. A claimed add-device link remains pending until its safety code is checked and an existing device commits the MLS Add.
- A newly authorized device cannot fetch server records at or before its activation boundary and cannot decrypt messages from prior MLS epochs. Removal invalidates that device's server token and push subscription and advances the MLS epoch for future messages.
- Client message IDs make retries idempotent. Transactional room sequence numbers define the display order.
- An outgoing payload is encrypted into IndexedDB before its first network send. Reconnect and acknowledgement-loss retries retain the same client message ID, while a server uniqueness constraint prevents duplicate commits.
- A failed or interrupted join is retried with the same locally persisted device identity, so a committed server join cannot strand the second slot merely because the response was lost.
- Inline thumbnails are not server-generated derivatives. The endpoint downloads ciphertext only when media is in or near the visible region, verifies and decrypts the original locally, and exposes it through a revocable object URL. Closing the viewer removes its rendered overlay; locking and runtime teardown revoke or discard the cached endpoint objects.
- Outside a user-initiated image picker, losing page visibility or window focus immediately replaces rendered content with the white privacy curtain, closes the socket, aborts file transfers, revokes object URLs, and releases in-memory application references to the decrypted session. A passkey prompt may suppress its own blur or hidden event only before the decrypted session is opened. `pagehide` always locks.

## Explicit limitations

New rooms use the standardized RFC 9420 MLS protocol, but the selected browser-capable `ts-mls` implementation states that it has not undergone a formal security audit. The integration must pass independent cryptographic review before high-risk production claims. Legacy rooms have no forward secrecy.

Per-message MLS secret-tree advancement provides forward secrecy for deleted generations. Full post-compromise recovery requires authenticated epoch updates after the attacker loses endpoint access, clean endpoints, and an audited incident procedure; that complete mechanism is not implemented or claimed here.

Removing the application gesture does not change MLS, message/attachment encryption, the 256-bit local master key, or AES-GCM. It does remove one independent knowledge factor from local vault access: version-3 unlock security is the PRF secret plus the authenticator and operating system's biometric/device-password policy. A syncable passkey is not strictly bound to one physical device, so deployments requiring that property must mandate a compatible single-device authenticator or hardware security key. Recovery is protected separately by its independent random 256-bit code. A legacy version-2 gesture is requested once only because it is cryptographic input needed to unwrap that existing vault, and is discarded after migration.

A fully malicious server can replace the JavaScript it serves and attempt to steal plaintext or keys on a later visit. CSP, pinned dependencies, HTTPS, and a separate static release channel reduce this risk but do not eliminate it. Strong protection from an actively malicious hosting server requires a signed client distributed from a separate trust root.

The server observes metadata needed for operation: room identifier, device pseudonyms/names and public keys, roles, device-link creation/claim/activation times, MLS key-package/welcome/commit sizes and epochs, per-device history boundaries, connection IP, ciphertext and encrypted-blob sizes, message and upload counts, acceptance time, delivery-receipt time, total order, registered push endpoints, and each live authenticated socket's reported `chat` or `away` view. It does not see encrypted reply references or encrypted album membership. A push provider observes endpoint and timing/volume metadata even though the request carries no payload. The service can delay, drop, or deny delivery. Cryptography cannot force delivery or make a disconnected network instantaneous.

Chat-page presence is deliberately separate from WebSocket connection state. A socket starts `away`; the client reports `chat` only on the chat surface, caches the desired view, and replays it after reconnect authentication. The service computes each role as online when any active socket for that role reports `chat`, holds this per-socket state only in process memory, and clears/recomputes it on `away`, close, membership changes, or ping/pong timeout. This is behavioral metadata visible to and asserted through the service. It is not signed inside MLS, is not end-to-end verifiable, does not prove that the named person is attending the page, and must not be used as a safety-code or delivery guarantee. Application non-persistence also does not prevent infrastructure, proxy, or process telemetry from observing timing.

The encrypted reading anchor and expression favorites are device-local convenience state. They are not synchronized, cannot establish peer behavior, and remain readable to an attacker who compromises the unlocked endpoint. Bundled meme SVGs avoid runtime third-party requests, but their OpenMoji 17.0.0 CC BY-SA 4.0 attribution and share-alike obligations remain release requirements.

Page-level double-tap/gesture zoom suppression, transparent application bars, and transition timing are interface behavior rather than cryptographic controls. Safari and Chrome retain control of their native toolbars; `theme-color`, edge-to-edge viewport settings, and installed-PWA display hints cannot guarantee a transparent browser-owned bottom bar. These best-effort hints must not be represented as a privacy or anti-spoofing boundary.

An endpoint compromise, malicious browser extension, screen recorder, operating-system compromise, or unlocked physical device can read plaintext. The hidden long-press entry is a privacy curtain, not an authentication boundary.

## Deployment requirements

- Terminate only modern HTTPS and proxy WebSocket upgrades correctly. Never expose this service over plaintext Internet HTTP.
- Do not add third-party analytics, tag managers, remote scripts, error collectors, or session replay.
- Keep `data/` on a private persistent volume with restrictive filesystem permissions.
- Run the included online backup worker, replicate completed snapshots to an independent failure domain with versioning/deletion protection, alert on backup age/capacity, and perform timed restore drills. See `OPERATIONS.md`.
- Keep the built-in request/frame limits, connection limits, message quotas, blob reservations, and incomplete-upload garbage collection enabled. Apply independent limits at the reverse proxy as defense in depth. A single encrypted chunk is slightly larger than 2 MiB.
- Review client dependency updates and run the complete test suite before every release.
- Keep the OpenMoji version, source, license file, attribution, and any required share-alike notices with every distribution containing the bundled meme assets; do not replace the local assets with runtime third-party loads without a new privacy and CSP review.
- Validate chat-page presence, soft-keyboard focus, reading-anchor restoration, image/gallery/viewer transitions, page-zoom suppression, safe areas, and page/native-chrome boundaries on supported real iOS and Android devices. Browser simulation cannot establish native-toolbar behavior.
- Treat both recovery parts as private-key material. Keep the recovery JSON and its independently displayed recovery code in different locations.
- A recovery checkpoint rebinds the same physical-device identity; it does not automatically revoke a still-running copy of that checkpoint. Keep the source copy offline during recovery, then use device management from another trusted device to remove any compromised device and advance the MLS epoch.
- Satisfy every blocking item in `PRODUCTION_SECURITY_GATE.md`, including independent cryptographic and application-security reviews, before using the service for high-risk communications.

## Reporting a vulnerability

Do not include real messages, invitations, recovery packages, private keys, or server data in a report. Provide a minimal synthetic reproduction and the affected commit or release identifier through the maintainer's private security channel.
