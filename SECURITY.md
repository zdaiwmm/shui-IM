# Security model

Quiet Room is a two-person, multi-device encrypted chat. Each participant may authorize up to three independent devices. The browser encrypts message, reply metadata, album membership, and image content before upload. The Node service stores public device keys and MLS key packages, opaque signed MLS welcome/Add/Remove/replacement messages and recovery authorization proofs, opaque message envelopes, per-device token hashes, device activation boundaries, signed delivery receipts, ordering metadata, push subscriptions, and encrypted image chunks. It also temporarily processes each authenticated socket's chat/away view for presence, but does not persist that state in the application database. It does not receive WebAuthn PRF output, vault master keys, recovery codes, pairing secrets, MLS private state, plaintext messages, reply targets or previews, album ordering, filenames, MIME types, or original image hashes.

## Cryptographic construction

- Each device generates separate P-256 ECDH and ECDSA identity key pairs in Web Crypto and an RFC 9420 MLS key package using `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- The MLS credential embeds the device ID and MLS signature public key. The device's P-256 identity key signs that binding; clients validate it against the public bundle authenticated by the invitation proof.
- The one-time participant invite pins the creator public-key fingerprint and carries a random pairing secret in a strictly validated `#invite` URL fragment. Additional-device links use a distinct, strictly validated `#device` fragment and exact schema; the client never reinterprets a valid device capability as a participant invitation merely because another device was already authorized.
- The joining device authenticates its public bundle with HMAC-SHA-256 under that pairing secret.
- New rooms create an initial two-member RFC 9420 MLS group. The creator signs the opaque welcome envelope with its P-256 identity key. Additional devices enter through a signed MLS Add commit and their own welcome; removals use signed MLS Remove commits. MLS advances the application-message secret tree on every message and the group epoch on membership change.
- Each device has a distinct random server access token. A new-device link carries a short-lived capability in its URL fragment, requires a manually compared six-digit safety code, and cannot activate the claimant without an existing same-participant device signing the MLS Add commit. The service sees the raw link capability while verifying link requests but stores only its hash; expired links and never-approved pending members are deleted.
- Activation records the room's current message and receipt sequences as the device's lower synchronization bounds. A late receipt for a pre-activation message is projected to a sequence-only skip marker for that device, so it cannot reveal an old message ID and cannot block later receipt processing. The service also parses the public MLS epoch field and rejects validly signed application ciphertext from an obsolete epoch, forcing the sender to process the membership change and re-encrypt. The new welcome contains current group state, not prior epoch secrets.
- The sender additionally signs each complete outer envelope with ECDSA P-256/SHA-256. The server verifies this signature before persistence, and recipients verify it again before MLS processing.
- Legacy rooms retain the original per-message random AES-256-GCM content key and ephemeral P-256 ECDH wrapping construction. They do not acquire forward secrecy automatically and must be replaced with a new room.
- After a recipient verifies, decrypts, and persists a message, it signs a receipt that binds the room ID, message ID, server sequence, receiver device ID, and receipt time. Only that receipt promotes the sender UI from server-stored to peer-delivered.
- Images are encrypted in 2 MiB AES-256-GCM chunks. A unique eight-byte random prefix plus a four-byte chunk counter forms each nonce. The authenticated data binds the blob ID, index, total chunk count, and original size.
- The encrypted image manifest contains the file key and SHA-256 digest. A receiver accepts a reconstructed image only when its exact byte length and digest match.
- Imported video and other file attachments retain the same original-byte encrypted chunk transport and length/digest verification. Videos remain `file` or `gallery-file` payloads, including previously stored compatible videos; display does not add a message kind or change the `file-message-v1` compatibility gate. A filename extension is used to classify video only when MIME is empty or `application/octet-stream`; an explicitly typed document is not made playable by its filename.
- User selections have no nine-image cap. Chat groups originals in order within the existing nine-image and 256 MiB per-message limits; each multi-image group is a strictly validated `image-album` payload with unique encrypted manifests. Gallery multi-selection creates individual gallery-only payloads. The sender requires every active device to have refreshed its `image-album-v1` capability before sending an album, preventing an old client from being advanced past an unknown payload. Grouping, order, and reply relation remain inside MLS ciphertext even though the service observes separate blob reservations and transfer sizes. Visible reply excerpts are derived only from encrypted local history, so a newly linked device does not receive copied pre-join text through a later reply.
- A random 256-bit AES-GCM master key encrypts the local vault, history, outgoing-message queue, pending-receipt queue, upload-resume plans, reading anchor, unsent text draft, recovery-reminder preferences, local-only hidden message IDs, and creator-Safe pin/hide projections. Version-3 vaults derive the key-encryption key with HKDF-SHA-256 from WebAuthn PRF output after authenticator user verification, then wrap the master key. Both single-device and syncable passkeys are accepted; the immutable backup-eligibility flag is recorded and checked on later assertions. PRF output and derived keys are not persisted.
- “仅为我删除” and Safe Pin/Delete are encrypted endpoint projections. They never alter server order, message ciphertext, the peer's state, or the chat bubble represented by a Safe-only action. “为所有人删除” is instead a strict `message-delete` payload inside the ordinary signed MLS message/outbox path. The target must be an exact locally available confirmed chat message, both target and deleting devices must map to the same role in authenticated membership history, the delete event must follow the target in server order, and every active device must advertise `message-delete-v1`. The server can observe another opaque message envelope but not its delete target or scope.
- QR3 recovery uses a random 128-bit locator plus a random 256-bit secret. Domain-separated HKDF derives independent retrieval and AES-256-GCM encryption keys. Each random archive key is inside the encrypted recovery checkpoint; authenticated archive indexes bind ciphertext digests, room, archive and part. The server stores ciphertext and scoped capability hashes, never codes or decrypting keys. The local code is encrypted under the device master key. See `RECOVERY_BACKUPS.md` for exact domains, formats, rotation and limits. Legacy password/gesture vaults and already-imported old recovery formats remain migration inputs.

## Real-time call construction

Two-person calls use browser-to-browser DTLS-SRTP, including when coturn relays
the encrypted packets. There is no media decoding, transcoding or recording on
the application server. SDP fingerprints and ICE candidates are carried inside
separately encrypted AES-256-GCM signaling envelopes, derived with domain-separated
P-256 ECDH/HKDF-SHA-256 and signed in full with the device ECDSA identity. Strict
recipient/room binding, expiry, replay checks and membership fencing apply.

Before creating a peer connection, requesting call media or publishing local
SDP, the client verifies the actual local MLS tree and a device-signed attestation
of the complete public bundle and role. The attestation signing key must match
the MLS-bound device identity; an unverified server roster or server-supplied
verified-device list is insufficient. Signed membership history also pins prior
identities. This attestation is required again for answering and refreshing ICE.

Signaling derives from long-term device ECDH keys and does not claim forward
secrecy after device-key compromise. Media keys use a separate ephemeral DTLS
exchange. The server observes routing and call timing; TURN sees traffic and
address metadata, while direct peers may learn each other's public IP. TURN has
short-lived authenticated credentials rather than an anonymous relay. Background
or privacy teardown stops capture even if the desktop vault remains temporarily
unlocked in memory. Calls do not remove the endpoint, malicious-served-JavaScript
or independent-audit limitations below. See `CALLS.md` for operational details.

## What this protects

- Safe photo properties are parsed only after the existing original-byte authentication and integrity check. The locally bundled EXIF parser runs in a dedicated worker that is terminated on close, lock, or a four-second deadline; parsed fields are rendered as bounded text, never HTML. The UI entry is creator/Safe-only and does not change who can decrypt an existing chat original or what metadata it contains. GPS coordinates are not sent to maps, reverse-geocoding services, or any other third party. No new encrypted payload, server metadata, plaintext persistence, or history access is introduced. Animated GIF/WebP/APNG playback uses the browser decoder; the pause frame is a bounded in-memory Canvas derivative, never uploaded and never used for original downloads. Paging/closing and privacy teardown revoke that derivative and cancel pending preparation; late results cannot restore a closed or locked viewer.
- Database, filesystem, object-volume, and backup disclosure does not reveal message or image contents without the relevant endpoint or recovery secret. Retaining decryptable history archives deliberately makes that archived history recoverable with its code; this is not a claim that archived content disappears with MLS ratchet generations.
- The service cannot forge a valid participant message or silently modify ciphertext.
- A device with only the room ID cannot join or decrypt. A claimed add-device link remains pending until its safety code is checked and an existing device commits the MLS Add.
- A newly authorized device cannot fetch server records at or before its activation boundary and cannot decrypt messages from prior MLS epochs. Removal invalidates that device's server token and push subscription and advances the MLS epoch for future messages.
- Client message IDs make retries idempotent. Transactional room sequence numbers define the display order.
- An outgoing payload is encrypted into IndexedDB before its first network send. Reconnect and acknowledgement-loss retries retain the same client message ID, while a server uniqueness constraint prevents duplicate commits.
- A failed or interrupted join is retried with the same locally persisted device identity, so a committed server join cannot strand the second slot merely because the response was lost.
- Inline thumbnails are not server-generated derivatives. The endpoint downloads ciphertext when media is needed, verifies and decrypts the original locally, and exposes it through a revocable object URL. Concealed portrait and panorama frames reuse that same verified object URL for a cover-fitted blurred background behind the contain-fitted foreground; no second plaintext derivative is uploaded or persisted. For video, only after authenticating every chunk and verifying the complete original length and digest does the browser decoder produce a preview-frame JPEG through a local Canvas. This derivative is memory-only, never uploaded or persisted, and never replaces or changes the encrypted original. Chat, gallery, and viewer reuse verified plaintext media and previews only during the unlocked runtime. The endpoint may persist the opaque server ciphertext chunks in IndexedDB across locks; their attachment keys remain inside the encrypted vault/history, and every reconstruction repeats per-chunk AES-GCM authentication, original-length validation and the complete SHA-256 check. Invalid local ciphertext is deleted and fetched once from the authenticated server; quota eviction merely causes another download. A video reached through viewer paging starts paused and remains horizontally pageable. Closing or paging away pauses video and removes the player's source; privacy teardown cancels pending preview work, revokes object URLs, and clears decrypted media and preview caches. Late results must not repopulate a locked runtime.
- Images and videos are the permitted in-app media-display exceptions. Video playback uses a browser video element and native controls; unsupported formats preserve verified original-file download. After complete authentication and integrity verification, a strict allowlist of inert readable document types may be handed to the browser/operating-system reader through a local object URL; application code does not interpret or render their contents. Active, unsupported, and unknown ordinary files remain download-only. Browser/system decoding remains part of the endpoint attack surface; verifying a file's digest confirms the sender's original bytes, not that its content is safe for a vulnerable decoder.
- The creator gallery's 保险箱 label and default thumbnail blur are visual concealment within the unlocked session. Its 相册 category includes photos and videos, with the same first-tap reveal and second-tap viewer behavior; its 文件 category includes other locally available chat and gallery-only files. Every locally available chat attachment is projected into the creator's Safe automatically, without creating another server record or expanding an endpoint's history boundary. Revealing individual items or all current thumbnails does not perform new authentication; blur does not prevent an unlocked endpoint from accessing cached originals. Reveal state is memory-only for the current visit, clears on leaving or runtime teardown, and never changes attachment bytes, keys or permissions. Safe Pin changes only the endpoint's order inside one category, and Safe Delete hides only the selected asset on that endpoint; neither action alters the source chat bubble or peer. Explicit gallery-only archive restoration includes media and valid encrypted room-wide delete projections without adding old chat bubbles or making their contents available as chat reply previews; normal device-join boundaries remain unchanged.
- Every unowned blur and hidden-visibility event synchronously shows an already-mounted opaque curtain before runtime teardown. A direct trusted primary pointer activation on the visible unlocked mobile chat textarea may instead create a separate one-use keyboard handoff for at most 1.2 seconds, solely to absorb Safari transferring visible window focus into its native keyboard. It is bound to the current runtime, session, chat surface and textarea; programmatic focus and an already-open keyboard cannot create it. Fresh post-tap keyboard-opening geometry and the first owned visible blur may arrive in either order and jointly clear the handoff; window-focus return may clear it independently, while geometry evidence alone keeps the owner available for that blur. A second blur, dual-clock timeout after consumption, hidden visibility, pagehide, freeze, persisted pageshow, explicit lock, idle expiry, native chooser/media ownership, runtime/session change, detached input or leaving chat invalidates it and follows the ordinary conceal/lock path. Starting a chooser or media owner clears only an unconsumed keyboard token; a consumed owner conflict fails closed instead of being replaced. Hard lifecycle signals never wait for this handoff. Ordinary desktop browsers clear rendered history, sockets, transfers and media but may retain an unlocked vault session only in page memory until 30 minutes after the last active in-app interaction. Cover activity, foreground return and remote call updates never extend this deadline. A deliberate one-second corner hold or two-second F hold rechecks both wall-clock and monotonic deadlines, validates the unchanged durable vault, and decrypts a fresh snapshot with the retained key. Changed/deleted vaults require normal verification. These bounded handoffs extend the window of endpoint decryption capability; they add no key or plaintext persistence and are not authentication.
- Chat photos, album cells and video still previews also start visually blurred. One tap reveals a thumbnail and another opens its viewer. A completed downward conversation drag or downward viewer dismissal conceals chat thumbnails; revealed media follows a damped pull until release, while cancellation or privacy teardown conceals immediately. Chat reveal state exists only in unlocked-session memory; the opaque privacy curtain synchronously clears it and closes any viewer before the ordinary mobile blur debounce, so quick focus return and late thumbnail decoding cannot restore a previous reveal. This is visual concealment, with no new authentication, persistence, permission or cryptographic boundary.
- Mobile/tablet browsers and installed PWAs retain immediate hidden-visibility locking and the 250 ms ordinary-blur teardown debounce. The one consumed blur owned by the narrowly scoped keyboard handoff above is not an ordinary blur; without that fresh token, including after it is consumed, the original synchronous curtain and debounce apply. Their normal idle limit remains 10 minutes; an active foreground call suspends that mobile idle timer, ending or leaving the call restores the normal policy. Desktop calls remain subject to the 30-minute real inactivity deadline.
- On all clients, pagehide, freeze, persisted pageshow, explicit lock, idle expiry and unowned focus loss during native surfaces discard retained sessions, stop capture, close sockets and clear decrypted runtime references. Export, clipboard and confirmation surfaces never acquire a foreground handoff. Foreground return never unlocks by itself. Gateway WebAuthn prompts alone have a bounded hidden-visibility teardown exemption before a conversation or socket opens, including recovery and migration. A result received while the visible document is still unfocused remains behind the opaque curtain and requires real focus within 1.5 seconds before it can be consumed; hidden settlement fails closed. Pagehide, explicit lock and idle lock always take precedence.
- Reaction targets and emoji/removal values use strict encrypted payloads and the existing signed message/outbox protocol. Badges require an exact locally available confirmed target ID, sequence, and sender. Events merge in server order, with one latest reaction per participant role. Reopening scans encrypted history in bounded batches without persisting a plaintext reaction index. All active devices must advertise support before sending this payload.
- A valid room-wide delete tombstone suppresses the target from the local chat and creator Safe projections after decryption and authenticated membership validation. It does not recall plaintext already displayed, erase another endpoint that remains offline or obsolete, destroy attachment ciphertext, rewrite backups/exports, or remove operating-system copies. Local-only hides and room-wide tombstones are therefore UI/history projections, not physical-erasure guarantees.

The cover's unread number uses a separate random 256-bit observer token. Local storage holds only this token, room/device IDs, and the last confirmed count; the server stores only its hash. The observer can GET a count and cannot read ciphertext, attachments, room state, open a socket, or advance the read cursor. Registration and read updates require the normal active device credential, and device removal/recovery fences the observer too. The server additionally persists a monotonic per-device read cursor and the sender's authenticated `countUnread` hint. The hint excludes gallery and reaction events and is not signed inside MLS; neither it nor the resulting count proves content type, reading, or delivery. It reveals countability and reading metadata to the service. Old clients omit the hint and their events default to countable. Initial enrollment does not promote the durable receive cursor to a read cursor: downloading ciphertext is not visible reading. Registration retries preserve the server read cursor; only messages actually visible in an active chat advance it.
- A user-opened chooser may own one visible blur for up to five minutes, and microphone/camera permission for up to thirty seconds, only from an unlocked, focused, visible session. These operations clear and replace any unconsumed keyboard handoff; ownership cannot stack. Focus return consumes the handoff; another departure does not reuse it. Hidden visibility and hard lifecycle/lock signals retain their normal teardown. A permission or chooser result preceding focus has at most a 250 ms return edge, then locks if focus has not returned. Uploads remain gated on visible focus and original room/device ownership. For a file chooser, a real background transition, hard lifecycle event, second focus loss, ownership loss, or focus return without a prompt `change`/`cancel` invalidates and detaches the hidden input; late events are ignored and no selection is retained across unlock. Browser code cannot reliably identify why a visible window lost focus or force an operating-system-owned picker/tooltip to close, so both chooser ownership and the shorter keyboard ownership are explicit usability tradeoffs rather than proof of foreground state. DOM detachment is best-effort privacy cleanup, not a guarantee about native UI. Microphone/camera prompts keep their existing bounded result edge. No persistent permission is forced and no idle media track is kept to avoid prompts. Unsent text is restored from encrypted local preferences after unlock.

## Explicit limitations

New rooms use the standardized RFC 9420 MLS protocol, but the selected browser-capable `ts-mls` implementation states that it has not undergone a formal security audit. The integration must pass independent cryptographic review before high-risk production claims. Legacy rooms have no forward secrecy.

Per-message MLS secret-tree advancement provides forward secrecy for deleted generations. Full post-compromise recovery requires authenticated epoch updates after the attacker loses endpoint access, clean endpoints, and an audited incident procedure; that complete mechanism is not implemented or claimed here.

Removing the application gesture does not change MLS, message/attachment encryption, the 256-bit local master key, or AES-GCM. It does remove one independent knowledge factor from local vault access: version-3 unlock security is the PRF secret plus the authenticator and operating system's biometric/device-password policy. A syncable passkey is not strictly bound to one physical device, so deployments requiring that property must mandate a compatible single-device authenticator or hardware security key. Recovery is protected separately by its independent random 256-bit code. A legacy version-2 gesture is requested once only because it is cryptographic input needed to unwrap that existing vault, and is discarded after migration.

A fully malicious server can replace the JavaScript it serves and attempt to steal plaintext or keys on a later visit. CSP, pinned dependencies, HTTPS, and a separate static release channel reduce this risk but do not eliminate it. Strong protection from an actively malicious hosting server requires a signed client distributed from a separate trust root.

The server observes metadata needed for operation: room identifier, device pseudonyms/names and public keys, roles, device-link creation/claim/activation times, MLS key-package/welcome/commit sizes and epochs, per-device history boundaries, connection IP, ciphertext and encrypted-blob sizes, message and upload counts, acceptance time, delivery-receipt time, total order, registered push endpoints, and each live authenticated socket's reported `chat` or `away` view. It does not see encrypted reply references or encrypted album membership. A push provider observes endpoint and timing/volume metadata even though the request carries no payload. The service can delay, drop, or deny delivery. Cryptography cannot force delivery or make a disconnected network instantaneous.

Chat-page presence is deliberately separate from WebSocket connection state. A socket starts `away`; the client reports `chat` only on the chat surface, caches the desired view, and replays it after reconnect authentication. The service computes each role as online when any active socket for that role reports `chat`, holds this per-socket state only in process memory, and clears/recomputes it on `away`, close, membership changes, or ping/pong timeout. This is behavioral metadata visible to and asserted through the service. It is not signed inside MLS, is not end-to-end verifiable, does not prove that the named person is attending the page, and must not be used as a safety-code or delivery guarantee. Application non-persistence also does not prevent infrastructure, proxy, or process telemetry from observing timing.

The encrypted reading anchor and recovery-reminder preference are device-local convenience state. They are not synchronized, cannot establish peer behavior, and remain readable to an attacker who compromises the unlocked endpoint. The composer has no dedicated emoji, meme, or expression-favorites panel; message reactions are a separate encrypted feature.

Page-level double-tap/gesture zoom suppression, transparent application bars, and transition timing are interface behavior rather than cryptographic controls. Safari and Chrome retain control of their native toolbars; `theme-color`, edge-to-edge viewport settings, and installed-PWA display hints cannot guarantee a transparent browser-owned bottom bar. These best-effort hints must not be represented as a privacy or anti-spoofing boundary.

An endpoint compromise, malicious browser extension, screen recorder, operating-system compromise, or unlocked physical device can read plaintext. The hidden long-press entry is a privacy curtain, not an authentication boundary.

The browser-load-failure cover is visual concealment. A website cannot guarantee when the operating system captures a task-switcher or tab thumbnail, remove an already cached snapshot, or prevent screenshots. Synchronous blur/visibility concealment minimizes the time sensitive content remains visible after lifecycle notification; it does not provide native screenshot-protection APIs. Native text selection remains browser-owned as well: selecting the inline read-only control cannot guarantee that every iOS version immediately opens its edit toolbar.

## Deployment requirements

- Terminate only modern HTTPS and proxy WebSocket upgrades correctly. Never expose this service over plaintext Internet HTTP.
- The canonical production origin is `https://ai.shui.click`. Keep WebAuthn bound to the exact `ai.shui.click` RP ID, keep API and WebSocket traffic same-origin, and retain control of both its DNS and certificate renewal. Do not broaden the RP ID to `shui.click` or add wildcard CORS for migration convenience.
- The retired `chat.mijiu.cloud` origin must not serve application JavaScript. Keep its DNS and certificate under control and return only a no-script redirect or a static retirement response so an old WebAuthn/IndexedDB origin cannot become a dangling takeover target.
- Do not add third-party analytics, tag managers, remote scripts, error collectors, or session replay.
- Keep `data/` on a private persistent volume with restrictive filesystem permissions.
- Run the included online backup worker, replicate completed snapshots to an independent failure domain with versioning/deletion protection, alert on backup age/capacity, and perform timed restore drills. See `OPERATIONS.md`.
- Keep the built-in request/frame limits, connection limits, message quotas, blob reservations, and incomplete-upload garbage collection enabled. Apply independent limits at the reverse proxy as defense in depth. A single encrypted chunk is slightly larger than 2 MiB.
- Review client dependency updates and run the complete test suite before every release.
- Validate chat-page presence, soft-keyboard focus, reading-anchor restoration, image/gallery/viewer transitions, page-zoom suppression, safe areas, and page/native-chrome boundaries on supported real iOS and Android devices. Browser simulation cannot establish native-toolbar behavior.
- Protect the QR3 code as private-key material and save it separately. Automatic backups contain encrypted identity and archive keys. The local encrypted code is viewable after fresh passkey verification; this UI gate does not hide it from malicious JavaScript in an already unlocked endpoint. No code escrow or administrator recovery exists.
- MLS recovery authorizes a fresh device, token and leaf through an old-identity signed request bound to the room, request ID, replacement public bundle, new token hash and an expiry of at most 15 minutes. Another trusted active device verifies this proof and commits a single Remove+Add replacement. A signed, contiguous membership chain anchored in the checkpoint authenticates the helper without replaying old application ratchets. Other active devices must advertise protocol support before a request is accepted.
- A pending recovery fences the original device; completing it atomically revokes the original token/push subscription and activates the replacement at a fresh history boundary. The restored device does not automatically fetch prior records or reuse checkpoint sending keys. It immediately rotates recovery protection, preserving all archive keys under the new code before atomically retiring the old online route. Explicit archive restore with the new code is the only recovery exception to the normal pre-join history rule; it does not alter MLS/network boundaries. Old code plus already copied old ciphertext remains decryptable offline. An expired request releases the original device. This protocol protects against stale checkpoint reuse; it cannot distinguish the legitimate owner from an attacker who possesses both recovery parts.
- Serialize the whole local vault read/derive/write operation under the physical current-record lifecycle lock, including unlock/import/delete/migration. Cross-tab Web Locks plus an IndexedDB expected-snapshot check prevent an older session from overwriting a newer ratchet or vault. Stale sessions fail closed and require re-unlock.
- Satisfy every blocking item in `PRODUCTION_SECURITY_GATE.md`, including independent cryptographic and application-security reviews, before using the service for high-risk communications.

## Reporting a vulnerability

Do not include real messages, invitations, recovery packages, private keys, or server data in a report. Provide a minimal synthetic reproduction and the affected commit or release identifier through the maintainer's private security channel.
