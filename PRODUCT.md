# Product

## Register

product

## Users

Two trusted people use the product from mobile or desktop browsers and installed PWAs. Each person may authorize up to three independently keyed devices. They need a quiet private channel for exchanging text and original-quality images without creating accounts. They expect the interface to stay concealed until intentionally unlocked, and they accept that losing both the usable local vault and recovery code makes history unrecoverable.

## Product Purpose

Provide a small, dependable one-to-one encrypted chat whose cloud service can order, relay, and retain ciphertext but cannot read message or image contents. Success means all authorized devices exchange new messages in a deterministic order, reconnect without gaps or duplicates, review only their locally available history and images, and verify that downloaded image bytes match the original upload.

## Brand Personality

Quiet, private, dependable. The product should feel composed and discreet, with clear system feedback and no security theater in its unlocked interface.

## Anti-references

Do not resemble a neon cyber-security dashboard, hacker terminal, crypto trading product, social feed, or decorative glassmorphism showcase. Avoid theatrical lock imagery, fear-based copy, excessive cards, gratuitous animation, and unfamiliar controls where platform conventions work better.

## Design Principles

1. Privacy is structural: sensitive content and keys stay on the endpoint, while visual concealment is treated only as a privacy curtain.
2. Calm before cleverness: standard controls, concise copy, and restrained feedback keep attention on the conversation.
3. Make system truth visible: pending, delivered, disconnected, locked, failed, and recovery states must be unambiguous.
4. Preserve originals: uploaded image bytes remain unchanged through encryption, storage, download, and decryption.
5. Fail closed: authentication, decryption, integrity, version, and sequence errors never silently downgrade or display partial content.

## Delivery Semantics

- **等待发送** (accessible description: 等待服务器): the payload is durably encrypted in the local outbox but has not yet been observed in the server sequence.
- **单柄对勾 / 已发送** (accessible description: 服务器已保存): the signed ciphertext has a committed server sequence and can be recovered by reconnect synchronization.
- **双柄对勾 / 已送达** (accessible description: 对端已安全接收): at least one active device owned by the other participant verified, decrypted, and durably stored the message, then signed a receipt bound to that exact message ID and sequence.
- Retries always reuse the original client message ID. After any disconnect, both message and receipt streams resume from the last locally durable contiguous sequence.
- A disconnected network cannot deliver instantly. The product must preserve the message locally, state the offline condition accurately, and converge automatically after connectivity returns.

## Message Timeline

- Message time and delivery information sit inside the bottom-right corner of each bubble. Text reserves inline space beside its last line for slightly lowered, light-gray metadata; only insufficient remaining width wraps this tail. Voice and file messages keep their compact footer; photos and videos use a small contrasting overlay, with failed-media retry kept in flow as a full touch target. Metadata uses secondary typography, readable contrast and consistent icon sizing; a pending clock occupies the same space as a sent/delivered check so short bubbles do not shrink when acknowledged. A decoded single-photo or video bubble, preview container and rendered thumbnail share the same geometry, so no larger letterboxed wrapper or active-state shrink exposes around it. Receipt updates preserve the bubble, decoded media, playback and text selection; the delivery meanings above remain unchanged.
- A centered, subdued date label appears above the first locally loaded chat message for each calendar date. Dates derive from the encrypted payload's `sentAt` in the viewing device's local timezone; labels include the year when it differs from the current year. Server sequence order remains unchanged, and clock skew does not create duplicate labels for a previously displayed date. Gallery-only uploads and reaction events create no date labels. Loading earlier history reuses and relocates the same date separator while preserving the message reading anchor; separators are not messages and never advance unread cursors.
- A downward control stays a fixed distance above the composer and fades in while the last message's lower edge lies below the control's upper edge, then fades out when that condition clears. Clicking loads any newer local history pages and scrolls naturally to the newest message without dismissing the keyboard. Short travel is slower in pixels per second; longer travel speeds up within a bounded duration. User scrolling, navigation and privacy cleanup cancel both the pending history read and animation; reduced motion uses immediate positioning. The newest row has enough bottom clearance to sit above the control threshold at rest, including after media finishes decoding.

## Local Files

- Both the chat attachment picker and gallery upload picker accept any local file format, including files whose MIME type the browser cannot identify. Files must be nonempty and no larger than 256 MiB each.
- A mixed chat selection preserves its order: consecutive images retain the existing album grouping, while each non-image becomes a separate file message. Videos use the existing file payload but display an inline preview and play control. Other file messages show the original name, size, download progress, and retry action. Both retain replies and reactions.
- Non-image gallery uploads use separate gallery-file entries and do not appear in either participant's chat or count as incoming chat notifications. Video entries appear in 相册; other entries appear in 文件. Gallery access and upload permissions remain creator-only. Every locally available chat attachment is also projected automatically into the creator's Safe without changing the chat message, server payload, peer view, or device-history boundary.
- File contents and metadata use the existing encrypted chunk transport, original-byte verification, and content-bound resumable upload. The entire original is authenticated and verified before any open or download action. Allowlisted inert document types such as PDF and plain text may then be handed to the browser/operating-system reader through a verified local object URL; they are not rendered by application code. Active, unsupported, or unknown formats remain download-only. Images and videos may be decoded locally for media display only after full verification. Video display introduces no new encrypted message kind and also applies to compatible existing file and gallery-file messages.
- All active devices must advertise `file-message-v1` before sending a file, gallery file, or reply referring to a file. The check also applies to queued-message retries; unsupported devices leave the encrypted item in the outbox until compatibility returns. Locked or detached file controls cannot start or complete a download. A bounded foreground chooser return may complete without relocking; a real background departure invalidates that chooser and requires a fresh selection after unlock, as specified below.

## Chat Images

- GIF, animated WebP and APNG originals retain their bytes and animation through the existing encrypted upload path in chat and Safe. Opening or paging to a supported animation plays it automatically. The viewer's 动态开启 / 动态关闭 control switches between the original animation and a temporary static frame; reopening resets playback to on. Single-frame images have no motion control. The original file is never replaced or transcoded for upload/download. Static frames are bounded to 8 million pixels and a 4096-pixel side, memory-only, and released on paging away, closing or privacy teardown. If the browser cannot prepare a still frame, the original remains viewable with an explicit unavailable-control status. Apple Live Photo import is excluded from this feature.
- Concealed media retains strong Gaussian blur to suppress recognizable contours. Safe gallery thumbnails use the existing 48 CSS pixel filter. Chat photos, album cells and video stills use a bounded, memory-only blurred PNG prepared from the fully verified local original or video poster, with the same 48px strength at the standard 288px chat width. It is never uploaded, persisted or substituted for the original.
- Concealed chat previews paint only one cover-fitted blurred bitmap, without a live CSS filter. The original foreground keeps its layout dimensions but is transparent until reveal. Cache eviction and privacy teardown revoke the bitmap URL; late preparation results cannot repopulate a locked runtime. Reveal gestures and original media remain unchanged.

- Pasting actual image files in the chat composer (Cmd/Ctrl+V or the native Paste action) uses the same original-byte encrypted upload path, grouping and capability gates. Image data takes precedence over accompanying text/HTML while preserving the current text draft; text-only paste stays native. Clipboard content is only read from the paste event. A busy upload asks the user to paste again; a covered, locked or detached input cannot start an upload.
- There is no nine-image limit on a user selection. Chat divides selected originals in order into messages containing at most nine images and at most 256 MiB of original bytes each. A one-image group uses an ordinary image message; each larger group uses one encrypted album payload, outbox item, server sequence, and chat bubble. Every original has its own encrypted, integrity-checked manifest. Albums require every active device to report `image-album-v1` through its authenticated current-version connection.
- Images in or near the visible chat viewport decrypt on the endpoint into strongly blurred thumbnails. This includes single photos, album cells and video still previews. The first tap reveals only the selected thumbnail; another tap opens its viewer. Once loaded, a single-photo or video bubble and its preview container fit the rendered media dimensions exactly, without a larger empty frame; albums use a compact, ordered collage. While concealed, the same verified local image supplies an equally strong cover-fitted blur behind the foreground, so the mask remains visually continuous without changing the revealed geometry.
- A downward drag on revealed chat media visibly displaces its bubble with progressive resistance. Releasing after a sufficient downward pull conceals all chat thumbnails and returns the bubble; a short pull returns without concealment. Dragging blank conversation space retains native scrolling and conceals only on release. A keyboard-dismiss gesture does not pull or conceal media; real gesture cancellation or privacy teardown clears the gesture immediately. Downward viewer dismissal also conceals chat thumbnails. Reveal state is held only in unlocked-session memory, survives ordinary message rerenders, and never reveals new arrivals automatically. The browser-failure privacy curtain synchronously clears it and closes the viewer, including a brief mobile blur followed by focus before the lock debounce ends. Locking and runtime teardown reset it.
- Chat, gallery, and viewer reuse verified plaintext media only within the unlocked runtime. Initial chat loading uses a quiet placeholder with visible download, decryption, and verified-preview stages plus determinate progress where available; tapping it starts or continues preparation but never marks unverified media as revealed. The verified thumbnail then replaces the placeholder in its default blurred state. Gallery tiles use a full-tile soft-glow skeleton until media decoding finishes and a static skeleton under reduced motion. Failures retain a visible retry action. The endpoint may persist the already encrypted server chunks so a later unlock can reconstruct and fully authenticate the original without downloading it again; corrupted or incomplete local ciphertext is discarded and fetched again. Locking still clears decrypted media, preparation status, previews and object URLs synchronously. Browser quota eviction may require another download.
- Tapping an already revealed chat image or album cell opens an overlay viewer at that exact item. The full-screen viewer uses the current light/dark page background with no blurred image fill. Each photo keeps its aspect ratio and fills the viewport width unless filling the viewport height is the limiting dimension, with no decorative inset around the media. A pinch may temporarily make a photo smaller, but releasing both fingers springs any sub-1× result back to the original fitted size; an enlargement up to 5× remains in place for inspection, with resistant overscale before settling to 5×. One-finger panning, double-tap/double-click reset/zoom and bounded wheel zoom remain available. At normal scale, vertical dragging uses edge resistance and progressively shrinks the photo to as little as one half of its fitted size at the viewport edge before dismissing it. Horizontal paging follows the finger with resistance and settles through a 380 ms transition between two mounted media layers without an intermediate centered frame, while the title/header stays mounted and does not blink. Paging to a video creates it paused by default and gives it the same full-stage container as a photo; video controls do not consume the surrounding horizontal pager, so the next image remains reachable. Leaving a video pauses it and removes its source. Previous/next controls, a position counter, current-original download, focus return, and reduced-motion behavior remain available. Image gestures cannot zoom or move the surrounding page.

## Video Attachments

- Videos in or near the chat viewport show a locally generated still preview and a play control, like photo previews. Inline previews start blurred and do not play automatically. The first tap reveals the still; tapping it again requests the system video player directly for an already verified cached original, preferring Safari's video fullscreen API and otherwise the standard video fullscreen API. A successful native request does not first show a custom player and Done/Escape returns to the originating page. Missing capability, rejected native entry or an original that still needs verification uses browser-native playback controls in the page viewer. Playback rejection leaves an explicit retry control; undecodable media retains the verified original download. Native video zoom gestures belong to the system player and vary by browser; the page cannot guarantee native fullscreen, automatic playback or a particular system zoom gesture.
- The endpoint first downloads, decrypts, and verifies the complete original length and SHA-256 digest, then uses the browser video decoder to generate a JPEG preview from a frame near the start in memory. This derived preview is never uploaded or persisted and does not resize, transcode, or replace the encrypted original. The verified original remains available for download if the browser cannot decode the video or generate a preview.
- Chat, 相册, and the viewer reuse verified videos and local previews within the unlocked session. Closing the viewer, changing items, locking, or privacy teardown stops playback and removes the player's source. Locking and runtime teardown cancel pending preview work, clear decrypted media and preview caches, and revoke their object URLs.

## Real-time Calls

- One active two-person WebRTC call per room, with encrypted/signed signaling and direct or TURN-relayed encrypted media. Calls use the existing verified device identities and MLS membership; legacy rooms cannot call.
- Video and audio call actions sit next to each other on the left of the chat header. The fullscreen FaceTime-style view uses remote video, an upper-right local preview, translucent bottom controls and green answer/red decline or end actions. Microphone, camera and camera-switch controls operate actual media; unavailable browser capabilities are not simulated.
- Incoming calls do not capture until accepted. The first authorized peer device to answer wins; an explicit decline ends ringing. Audio can become video during the same call. Weak networks reduce video quality and may fall back to audio.
- Calls are foreground-only and leave no recording or call history. Privacy concealment, locking, membership revocation and runtime teardown synchronously stop all tracks; a late permission grant cannot restart a discarded call. Mobile foreground calls suspend the ordinary ten-minute idle timer; desktop's independent thirty-minute real-inactivity deadline remains in force.
- TURN configuration is optional and uses short-lived credentials. The app does not promise universal NAT traversal without a tested relay, native system-call integration, background ringing or screenshot protection. Implementation and deployment boundaries are documented in `CALLS.md`.

## Voice Messages

- The empty text composer exposes a microphone action. Holding it smoothly enlarges the microphone from the trigger into a floating circle that follows only horizontal finger movement across a longer, progressively resistant travel. Entering any voice-recording state hides the unavailable text-input surface; an active reply context may remain visible without its text field. Before the cancel threshold, the circle stays blue and the visible status says “松手发送，左滑取消录制”. Sliding left by 220 CSS pixels arms cancellation without ending capture; the circle turns red and the status says “松手取消录制”. Sliding back restores the send state, and only release commits the currently displayed outcome. A cancel release discards audio capture and the draft before the empty controls retire toward the right; a send release stops and sends a valid recording. Automatic processing and upload show only compact progress, without briefly exposing paused-draft delete, waveform or send controls. An error restores the retryable draft. Pointer interaction does not leave a blue focus ring on the original microphone; keyboard focus remains visible. Vertical movement does not lock or move the circle. A short tap or keyboard activation starts hands-free recording. The hands-free state has a large send arrow, a cancel action, and a separate pause button above it. Pause replaces the recording bar with a compact waveform preview, delete and send controls, and a microphone to continue. All states stay inline. Pause releases microphone access; continuing requests it again and combines a new local segment into the same message. A cancelled/interrupted pointer or an ordinary release while permission is pending cancels the hold; reaching the duration limit or losing the microphone always requires review rather than automatic send.
- Voice is limited to 0.5 seconds–5 minutes and 16 MiB. Browser recording segments are converted only on-device into portable 24 kHz mono PCM WAV. Reaching the limit pauses for review and never sends automatically. Real audio amplitudes produce the waveform.
- Audio bytes, metadata, duration, waveform, and reply references use the existing encrypted attachment and message pipeline. Playback begins only after authenticated decryption and full length/digest verification. Voice never enters the creator's image gallery.
- Only one voice message can load or play at a time. Playback controls include play/pause, duration, an accessible waveform seek slider, and explicit loading/error/retry states. Messages are retained like ordinary chat; automatic transcription, automatic expiry, raise-to-listen, and background recording are outside this version.
- All active devices must confirm `voice-message-v1` before sending a voice message or a reply referencing voice. This gate does not claim that capabilities are end-to-end authenticated.
- Unsent voice drafts and upload retry plans are memory-only. Failed sends preserve a frozen draft for same-session retry. Navigating away, locking, hiding, or backgrounding stops microphone/playback and clears unsent drafts; only completed encrypted-outbox commits receive normal durable retry semantics.
- A microphone permission request times out after 30 seconds. Its own visible foreground prompt uses the bounded native handoff below; a real background departure still locks immediately. Late permission grants must immediately stop their tracks and never revive a locked or cancelled recorder.

Viewport panning only repositions controls and does not change document padding or trigger bottom-follow. Safari’s browser-owned keyboard accessory toolbar cannot be forcibly removed by page code.

Initial intermediate mounts stay concealed, and returning from a suspended surface restarts the stability clocks from the first resumed sample. Native viewport events outside settled focused typing are coalesced into one animation-frame snapshot. On touch iOS WebKit, the chat header uses fixed positioning outside document-flow and sticky-container bounds, including bottom overscroll. ## Chat-page Presence

- Green online dots in the chat header breathe over 2.4 seconds with moderate dim/bright contrast, scale change and a soft green halo at the bright peak; offline/unknown states stay still, and reduced motion disables the animation. Header actions use the composer's neutral icon colors, including its disabled-state color without dimming the entire glass control.
- “Online” means that at least one active device for that participant is currently on the chat page. Presence is aggregated by participant role across devices: one role remains online while any of its active sockets reports `chat`; gallery, image viewer, and device-management surfaces report `away`.
- The centered status capsule combines “我” and its status icon before “对方” and its status icon on the first line. The second line shows the peer’s “在线” state or time since last online. The capsule has the same 44px height as the action buttons and a bounded width that preserves spacing between the two right-hand actions. Self presence remains accessible by its label and status icon without a separate left-hand control. The last-online timestamp stays in server memory and is unavailable after a server restart.
- Chat-page presence is independent from transport connectivity. Moving to another product surface updates presence without closing or reconnecting the WebSocket, while reconnect replays the desired surface state. Socket close, device removal, and ping/pong timeout provide stale-session cleanup.
- Each user-visible release has one repository-owned release ID and a concise ordered change list. When an already open older client learns that the new Service Worker has activated, chat shows a pinned “有新版本待更新” notice that slides and fades down from the top; its Update button reloads the page. After the updated client loads, its change list opens only on the first subsequent entry to chat and remains pending across cover-only reloads until that entry. A fresh installation is not presented as an update. Release tracking stores only local release IDs and never changes room, message, device-history, or server metadata.
- Presence is ephemeral server-memory behavioral metadata and is broadcast as a role-level snapshot. It is not persisted as conversation history, is not protected or authenticated by the end-to-end message protocol, and must never be presented as proof of identity, attention, physical presence, or cryptographic safety.

## Multi-device and Reply

- Every physical device has an independent identity key pair, MLS leaf/key package, local vault, passkey binding, and server access token. Private identity keys and existing MLS state are never copied through an add-device link.
- An existing same-participant device creates a ten-minute link. Participant invitations and device links use distinct, strictly validated URL-fragment discriminators and exact payload schemas; pasting or opening a newly generated device link always enters the device flow, including after a prior device was added. Reusing a claimed/expired device link reports that device-link state instead of the sealed participant-invite error. The claimant and authorizer must display the same six-digit safety code before the authorizer signs the MLS Add commit. A device is not active before that approval.
- The activation sequence is a hard history boundary: the new device starts from the Add welcome state, the service omits earlier messages and receipts, and application ciphertext from any prior MLS epoch is rejected. Pending stale-epoch messages are re-encrypted after the client processes the membership update.
- Device management lists both participants' active devices, allows removal only within the current participant's device set, prevents removal of the last device for a participant, and caps each participant at three active devices.
- A 500 ms long press anywhere on the source bubble—including every part of a voice bubble—highlights it above a slowly fading dim/blur backdrop and opens a six-emoji reaction bar with a compact vertical copy/select/reply/delete menu. Menus use a 320 ms anchor-origin scale/fade in and the same reversed close timing. The synthesized click after a voice hold is consumed so playback does not start beneath the action menu. Delete text and icon are red; its submenu receives no preselected/active option styling. A confirmed message from the same participant offers “为所有人删除” and “仅为我删除”; incoming messages and pending/failed outgoing messages offer only the local choice. Selecting text activates native selection directly in the original bubble; there is no separate copy sheet. The browser controls native handles and edit-toolbar presentation. Supported devices receive brief vibration feedback. Desktop right-click and keyboard shortcuts open the same menu; hovering a message does not show a separate reply button.
- Each participant can add, replace, or remove one reaction per confirmed chat message. The emoji, removal, and exact target stay inside encrypted message history and the durable outbox; reactions project into corner badges and never become chat rows. Inserting or removing a badge moves later bubbles through a smooth positional transition. All active devices must advertise `message-reactions-v1`. Target validation and local history boundaries also apply after reopening.
- Dragging a confirmed bubble left follows a smooth bounded resistance curve and never moves it farther than one sixth of the current visible viewport width. Releasing after the threshold (or a deliberate fast flick) activates Reply, restores/focuses the composer and keyboard, and settles the bubble back; vertical scrolling and short horizontal exploration do not activate it. A clearly horizontal swipe retains ownership even when the keyboard is already open. The draft quote and text field share one outlined input stack, and quote content is limited to one ellipsized line with a close action. Reply references use a compact local preview with a leading vertical line and no nested background card. The reference and generic kind label stay inside the encrypted message payload; content previews are derived only from this device's encrypted history. If the original is outside this device's local history boundary, the quote reports that the historical message is unavailable and does not copy pre-join content into the new reply.
- “仅为我删除” is an encrypted device-local projection and leaves the durable outbox/history untouched; failure to save restores the row. “为所有人删除” is a capability-gated encrypted `message-delete` event authorized only for a confirmed target belonging to the same authenticated participant role. Valid tombstones suppress the target from chat and Safe, survive pagination/reopen and gallery-only recovery, and make old reply/reaction actions unavailable. This is logical recall, not physical erasure of ciphertext, previous exports, system copies, offline devices, or backup material already obtained.

## Local Unlock and Privacy Curtain

- New vaults use a random 256-bit master key wrapped by a key derived from a WebAuthn PRF-capable passkey. Setup and unlock use the operating system's biometric or device-password user verification; entering the version-3 unlock gateway automatically starts verification, with manual retry after cancellation or failure.
- Both single-device and syncable passkeys are accepted. Backup eligibility is recorded at registration and verified on later assertions; it informs the security properties of the credential but does not make a valid credential fail setup.
- Legacy password vaults migrate to passkey-only version 3 after one successful password unlock. Existing version-2 gesture vaults require the old gesture once because it is part of the old key derivation, then are immediately rewrapped as passkey-only version 3.
- A browser-load-failure cover retains an enlarged blank bottom-right one-second long-press entry. The hold keeps its restrained progress cue; completion directly enters the gateway and starts passkey verification as soon as real document focus is present, without a decorative ring, fireworks or another button click. Because Safari may update `document.hasFocus()` without a `focus` event after foreground return, the gateway also observes a short silent-focus edge while retaining the normal lifecycle-bound focus listener. It never calls WebAuthn while unfocused. User-cancelled WebAuthn returns a “重新验证” action without a red error sentence. Pointer capture tolerates small slips, and repeated returns to the cover—including after foreground restoration—must leave its entry operable. Ordinary desktop browsers also accept holding unmodified F for two seconds while the cover is visible and focused; completing that trusted hold likewise starts gateway verification directly, while release before completion, blur, hiding, or composition cancels it. Neither entry substitutes for authentication, and browser-owned passkey UI still cannot be forced to appear.
- Each version-3 gateway unlock owns one native passkey request. Runtime teardown, including lock, pagehide, freeze and the existing 65-second verification bound, aborts that request as well as rejecting its late result. If the native result arrives while Safari still reports the visible document as unfocused, the gateway stays obscured and waits up to 1.5 seconds for real focus before continuing; it never accepts the result while unfocused. Waiting does not launch automatic parallel retries. Browser/OS-owned passkey confirmation and biometric selection remain system-controlled: the page requires user verification but cannot guarantee skipping “使用通行密钥” or forcing Face ID over device passcode.
- The touch cover entry preserves the browser's default focus path. If Safari returns visible but unfocused, the version-3 gateway requests focus on its existing unlock button and keeps that button enabled until real document focus is available. Focus return starts the live entry once; a manual button click remains a fallback. No native request or busy state starts while unfocused, and hidden visibility, pagehide, freeze, explicit lock or gateway replacement discard the waiting intent. This governs when verification starts; a completed result remains separately gated on the visible, focused return rule above.
- On ordinary desktop-browser blur or hidden visibility, conceal immediately, tear down rendered history, media, transfers and sockets, and retain the unlocked vault session only in page memory. A completed cover gesture can resume within 30 minutes of the last active in-app interaction. Cover input and foreground return do not renew the deadline. Check both wall-clock and monotonic deadlines before accepting activity or restoring a session, including after background timer suspension. Resume revalidates and decrypts the durable vault snapshot with the retained key; a changed/deleted vault requires normal authentication. No new key or plaintext persistence is introduced.
- Mobile/tablet browsers and installed PWAs retain strict locking: hidden visibility locks immediately, ordinary blur has a 250 ms teardown debounce, and idle timeout remains 10 minutes, suspended only during an active foreground call. Desktop calls keep the 30-minute inactivity deadline; remote call updates never renew it. UA/platform classification excludes mobile devices (including iPad desktop mode) and installed display modes; screen width or a keyboard alone never enables desktop retention.
- On all clients, unowned native-surface focus loss, export/clipboard/confirmation focus loss, pagehide, freeze, persisted pageshow, explicit lock and idle expiry discard any retained session. Gateway WebAuthn retains its bounded exception. Safari may briefly transfer window focus to its native keyboard after a direct, trusted primary pointer activation on the visible unlocked chat textarea. Only that activation may own one visible blur for at most 1.2 seconds. Fresh post-tap keyboard-opening geometry and the first owned visible blur may arrive in either order and jointly settle the handoff; window-focus return can clear it independently, while geometry evidence alone does not discard ownership before a possible blur. Programmatic focus, an already-open keyboard, a second blur, timeout after consumption, hidden visibility, navigation/lifecycle signals, idle expiry, session or textarea replacement, and leaving chat never inherit the exception. Because browsers do not expose a trustworthy blur reason, a real visible-window departure immediately after that tap can remain uncovered until the 1.2-second deadline unless a hard lifecycle signal arrives; this is a bounded foreground-usability tradeoff, not authentication. Foreground return after any ordinary departure still shows the cover until a deliberate entry gesture. A permanently mounted opaque curtain conceals synchronously before ordinary teardown; the page cannot invalidate thumbnails already cached by the browser or operating system.
- `ERR_CONNECTION_CLOSED` is followed by the device's unread incoming-chat count in the same monospace style with slightly stronger color. A restricted observer token can fetch only this number while the vault is locked. The server stores its hash, a monotonic per-device read cursor, and a countable-message flag; own-role messages, gallery uploads, and reactions do not count. Visible chat messages advance the read cursor. Foreground/online return refreshes the count, with 15-second polling while visible; offline cover keeps the last confirmed count. This is behavioral metadata, separate from cryptographic delivery receipts.
- A user-opened file chooser (up to five minutes) or microphone/camera permission request (up to thirty seconds) may own one visible window-focus loss while the app remains in the foreground. It does not exempt hidden visibility, pagehide, freeze, explicit lock or idle expiry. For image/gallery choosers, focus return consumes ownership; if no `change`/`cancel` arrives within the short return edge, the detached input is removed. Another departure, a real background transition, lifecycle teardown, or loss of owner invalidates the selection; late events are ignored and the user must choose again after unlock. A result arriving before focus gets at most 250 ms to return; uploads wait for a visible focused document and the original room/device. Browsers cannot reliably identify why a visible window lost focus or force an operating-system-owned picker/tooltip to close; removing the DOM input is a best-effort privacy cleanup, not a guarantee about native UI. Microphone/camera prompts retain their existing bounded handoff semantics.
- Only gateway passkey prompts may suppress their own hidden events before a conversation or socket opens, including recovery and migration gateways. If WebAuthn settles while the visible document is still unfocused, the opaque curtain remains and the gateway requires a real focus return within 1.5 seconds before consuming the result. Hidden settlement still locks immediately. The exception ends after that return edge or the outer 65-second bound and never overrides `pagehide`, explicit lock, or idle timeout.

## Recovery Setup

- Unlocked, online MLS devices automatically back up their recovery checkpoint and local history as ciphertext. Backup status, retry, local recovery-code viewing and optional history restore live in “备份与恢复”; manual recovery-file import/export controls are removed.
- A reminder can be dismissed through an encrypted local preference. It directs users to save their QR3 code separately; only the current device stores that code, encrypted in its vault. Viewing it requires fresh passkey verification and closes the active conversation first. The code screen locks after one minute or privacy teardown.
- A QR3 code locates the corresponding server backup and decrypts it locally. The server and administrator never receive the code or decryption keys. Forgotten code plus lost devices has no administrator bypass.
- MLS recovery proves the original identity but creates a fresh device, token and leaf. Another trusted active device must be online; all active devices need protocol support. Pending recovery fences the original for at most 15 minutes; success permanently revokes it.
- After replacement, rotate the code immediately. Persist the exact new encrypted wrapper and all retained archive keys locally before upload. Atomically retire the old online entry only when the new wrapper and archive transfer are stored. Failed or ambiguous uploads retry the same request; expose the new code as active only after confirmation.
- Recovery opens at a new message/receipt boundary without loading old history or reusing an old sending ratchet. Users explicitly request historical chat or creator gallery restore and enter the current new code again. Gallery-only restore must not create old chat bubbles or reply previews. Normal linked devices receive no archive secrets.
- Historical attachments still depend on retained original ciphertext and download only when viewed/saved. Codes and copied old backups can still decrypt offline after rotation; no remote destruction is promised. Foreground-only backups can lag the latest message.
- Old QR2 files require migration from a still-usable original device or trusted legacy recovery flow before switching to QR3. The current UI has no legacy file-import entry. See [RECOVERY_BACKUPS.md](./RECOVERY_BACKUPS.md) for migration limits, scope separation and failure behavior.
- Full local history remains available through bounded paging. Room-based administration on `sao.shui.click` uses a strong administrator password plus TOTP and exposes metadata only. Clearing a whole room requires fresh factors and exact room-ID confirmation; administrator credentials never recover user content.

## Interface continuity

- Ordinary forward/back navigation keeps both painted pages mounted during a 380 ms push/pop transition, so the incoming page enters from the navigation edge while the outgoing page moves only partway and no white frame appears. Fixed controls move with their page instead of independently jumping. Button feedback starts immediately without shrinking file/media cards. Privacy concealment, locking and media teardown remain immediate; pending animation cannot reveal a locked session. Reduced-motion settings bypass decorative motion.
- The standard passkey unlock page contains only its bottom-aligned unlock button. Verification failures add an accessible retry error above that button; legacy migration and recovery retain their necessary inputs and explanations.
- The local-safety menu contains device management and backup/recovery; the persistent security-code item, background-notification shortcut and immediate-lock shortcut are absent. Six-digit safety-code comparison remains mandatory inside the separate new-device approval flow. Opening and closing local menus use equal 320 ms anchor-origin opacity/scale transitions. Existing privacy/idle locking and notification delivery are unaffected.
- The backup overview uses compact spacing to fit a typical phone screen. Smaller viewports, increased text size and the expanded history-restore form can scroll; controls and recovery boundaries remain available.
- Incidental long press on non-editable page surfaces suppresses native selection and context menus. Message long press opens the application menu. Text entry and explicitly choosing “选择文字” retain platform editing support; native input loupe/edit controls are browser-owned and cannot be universally disabled without impairing editing.
- Microphone and camera permission is requested only for the operation using it. The page cannot grant permission or force persistence; users may select Allow in the browser's settings for the exact site. Idle capture is never retained to avoid future prompts.

Target WCAG 2.2 AA for the unlocked experience. Support keyboard navigation, visible focus, screen-reader labels, sufficient contrast, touch targets of at least 44 by 44 CSS pixels, reduced-motion preferences, clear non-color-only status communication, and resilient layouts from small mobile screens through desktop browsers.
