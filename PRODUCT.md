# Product

## Register

product

## Users

Two trusted people use the product from mobile or desktop browsers and installed PWAs. Each person may authorize up to three independently keyed devices. They need a quiet private channel for exchanging text and original-quality images without creating accounts. They expect the interface to stay concealed until intentionally unlocked, and they accept that losing both the usable local vault and recovery code makes history unrecoverable.

## Product Purpose

Provide a small, dependable one-to-one encrypted chat whose cloud service can order, relay, and retain ciphertext but cannot read message or image contents. Success means all authorized devices exchange new messages in a deterministic order, reconnect without gaps or duplicates, review only their locally available history and images, and verify that downloaded image bytes match the original upload.

## Brand Personality

Quiet, private, dependable. The product should feel composed and discreet, with clear system feedback and no security theater in its unlocked interface.

## Anti-references

Do not resemble a neon cyber-security dashboard, hacker terminal, crypto trading product, social feed, or decorative glassmorphism showcase. Avoid theatrical lock imagery, fear-based copy, excessive cards, gratuitous animation, and unfamiliar controls where platform conventions work better.

## Design Principles

1. Privacy is structural: sensitive content and keys stay on the endpoint, while visual concealment is treated only as a privacy curtain.
2. Calm before cleverness: standard controls, concise copy, and restrained feedback keep attention on the conversation.
3. Make system truth visible: pending, delivered, disconnected, locked, failed, and recovery states must be unambiguous.
4. Preserve originals: uploaded image bytes remain unchanged through encryption, storage, download, and decryption.
5. Fail closed: authentication, decryption, integrity, version, and sequence errors never silently downgrade or display partial content.

## Delivery Semantics

- **等待发送** (accessible description: 等待服务器): the payload is durably encrypted in the local outbox but has not yet been observed in the server sequence.
- **单柄对勾 / 已发送** (accessible description: 服务器已保存): the signed ciphertext has a committed server sequence and can be recovered by reconnect synchronization.
- **双柄对勾 / 已送达** (accessible description: 对端已安全接收): at least one active device owned by the other participant verified, decrypted, and durably stored the message, then signed a receipt bound to that exact message ID and sequence.
- Retries always reuse the original client message ID. After any disconnect, both message and receipt streams resume from the last locally durable contiguous sequence.
- A disconnected network cannot deliver instantly. The product must preserve the message locally, state the offline condition accurately, and converge automatically after connectivity returns.

## Local Files

- Chat and Safe file cards open an in-app reader for PDF, EPUB, plain text, JSON, Markdown and CSV. The full original is authenticated and verified before any document parsing or display. PDF uses locally bundled PDF.js; text formats display literal text, including Markdown markup. The reader follows the existing liquid-glass controls and system theme, with a clear document stage, rounded search focus, page navigation, zoom and fit-width. PDF supports horizontal swipe paging when the page fits the viewport; enlarged pages retain horizontal panning. Vertical scrolling, short movements and multitouch do not turn pages. Search visits matching PDF pages; scanned pages without a text layer are not OCR-searchable. Text search highlights the next occurrence. Favorites retains its existing no-reader/no-export file behavior.
- EPUB 2/3 uses bundled epub.js package/navigation parsing, zip.js extraction in a dedicated worker and DOMPurify chapter cleaning. Chapters reflow in the app theme with a chapter directory, previous/next navigation, adjustable text size and search across chapters. Internal chapter links and packaged PNG/JPEG/GIF/WebP images are supported. Publisher CSS, fonts, scripts, forms, embedded frames, SVG and external resources are not loaded; fixed-layout fidelity, DRM and encrypted/obfuscated resources are not supported. EPUB files reported as ZIP are eligible only with an .epub extension and valid EPUB structure.
- Chat, Safe and Favorites use the same format-specific file icons, with distinct glyph families, colors and PDF/EPUB/DOCX/XLSX/PPTX/etc. labels. The icon is presentation only and does not grant a file reader eligibility.
- Reader limits are 64 MiB / 2,000 pages for PDF and 4 MiB / 2,000,000 decoded characters for text. Unsupported, damaged, password-protected or over-limit documents show a local error without automatic download or external handoff. Closing during transfer cancels the pending read. Closing, navigation, privacy concealment and lock discard text, canvases and worker state; late work cannot reopen the reader. Reading uses the away surface and does not advance visible chat read state. No native-reader blur exemption is acquired.
- EPUB limits are 32 MiB compressed, 1,000 ZIP entries, 128 MiB total declared extraction, 16 MiB per entry, 2 MiB per XML/chapter and 8 MiB per image (24 MiB image bytes per visible chapter). Actual streamed extraction is also bounded. Only the current chapter's image URLs are retained and are revoked on replacement, error or close.

- Both the chat attachment picker and gallery upload picker accept any local file format, including files whose MIME type the browser cannot identify. Files must be nonempty and no larger than 256 MiB each.
- A mixed chat selection preserves its order: consecutive images retain the existing album grouping, while each non-image becomes a separate file message. Videos use the existing file payload but display an inline preview and play control. Other file messages show the original name, size, download progress, and retry action. Both retain replies and reactions.
- Non-image gallery uploads use separate gallery-file entries and do not appear in either participant's chat or count as incoming chat notifications. Video entries appear in 相册; other entries appear in 文件. Gallery access and upload permissions remain creator-only. Every locally available ordinary chat attachment (expressions excluded) is also projected automatically into the creator's Safe without changing the chat message, server payload, peer view, or device-history boundary.
- File contents and metadata use the existing encrypted chunk transport, original-byte verification, and content-bound resumable upload. The entire original is authenticated and verified before any parsing, display or download action. Allowlisted documents use the bounded local reader above. Active, unsupported, or unknown formats remain download-only. Images and videos may be decoded locally for media display only after full verification. Video display introduces no new encrypted message kind and also applies to compatible existing file and gallery-file messages.
- All active devices must advertise `file-message-v1` before sending a file, gallery file, or reply referring to a file. The check also applies to queued-message retries; unsupported devices leave the encrypted item in the outbox until compatibility returns. Locked or detached file controls cannot start or complete a download. A bounded foreground chooser return may complete without relocking; a real background departure invalidates that chooser and requires a fresh selection after unlock, as specified below.

## Chat Images

- GIF, animated WebP and APNG originals retain their bytes and animation through the existing encrypted upload path in chat and Safe. Opening or paging to a supported animation plays it automatically. The viewer's 动态开启 / 动态关闭 control switches between the original animation and a temporary static frame; reopening resets playback to on. Single-frame images have no motion control. The original file is never replaced or transcoded for upload/download. Static frames are bounded to 8 million pixels and a 4096-pixel side, memory-only, and released on paging away, closing or privacy teardown. If the browser cannot prepare a still frame, the original remains viewable with an explicit unavailable-control status. Apple Live Photo import is excluded from this feature.
- Concealed media retains strong Gaussian blur to suppress recognizable contours. Safe gallery thumbnails use the existing 48 CSS pixel filter. Chat photos, album cells and video stills use a bounded, memory-only blurred PNG prepared from the fully verified local original or video poster, with the same 48px strength at the standard 288px chat width. It is never uploaded, persisted or substituted for the original.
- Concealed chat previews paint only one cover-fitted blurred bitmap, without a live CSS filter. The original foreground keeps its layout dimensions but is transparent until reveal. Cache eviction and privacy teardown revoke the bitmap URL; late preparation results cannot repopulate a locked runtime. Reveal gestures and original media remain unchanged.

- Pasting actual image files in the chat composer (Cmd/Ctrl+V or the native Paste action) uses the same original-byte encrypted upload path, grouping and capability gates. Image data takes precedence over accompanying text/HTML while preserving the current text draft; text-only paste stays native. Clipboard content is only read from the paste event. A busy upload asks the user to paste again; a covered, locked or detached input cannot start an upload.
- There is no nine-image limit on a user selection. Chat divides selected originals in order into messages containing at most nine images and at most 256 MiB of original bytes each. A one-image group uses an ordinary image message; each larger group uses one encrypted album payload, outbox item, server sequence, and chat bubble. Every original has its own encrypted, integrity-checked manifest. Albums require every active device to report `image-album-v1` through its authenticated current-version connection.
- Ordinary images in or near the visible chat viewport decrypt on the endpoint into strongly blurred thumbnails. Expression messages instead start revealed, render at two-thirds of the previous image dimensions without a background or border, and remain explicitly concealable by dragging. This includes single photos, album cells and video still previews. The first tap reveals only the selected thumbnail; another tap opens its viewer. Once loaded, a single-photo or video bubble and its preview container fit the rendered media dimensions exactly, without a larger empty frame; albums use a compact, ordered collage. While concealed, the same verified local image supplies an equally strong cover-fitted blur behind the foreground, so the mask remains visually continuous without changing the revealed geometry.
- A downward drag on revealed chat media visibly displaces its bubble with progressive resistance. Releasing after a sufficient downward pull conceals all chat thumbnails and returns the bubble; a short pull returns without concealment. Dragging blank conversation space retains native scrolling and conceals only on release. A keyboard-dismiss gesture does not pull or conceal media; real gesture cancellation or privacy teardown clears the gesture immediately. Downward viewer dismissal also conceals chat thumbnails. Reveal state is held only in unlocked-session memory, survives ordinary message rerenders, and never reveals new ordinary-media arrivals automatically; expressions default to revealed. The browser-failure privacy curtain synchronously clears it and closes the viewer, including a brief mobile blur followed by focus before the lock debounce ends. Locking and runtime teardown reset it.
- Chat, gallery, and viewer reuse verified plaintext media only within the unlocked runtime. Initial chat loading uses a quiet placeholder with visible download, decryption, and verified-preview stages plus determinate progress where available; tapping it starts or continues preparation but never marks unverified media as revealed. The verified thumbnail then replaces the placeholder, blurred for ordinary media and revealed for expressions. Gallery tiles use a full-tile soft-glow skeleton until media decoding finishes and a static skeleton under reduced motion. Failures retain a visible retry action. The endpoint may persist the already encrypted server chunks so a later unlock can reconstruct and fully authenticate the original without downloading it again; corrupted or incomplete local ciphertext is discarded and fetched again. Locking still clears decrypted media, preparation status, previews and object URLs synchronously. Browser quota eviction may require another download.
- Tapping an already revealed chat photo, album cell or video opens at that exact item in the ordered, locally loaded chat media list. Paging crosses message boundaries and excludes expressions, ordinary files, gallery-only uploads and unavailable messages; identical originals in different messages retain distinct item identities. The full-screen viewer uses the current light/dark page background with no blurred image fill. Each photo keeps its aspect ratio and fills the viewport width unless filling the viewport height is the limiting dimension, with no decorative inset around the media. A pinch may temporarily make a photo smaller, but releasing both fingers springs any sub-1× result back to the original fitted size; an enlargement up to 5× remains in place for inspection, with resistant overscale before settling to 5×. One-finger panning, double-tap/double-click reset/zoom and bounded wheel zoom remain available. At normal scale, vertical dragging uses edge resistance and progressively shrinks the photo to as little as one half of its fitted size at the viewport edge before dismissing it. Horizontal paging follows the finger with resistance and settles through a 380 ms transition between two mounted media layers without an intermediate centered frame, while the title/header stays mounted and does not blink. Paging to a video from chat, Safe or favorites immediately requests the system video player and playback, without first animating into the custom video page. Neighboring originals may be prefetched and fully verified to retain the next gesture's native activation. If the browser refuses native entry, its playback controls remain available and the next horizontal page remains reachable. Leaving a video pauses it and removes its source. Previous/next controls, a position counter, focus return, and reduced-motion behavior remain available. Chat media viewers do not offer downloads. Image gestures cannot zoom or move the surrounding page.

## Video Attachments

- Videos in or near the chat viewport show a locally generated still preview and a play control, like photo previews. Inline previews start blurred and do not play automatically. The first tap reveals the still; tapping it again requests the system video player directly for an already verified cached original, preferring Safari's video fullscreen API and otherwise the standard video fullscreen API. A successful native request does not first show a custom player and Done/Escape returns to the originating page. Uncached originals must finish verification before the native request; the browser may require another play tap if activation has expired. Missing capability or rejected native entry uses browser-native playback controls in the page viewer. Playback rejection leaves an explicit retry control; undecodable media shows a playback error without a viewer download action. Native video zoom gestures belong to the system player and vary by browser; the page cannot guarantee native fullscreen, automatic playback or a particular system zoom gesture.
- The endpoint first downloads, decrypts, and verifies the complete original length and SHA-256 digest, then uses the browser video decoder to generate a JPEG preview from a frame near the start in memory. This derived preview is never uploaded or persisted and does not resize, transcode, or replace the encrypted original. A missing poster does not prevent trying the verified original in the system player; a decoder failure does not introduce a download action in the viewer.
- Chat, 相册, and the viewer reuse verified videos and local previews within the unlocked session. Closing the viewer, changing items, locking, or privacy teardown stops playback and removes the player's source. Locking and runtime teardown cancel pending preview work, clear decrypted media and preview caches, and revoke their object URLs.

## Real-time Calls

- One active two-person WebRTC call per room, with encrypted/signed signaling and direct or TURN-relayed encrypted media. Calls use the existing verified device identities and MLS membership; legacy rooms cannot call.
- Video and audio call actions live in the composer's plus panel. The fullscreen FaceTime-style view uses remote video, an upper-right local preview, translucent bottom controls and green answer/red decline or end actions. Microphone, camera and camera-switch controls operate actual media; unavailable browser capabilities are not simulated.
- Incoming calls do not capture until accepted. The first authorized peer device to answer wins; an explicit decline ends ringing. Audio can become video during the same call. Weak networks reduce video quality and may fall back to audio.
- Calls are foreground-only and leave no recording or call history. Privacy concealment, locking, membership revocation and runtime teardown synchronously stop all tracks; a late permission grant cannot restart a discarded call. Mobile foreground calls suspend the ordinary ten-minute idle timer; desktop's independent thirty-minute real-inactivity deadline remains in force.
- TURN configuration is optional and uses short-lived credentials. The app does not promise universal NAT traversal without a tested relay, native system-call integration, background ringing or screenshot protection. Implementation and deployment boundaries are documented in `CALLS.md`.

## Voice Messages

- Holding the empty textarea for 350 ms starts recording; a short tap focuses normal typing, and a nonempty draft retains native text editing. There is no microphone button. Recording dims the page and shows a blue waveform card above a large blue breathing holding area. Reduced motion disables the breathing animation; empty-input recording gestures suppress native touch selection while nonempty drafts retain native editing. A closed curved cancel band sits above that area, uses matching curvature and fully rounded ends, and stays clear of both screen edges. Hit testing follows the visible curved path: entering it turns the card/band red and changes the status to 松手取消录制; moving out restores blue and 松手发送. Release sends a valid recording or cancels according to the final position. No transcription region exists. Pointer interruption, foreground loss or release while permission is pending cancels the hold; late permission results cannot restart it. A recording shorter than 0.5 seconds is discarded with feedback.
- Automatic processing and upload show compact progress. A send error restores a retryable memory-only draft; reaching the duration limit or losing the microphone requires review, never automatic sending. Keyboard-only users may activate Alt+R on the empty input to use the existing hands-free pause/review/send controls. Pause releases microphone access and continuation requests a new local segment. These recovery/accessibility controls do not add an idle microphone or text-send entry.
- Voice is limited to 0.5 seconds–5 minutes and 16 MiB. Browser recording segments are converted only on-device into portable 24 kHz mono PCM WAV. Reaching the limit pauses for review and never sends automatically. Real audio amplitudes produce the waveform.
- Audio bytes, metadata, duration, waveform, and reply references use the existing encrypted attachment and message pipeline. Playback begins only after authenticated decryption and full length/digest verification. Voice never enters the creator's image gallery.
- Only one voice message can load or play at a time. Playback controls include play/pause, duration, an accessible waveform seek slider, and explicit loading/error/retry states. Messages are retained like ordinary chat; automatic transcription, automatic expiry, raise-to-listen, and background recording are outside this version.
- All active devices must confirm `voice-message-v1` before sending a voice message or a reply referencing voice. This gate does not claim that capabilities are end-to-end authenticated.
- Unsent voice drafts and upload retry plans are memory-only. Failed sends preserve a frozen draft for same-session retry. Navigating away, locking, hiding, or backgrounding stops microphone/playback and clears unsent drafts; only completed encrypted-outbox commits receive normal durable retry semantics.
- A microphone permission request times out after 30 seconds. Its own visible foreground prompt uses the bounded native handoff below; a real background departure still locks immediately. Late permission grants must immediately stop their tracks and never revive a locked or cancelled recorder.

## Conversation Continuity and Interaction

- Ordinary toast messages appear just below the page header, centered with content-sized width and a bounded maximum. The open chat tools panel has a complete opaque background so conversation media cannot show through its rows.

- Each device stores an encrypted local reading anchor containing the first relevant visible message, its viewport offset, and whether the user was pinned to the bottom. Entering chat, returning from gallery or image detail, and unlocking restore that position instead of replaying a visible scroll from the first message. Short conversations align their latest message above the composer. Sending a new message keeps the newest message above the composer as its height or the keyboard changes; a delayed native scroll does not discard this intent, while an explicit upward reading gesture cancels it. On touch iOS WebKit, opening the composer from older history explicitly returns to the latest message. Closing from the bottom retains latest-message alignment; closing from history preserves the reading position. All list-owned positioning uses the same scroll owner, including the keyboard endpoint.
- Multiline typing and sending keep the header and plus action at their viewport edges. The text field expands upward and returns to its single-line height. While editing on touch iOS WebKit, layout growth commits in the input event and includes the live editor's overflow when marked text wraps before the measurement copy. Composition retains its expanded editing area until commit; other shrinking reads the latest value on the next frame. Only message contents animate for 280 ms after the endpoint layout commits. A capped multiline editor retains fixed top and bottom text insets while its contents scroll. The independent list reserves composer space inside its scrollable content, without enlarging its viewport, and restores its bottom or history anchor after resizing. Other browsers use one 280 ms frame update for visible field height and the matching timeline displacement. Repeated wrapping retargets message motion from the current painted position, and sending during expansion preserves that position before inserting the new row. Older-history readers retain their reading anchor throughout resizing. Reduced motion commits directly to the endpoint. Typing only changes the draft; new message rows appear after durable local enqueue.
- Unsent text is saved automatically as an encrypted local draft and restored after unlocking. Sending clears only the submitted draft after durable outbox storage; newer input remains intact.
- Opening the plus panel dismisses the keyboard while preserving the draft; direct system pickers retain their bounded foreground handoff. While the keyboard is open, a vertical touch on the conversation cannot scroll the list or dismiss the keyboard during movement; releasing the last finger dismisses it. Tapping outside the composer also dismisses on release. The expression button opens a half-screen liquid-glass panel beneath the composer, defaulting to individual GIFs. Stickers are grouped into complete packs with top thumbnail shortcuts; favorites use a star shortcut. Only Search opens a full-screen dialog, without a drag handle or bottom categories. GIF search returns individual animations; sticker search returns packs that can be previewed and downloaded atomically for local reuse. Default browsing and search read only published server catalog entries through authenticated same-origin APIs; client reads never trigger upstream acquisition. Expression originals are excluded from the application bundle, and upgrades remove the old public-asset cache. The full-screen background is inert; visible-read cursors remain paused while the picker is open. Tap or preview-send closes the panel on success, without scaling the image on tap or long press. Animated originals play in the picker and revealed chat images. Closing preserves the draft. Favorites and added packs are independent encrypted local copies, survive source-message deletion, and are not synchronized or included in recovery backups. See [MEMES.md](./MEMES.md).
- Page-level double-tap, gesture, and modifier-wheel zoom are suppressed; media enlargement belongs to the dedicated image viewer. The page uses the visual viewport so the composer follows the mobile soft keyboard, omitting the home-indicator inset while a docked keyboard is visible. Viewport panning only repositions controls and does not change document padding or trigger bottom-follow. Upward scroll intent immediately cancels bottom-follow, including near the bottom; sending explicitly resumes it. Safari’s browser-owned keyboard accessory toolbar cannot be forcibly removed by page code.
- Touch iOS WebKit chat uses an independently scrolling message list inside one visual-viewport shell. The root page is locked against scrolling; native inertia and boundary bounce belong to the list. The header, composer, and notices are positioned within the shell, so message overscroll cannot move them. ## Local Unlock and Privacy Curtain

- New vaults use a random 256-bit master key wrapped by a key derived from a WebAuthn PRF-capable passkey. Setup and unlock use the operating system's biometric or device-password user verification; entering the version-3 unlock gateway automatically starts verification, with manual retry after cancellation or failure.
- Both single-device and syncable passkeys are accepted. Backup eligibility is recorded at registration and verified on later assertions; it informs the security properties of the credential but does not make a valid credential fail setup.
- Legacy password vaults migrate to passkey-only version 3 after one successful password unlock. Existing version-2 gesture vaults require the old gesture once because it is part of the old key derivation, then are immediately rewrapped as passkey-only version 3.
- A browser-load-failure cover retains an enlarged blank bottom-right one-second long-press entry. The hold keeps its restrained progress cue; completion directly enters the gateway and starts passkey verification as soon as real document focus is present, without a decorative ring, fireworks or another button click. Because Safari may update `document.hasFocus()` without a `focus` event after foreground return, the gateway also observes a short silent-focus edge while retaining the normal lifecycle-bound focus listener. It never calls WebAuthn while unfocused. User-cancelled WebAuthn returns a “重新验证” action without a red error sentence. Pointer capture tolerates small slips, and repeated returns to the cover—including after foreground restoration—must leave its entry operable. Ordinary desktop browsers also accept holding unmodified F for two seconds while the cover is visible and focused; completing that trusted hold likewise starts gateway verification directly, while release before completion, blur, hiding, or composition cancels it. Neither entry substitutes for authentication, and browser-owned passkey UI still cannot be forced to appear.
- Each version-3 gateway unlock owns one native passkey request. Runtime teardown, including lock, pagehide, freeze and the existing 65-second verification bound, aborts that request as well as rejecting its late result. If the native result arrives while Safari still reports the visible document as unfocused, the gateway stays obscured and waits up to 1.5 seconds for real focus before continuing; it never accepts the result while unfocused. Waiting does not launch automatic parallel retries. Browser/OS-owned passkey confirmation and biometric selection remain system-controlled: the page requires user verification but cannot guarantee skipping “使用通行密钥” or forcing Face ID over device passcode.
- The touch cover entry preserves the browser's default focus path. If Safari returns visible but unfocused, the version-3 gateway requests focus on its existing unlock button and keeps that button enabled until real document focus is available. Focus return starts the live entry once; a manual button click remains a fallback. No native request or busy state starts while unfocused, and hidden visibility, pagehide, freeze, explicit lock or gateway replacement discard the waiting intent. This governs when verification starts; a completed result remains separately gated on the visible, focused return rule above.
- On ordinary desktop-browser blur or hidden visibility, conceal immediately, tear down rendered history, media, transfers and sockets, and retain the unlocked vault session only in page memory. A completed cover gesture can resume within 30 minutes of the last active in-app interaction. Cover input and foreground return do not renew the deadline. Check both wall-clock and monotonic deadlines before accepting activity or restoring a session, including after background timer suspension. Resume revalidates and decrypts the durable vault snapshot with the retained key; a changed/deleted vault requires normal authentication. No new key or plaintext persistence is introduced.
- Mobile/tablet browsers and installed PWAs retain strict locking: hidden visibility locks immediately, ordinary blur has a 250 ms teardown debounce, and idle timeout remains 10 minutes, suspended only during an active foreground call. Desktop calls keep the 30-minute inactivity deadline; remote call updates never renew it. UA/platform classification excludes mobile devices (including iPad desktop mode) and installed display modes; screen width or a keyboard alone never enables desktop retention.
- On all clients, unowned native-surface focus loss, export/clipboard/confirmation focus loss, pagehide, freeze, persisted pageshow, explicit lock and idle expiry discard any retained session. Gateway WebAuthn retains its bounded exception. Safari may briefly transfer window focus to its native keyboard after a direct, trusted primary pointer activation on the visible unlocked chat textarea. Only that activation may own one visible blur for at most 1.2 seconds. Fresh post-tap keyboard-opening geometry and the first owned visible blur may arrive in either order and jointly settle the handoff; window-focus return can clear it independently, while geometry evidence alone does not discard ownership before a possible blur. Programmatic focus, an already-open keyboard, a second blur, timeout after consumption, hidden visibility, navigation/lifecycle signals, idle expiry, session or textarea replacement, and leaving chat never inherit the exception. Because browsers do not expose a trustworthy blur reason, a real visible-window departure immediately after that tap can remain uncovered until the 1.2-second deadline unless a hard lifecycle signal arrives; this is a bounded foreground-usability tradeoff, not authentication. Foreground return after any ordinary departure still shows the cover until a deliberate entry gesture. A permanently mounted opaque curtain conceals synchronously before ordinary teardown; the page cannot invalidate thumbnails already cached by the browser or operating system.
- `ERR_CONNECTION_CLOSED` is followed by the device's unread incoming-chat count in the same monospace style with slightly stronger color. A restricted observer token can fetch only this number while the vault is locked. The server stores its hash, a monotonic per-device read cursor, and a countable-message flag; own-role messages, gallery uploads, and reactions do not count. Visible chat messages advance the read cursor. Foreground/online return refreshes the count, with 15-second polling while visible; offline cover keeps the last confirmed count. This is behavioral metadata, separate from cryptographic delivery receipts.
- A user-opened file chooser (up to five minutes) or microphone/camera permission request (up to thirty seconds) may own one visible window-focus loss while the app remains in the foreground. It does not exempt hidden visibility, pagehide, freeze, explicit lock or idle expiry. For image/gallery choosers, focus return consumes ownership; if no `change`/`cancel` arrives within the short return edge, the detached input is removed. Another departure, a real background transition, lifecycle teardown, or loss of owner invalidates the selection; late events are ignored and the user must choose again after unlock. A result arriving before focus gets at most 250 ms to return; uploads wait for a visible focused document and the original room/device. Browsers cannot reliably identify why a visible window lost focus or force an operating-system-owned picker/tooltip to close; removing the DOM input is a best-effort privacy cleanup, not a guarantee about native UI. Microphone/camera prompts retain their existing bounded handoff semantics.
- Only gateway passkey prompts may suppress their own hidden events before a conversation or socket opens, including recovery and migration gateways. If WebAuthn settles while the visible document is still unfocused, the opaque curtain remains and the gateway requires a real focus return within 1.5 seconds before consuming the result. Hidden settlement still locks immediately. The exception ends after that return edge or the outer 65-second bound and never overrides `pagehide`, explicit lock, or idle timeout.

## Recovery Setup

- Unlocked, online MLS devices automatically back up their recovery checkpoint and local history as ciphertext. Backup status, retry, local recovery-code viewing and optional history restore live in “备份与恢复”; manual recovery-file import/export controls are removed.
- A reminder can be dismissed through an encrypted local preference. It directs users to save their QR3 code separately; only the current device stores that code, encrypted in its vault. Viewing it requires fresh passkey verification and closes the active conversation first. The code screen locks after one minute or privacy teardown.
- A QR3 code locates the corresponding server backup and decrypts it locally. The server and administrator never receive the code or decryption keys. Forgotten code plus lost devices has no administrator bypass.
- MLS recovery proves the original identity but creates a fresh device, token and leaf. Another trusted active device must be online; all active devices need protocol support. Pending recovery fences the original for at most 15 minutes; success permanently revokes it.
- After replacement, rotate the code immediately. Persist the exact new encrypted wrapper and all retained archive keys locally before upload. Atomically retire the old online entry only when the new wrapper and archive transfer are stored. Failed or ambiguous uploads retry the same request; expose the new code as active only after confirmation.
- Recovery opens at a new message/receipt boundary without loading old history or reusing an old sending ratchet. Users explicitly request historical chat or creator gallery restore and enter the current new code again. Gallery-only restore must not create old chat bubbles or reply previews. Normal linked devices receive no archive secrets.
- Historical attachments still depend on retained original ciphertext and download only when viewed/saved. Codes and copied old backups can still decrypt offline after rotation; no remote destruction is promised. Foreground-only backups can lag the latest message.
- Old QR2 files require migration from a still-usable original device or trusted legacy recovery flow before switching to QR3. The current UI has no legacy file-import entry. See [RECOVERY_BACKUPS.md](./RECOVERY_BACKUPS.md) for migration limits, scope separation and failure behavior.
- Full local history remains available through bounded paging. Room-based administration on `admin.mijiu.cloud` uses a strong administrator password plus TOTP and exposes metadata only. Clearing a whole room requires fresh factors and exact room-ID confirmation; administrator credentials never recover user content.
