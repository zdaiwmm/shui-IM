# 知识库维护规则

目标是减少每次接手的重复阅读，而不是制造第二套会漂移的完整文档。

## 可用范围

这套知识库属于仓库文件，不是跨所有会话的全局记忆。新任务必须打开包含这些文件的项目目录；从其他分支或独立工作树启动时，也必须在该版本中包含这些文件。未提交文件不会自动进入从 `main` 新建的工作树。提交、推送仍按用户要求处理，不因维护知识库而擅自带入其他开发改动。

`AGENTS.md` 是 Codex 的项目指令入口，其余文件由入口指引按需读取。机制依据：[OpenAI 官方项目指令说明](https://developers.openai.com/codex/guides/agents-md)。本库不是实时监控，也不承诺自动补齐没有记录的历史对话。

## 新会话入口

2026-09-08 起，根 `AGENTS.md` 要求每个新会话先读本机 main 的入口及
[固定交付流程](workflow.md#固定交付流程)，报告规则来源 SHA。旧分支的历史流程不作为最新执行规则；
任务代码和产品／安全契约仍需按实际版本核实，不能把最新规则误当作该工作树已有最新实现。

规则的持久载体是已合并的仓库文件，不能只留在聊天、未提交目录或未合并分支中。
另一台电脑在获得同步授权并更新 main 后才能得到新规则；未联网核实时明确说明只是本机版本。

本机 Codex 全局 `AGENTS.md` 可保存仅针对 Quiet Room 的短入口：按 canonical origin
`zdaiwmm/shui-IM` 识别仓库，从本机 main 读取规则，覆盖旧工作树尚未包含新入口的接手缺口。
入口只引用仓库规则，不复制整份流程、不改变其他项目规则，也不授予或继承推送、合并、发布权限。
使用其他 `CODEX_HOME`、另一台电脑或全局 `AGENTS.override.md` 时，需要在实际生效的配置中核对该入口。

Codex 在新运行开始时发现全局和项目指令；修改文件不保证已经运行的会话自动重读。
活动会话应显式重读，新会话开工时用规则来源回执核验。
自动加载是指令发现机制，不是能强制任意模型执行的发布锁；实际 CI、精确 SHA 发布和回读门禁继续由现有工具检查。
依据：[官方 AGENTS.md 发现机制](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

## 哪个文件负责什么

- 根目录 `AGENTS.md`：每次会话都需要的短规则、接手顺序和不可违反的边界。
- `overview.md`：相对稳定的任务到代码/文档/测试路由。
- [workflow.md](workflow.md)：任务隔离、任务分级、模型建议、诊断检查点和交付规则；不替代安全、测试或发布门禁，也不自动配置模型。
- `status.md`：带时间和证据级别的工作树、生产状态、已知漂移与下一步门槛。
- `decisions.md`：长期决策、理由、后果、限制和权威依据。
- 既有根目录文档：详细产品、安全、测试、发布、部署和运维事实的权威载体。

## 何时更新

仅在以下情况更新知识库：

- 产品或安全不变量被明确增加、修改或废弃；
- 功能在“工作树、测试、真机、CI、生产”之间跨越了状态层级；
- 模块入口、测试命令或发布流程发生变化；
- 发现会让下一次会话作出错误判断的文档冲突；
- 用户明确确认了具有长期影响、无法仅从代码推导的取舍。

普通重构、无语义变化的改名、单次排错过程和每次测试输出不需要写入知识库。
纯问答、只读诊断或审核不自动触发文件修改；在用户授权的实际变更任务中同步维护。

### 发布后的固定触发点

每次生产发布都必须触发一次知识库对账和上下文轻治理；检查结果可以是“事实一致，
无需修改”，不能因为没有文档差异就跳过检查。触发顺序固定为：

```text
完整 CI → 隔离发布 → release.mjs 写入精确 SHA 回执并输出 DEPLOY_VERIFIED
→ publish.mjs 核对回执 → 独立只读生产回读 READBACK_OK
→ 知识库对账与上下文治理 → 文档检查 → 有差异时提交独立文档 PR
→ 核验并清理本批符合条件的工作树与分支 → 报告清理或保留结果
```

资源清理按 [工作流清理规则](workflow.md#发布后资源清理)执行。对账文档 PR 尚未合并时，保留其工作树与分支；已完成的开发资源逐项判断。未保存证据、活动任务或归属不明的目录不删除。清理属于本地/远端开发资源收尾，不删除服务器备份或发布产物，失败不能触发再次发布。

机械核验与删除使用 `npm run tasks:cleanup -- --plan /绝对路径/plan.json`，默认只检查；执行 agent 填写审阅过的交接确认，检查后加 `--apply`。清理回执存于公共 Git 目录，详情见[脚本说明](../workflows/task-cleanup.md)；它不自动证明生产或会话已停止。

不要在 PR 合并、CI 变绿、服务器开始切换或只看到 `DEPLOY_OK` 时把状态写成已部署；
这些时间点都不能证明生产最终运行目标版本。对账属于维护窗口结束后的独立后置阶段，
文档失败不能触发回滚或重新发布。应保存同一份发布/回读证据，只重试对账，并明确写
`CONTEXT_SYNC_BLOCKED` 或等价状态。若固定入口成功而独立回读未完成，分别记录
“固定入口已验证”和“独立回读待完成”，只重试只读回读及后续对账。

如果发布进入过非只读切换阶段后连接中断、出现开放流量后的检查失败，或没有取得精确
成功回执，生产状态不能默认为旧版或新版。先独立回读；在查明前记录
`PRODUCTION_STATE_UNRESOLVED`，禁止盲目重发。实际已切换时按真实生产 SHA 对账，不能因
外层入口失败而让知识库继续声称旧版本仍在运行。

每次发布的轻治理负责同步可机械验证的生产事实、清除过时的候选状态、检查链接与敏感
信息，并确认 `status.md` 没有把知识库提交误称为线上应用提交。现有
`node scripts/check-docs.mjs` 只验证本地链接、标题锚点、围栏和文本格式；`git diff --check`
检查差异格式，CI 凭据扫描检查已提交内容，跨文档语义仍需人工或代理审阅。产品/安全边界、模块路由、
测试命令或发布流程实际变化时，再做深治理，检查 `overview.md`、`decisions.md`、
`AGENTS.md` 和 `PRODUCTION_SECURITY_GATE.md`；不要让生成器每次机械重写长期语义。

结构化生产回读使用 `npm run deploy:readback -- --sha <精确SHA>`，成功/失败证据保存在
`.git/quiet-room-readback/`，安全续跑只重跑该只读入口，不能触发生产切换。在独立文档 PR
对账器落地前，由执行发布的任务按上述顺序完成审阅与对账。未来文档自动化必须在第二个独立克隆或单独 `git worktree` 中运行，不污染调用
发布的工作树，也不得复制 `.deploy.local.json`、密钥相关环境或未脱敏原始回执。有文档
差异时创建 PR；无差异时记录检查成功，不制造空提交。不直接推送 `main`；文档 PR 合并后
仓库 SHA 可以领先于线上应用 SHA，不因此重新发布。

### 自动事实与审阅事实

自动对账只可写入由严格、版本化、白名单化的发布/CI/回读组合证据直接证明的字段，例如：完整应用 SHA、精确 SHA 最新完整 main CI run、
发布与回读时间、线上 `current-sha`、维护标记、容器运行状态、实际健康探针结论、镜像
一致性、HTTPS 健康字段、公开产物一致性、WebSocket 检查和功能开关。`running` 与
`healthy` 必须分开；没有健康探针只能写运行中。

以下内容必须继续审阅，不能从发布成功、PR 标题或 Git diff 自动推导：用户确认的产品
取舍、功能是否完整、协议或安全边界是否未变、真机是否通过、权限/播放器手感、独立
安全审计结论以及“所有功能没有问题”。缺少绑定目标 SHA 的证据时，保留“未验证”。

### 大批量变更的成本控制

同时涉及三个以上风险域，或触及 `src/app.ts`、保险库、消息载荷、服务端投影和浏览器
生命周期中的多个部分时，开工前先建立短验收矩阵并按风险域分批：每批写明产品边界、
定向测试、跨批依赖、全量回归触发条件和真机缺口。实现范围一旦冻结，除真实阻塞外不在
同一发布批次继续扩张。

验证使用漏斗而不是机械重复全量：每批先运行类型检查、单元测试和最小相关浏览器专项；
集成冻结后运行一次 `npm run check:full`。失败后先分类为产品、测试夹具或基础设施：产品
失败修改实现，夹具失败只修正可移植性并保留产品断言，下载/网络/排队故障只做有证据的
有限重试。未完成分类前，不同时修改产品与断言，也不启动另一轮完整验证。

浏览器几何断言不得把 CJK、emoji 或系统字体的固定像素当作产品语义。优先断言事件顺序、
首帧零跳动、相对几何、动画时长、最终状态、DOM/焦点保留和减少动态效果；必须断言距离时，
使用当前行高等运行时几何推导阈值，并在失败信息中输出测量值。测试夹具应显式把目标元素
放入视口，避免浏览器自动滚动或字体回退形成环境相关结果。

发布仍保留 PR 审查、精确 main 完整 CI、隔离发布和独立回读。性能优化应集中在依赖/浏览器
缓存、受影响分组的快速反馈、克隆通道快速预检与服务器调用前的有界重试；删除安全门或在
进入非只读阶段后自动重发不属于提速。若未来复用 PR CI，必须先有经审阅的源码树一致性
证明、策略变更和自动回归，不能临时人工推断。

里程碑更新只报告当前证据层级、一个阻塞和下一步，避免反复转述探索过程。2026-09-05
批次的事实、问题与改进清单见[交付复盘](../../audit/2026-09-05-mobile-ux-delivery-retrospective.md)。

## 如何更新

1. 先更新真正拥有该事实的详细文档或代码测试。
2. 再更新知识库中的导航、状态或决策摘要，避免它成为唯一事实源。
3. 在 `status.md` 记录时间、目标提交/工作树、证据层级和仍未验证的部分。
4. 决策使用稳定编号；变更时保留原编号并标记“被 D-xxx 取代”，不要静默改写历史理由。
5. 删除过时的临时状态，而不是让 `status.md` 无限追加。重要历史保留在 Git 和带日期的 `audit/` / 发布记录中。
6. 检查所有相对链接存在，检查入口是否仍然简短，并确认没有复制密钥或真实数据。
7. 发布后分别记录“已部署应用 SHA”和“知识库所在仓库状态”；文档提交 SHA 不进入线上
   应用字段，避免文档更新形成自引用发布循环。

## 证据写法

推荐使用以下明确措辞：

- `工作树存在`：文件或改动当前可见，尚未推断测试、合并或部署。
- `本地自动测试通过`：写明运行的命令、时间和目标工作树；不能外推到真机或生产。
- `真机验证通过`：写明设备/系统/浏览器和范围；模拟 UA 或合成媒体不算真机。
- `CI 通过`：写明完整提交和 CI 运行；不能用配置文件存在代替运行结果。
- `已部署`：写明完整提交、发布记录和生产回读；本地构建成功不算上线。

若证据只支持部分范围，就直接写“仅覆盖……，未覆盖……”。不要使用含糊的“已完成”“应该没问题”或“全面验证”。

## 冲突处理

- 产品文档与实现不一致：记录为产品/实现漂移，请用户或现有明确验收依据裁决；不要让当前实现自动成为产品决定。
- 安全文档与实现不一致：先采取失败关闭，检查相关威胁模型和测试，再同步修改。
- 历史审查与当前状态不一致：历史记录保持原样，在 `status.md` 写当前快照，不回写篡改旧报告。
- 发布记录之间不一致：优先比较记录时间、完整提交和生产回读；不凭猜测选择最新版本。
- 当前工作树持续变化：停止固化细节，只记录“开发中”，并在实际交付前重新取快照。

## 安全与隐私

知识库永远不得包含：

- `.deploy.local.json` 或非示例 `.env` 的内容；
- SSH、TURN、VAPID、GitHub、房间或设备凭据；
- 邀请链接、恢复包、恢复码、私钥、真实消息或附件；
- 生产数据库、备份内容、真实用户标识或不必要的网络地址。

需要记录配置时，只写环境变量名称、示例文件路径和验证方法，不复制实际值。

## 定期轻审

在重大发布、产品边界变化或文档明显漂移后做一次轻审：

1. `AGENTS.md` 是否仍能在几分钟内读完；
2. 项目地图里的文件和命令是否仍存在；
3. `status.md` 是否把旧工作树误称为当前状态；
4. 决策依据是否仍指向有效、相互一致的资料；
5. `PRODUCTION_SECURITY_GATE.md` 的阻塞项是否被准确反映；
6. 是否无意写入敏感信息。

不需要把每个新会话自动转成日志，也不需要为这个规模的仓库建立向量数据库。只有当资料数量、跨仓库范围或检索需求显著增长后，再评估自动索引。
