# 知识库维护规则

目标是减少每次接手的重复阅读，而不是制造第二套会漂移的完整文档。

## 可用范围

这套知识库属于仓库文件，不是跨所有会话的全局记忆。新任务必须打开包含这些文件的项目目录；从其他分支或独立工作树启动时，也必须在该版本中包含这些文件。未提交文件不会自动进入从 `main` 新建的工作树。提交、推送仍按用户要求处理，不因维护知识库而擅自带入其他开发改动。

`AGENTS.md` 是 Codex 的项目指令入口，其余文件由入口指引按需读取。机制依据：[OpenAI 官方项目指令说明](https://developers.openai.com/codex/guides/agents-md)。本库不是实时监控，也不承诺自动补齐没有记录的历史对话。

## 哪个文件负责什么

- 根目录 `AGENTS.md`：每次会话都需要的短规则、接手顺序和不可违反的边界。
- `overview.md`：相对稳定的任务到代码/文档/测试路由。
- `status.md`：带时间和证据级别的工作树、生产状态、已知漂移与下一步门槛。
- `decisions.md`：长期决策、理由、后果、限制和权威依据。
- 既有根目录文档：详细产品、安全、测试、发布、部署和运维事实的权威载体。

## 何时更新

仅在以下情况更新知识库：

- 产品或安全不变量被明确增加、修改或废弃；
- 功能在“工作树、测试、真机、CI、生产”之间跨越了状态层级；
- 模块入口、测试命令或发布流程发生变化；
- 发现会让下一次会话作出错误判断的文档冲突；
- 用户明确确认了具有长期影响、无法仅从代码推导的取舍。

普通重构、无语义变化的改名、单次排错过程和每次测试输出不需要写入知识库。
纯问答、只读诊断或审核不自动触发文件修改；在用户授权的实际变更任务中同步维护。

## 如何更新

1. 先更新真正拥有该事实的详细文档或代码测试。
2. 再更新知识库中的导航、状态或决策摘要，避免它成为唯一事实源。
3. 在 `status.md` 记录时间、目标提交/工作树、证据层级和仍未验证的部分。
4. 决策使用稳定编号；变更时保留原编号并标记“被 D-xxx 取代”，不要静默改写历史理由。
5. 删除过时的临时状态，而不是让 `status.md` 无限追加。重要历史保留在 Git 和带日期的 `audit/` / 发布记录中。
6. 检查所有相对链接存在，检查入口是否仍然简短，并确认没有复制密钥或真实数据。

## 证据写法

推荐使用以下明确措辞：

- `工作树存在`：文件或改动当前可见，尚未推断测试、合并或部署。
- `本地自动测试通过`：写明运行的命令、时间和目标工作树；不能外推到真机或生产。
- `真机验证通过`：写明设备/系统/浏览器和范围；模拟 UA 或合成媒体不算真机。
- `CI 通过`：写明完整提交和 CI 运行；不能用配置文件存在代替运行结果。
- `已部署`：写明完整提交、发布记录和生产回读；本地构建成功不算上线。

若证据只支持部分范围，就直接写“仅覆盖……，未覆盖……”。不要使用含糊的“已完成”“应该没问题”或“全面验证”。

## 冲突处理

- 产品文档与实现不一致：记录为产品/实现漂移，请用户或现有明确验收依据裁决；不要让当前实现自动成为产品决定。
- 安全文档与实现不一致：先采取失败关闭，检查相关威胁模型和测试，再同步修改。
- 历史审查与当前状态不一致：历史记录保持原样，在 `status.md` 写当前快照，不回写篡改旧报告。
- 发布记录之间不一致：优先比较记录时间、完整提交和生产回读；不凭猜测选择最新版本。
- 当前工作树持续变化：停止固化细节，只记录“开发中”，并在实际交付前重新取快照。

## 安全与隐私

知识库永远不得包含：

- `.deploy.local.json` 或非示例 `.env` 的内容；
- SSH、TURN、VAPID、GitHub、房间或设备凭据；
- 邀请链接、恢复包、恢复码、私钥、真实消息或附件；
- 生产数据库、备份内容、真实用户标识或不必要的网络地址。

需要记录配置时，只写环境变量名称、示例文件路径和验证方法，不复制实际值。

## 定期轻审

在重大发布、产品边界变化或文档明显漂移后做一次轻审：

1. `AGENTS.md` 是否仍能在几分钟内读完；
2. 项目地图里的文件和命令是否仍存在；
3. `status.md` 是否把旧工作树误称为当前状态；
4. 决策依据是否仍指向有效、相互一致的资料；
5. `PRODUCTION_SECURITY_GATE.md` 的阻塞项是否被准确反映；
6. 是否无意写入敏感信息。

不需要把每个新会话自动转成日志，也不需要为这个规模的仓库建立向量数据库。只有当资料数量、跨仓库范围或检索需求显著增长后，再评估自动索引。
