### 持续远端交付授权

2026-09-09 用户明确要求将自动验收、推送、创建 PR、等待 CI、合并固定为后续默认流程，并要求不再逐项询问。此为针对 `https://github.com/zdaiwmm/shui-IM.git`（同一仓库的 SSH 地址等效）的持续授权，后续会话从本机 main 读取后沿用；它替代旧规则中“默认不 fetch/push/PR/合并”或“每次重新授权远端交付”的表述。

- 范围仅限用户交办的本任务及其必要修复、测试和知识库更新；允许核验远端、同步主线、提交、推送任务分支、创建 PR、等待必需 CI 并在通过后合并 main。不得顺带纳入其他任务、强推、直接推送 main 或绕过分支保护。
- 自动验收属于交付必做项：按风险运行现有测试门禁，UI 改动补相关浏览器验收；缺少依赖时按锁文件安装，环境或权限失败先处理再重跑。测试失败必须定位修复，不能只写“未运行”便结束，也不能以单元测试通过替代交互验收。
- 核对精确候选、PR head、最新 CI 和可合并状态后执行合并并回查合并结果；候选变化后重新评估受影响验证。报告代码 SHA、PR、测试、CI 和实际交付终点，真机缺口单列。
- 只分析、只出方案、不提交、不推送、暂不合并等明确限制优先；纯问答不触发写入。生产发布、其他仓库和未确认的产品或安全语义不包含在本授权中。
- 沙箱或自动审批出现阻塞时先提交已有授权和精确远端证据申请必要权限；不能绕过拒绝。只有确实无法继续时报告具体阻塞，不将同一已授权动作重新当作普通确认问题。

这是每次实施任务内自动执行的交付规则，不是定时后台任务，不额外创建调度器。

## 执行顺序

1. 接手：复核工作树和 HEAD，按项目地图读取必要资料；所有写入任务必须先通过下节开工隔离门槛，不能等发现同文件冲突后才隔离。进入任务树后运行 `npm run repo:doctor -- --local`，检查本机 Node、公共及工作树 Git 元数据写入、开发工具；远端同步获授权后再运行不带 `--local` 的检查。
2. 定义完成：用简短任务卡明确故障域、验收结果、定向验证和最终门禁。常规授权范围内直接执行，不为任务卡额外要求确认。
3. 诊断：先保留复现步骤与失败证据，提出可检验的假设，再修改。移动 UI 明确设备、系统、浏览器；模拟环境通过不能写成真机验收通过。
4. 实现：围绕当前验收做最小改动。旁支问题记录为后续项；只有阻断当前目标或必要的安全修复才纳入，并说明原因。
5. 验证：开发中定向反馈，候选冻结后按既有门禁执行。纯文档用文档检查；普通代码通常 check；跨页面、生命周期、附件等用 check:full；通话按地图补专项。
6. 审查与交付：审查具体正确性和安全问题；通过后不反复扩大审查。记录证据层级、已解决内容、未验证范围。发布必须满足既有授权与精确提交要求。

### 阶段与完成证据

新会话首先报告：`规则来源 SHA；实际工作目录／分支／HEAD；未提交状态；当前任务目标与授权范围`。
同一轮执行只更新变化项。按下表推进，每个阶段分别记证据，不能只写“完成”。

| 阶段 | 固定动作 | 完成证据与边界 |
| --- | --- | --- |
| 接手 | 一次读取 Git 状态、HEAD、远端地址、worktree 清单和状态页，按项目地图补读必要文档 | 明确规则版本、目录归属与任务范围；不读取凭据、消息或备份内容 |
| 连接与同步 | 当前任务获远端同步授权后用 `npm run repo:doctor` 核验 GitHub；获取需要的远端引用；干净 main 用 `npm run repo:pull` 快进 | 记录核实过的 main SHA；fetch 只更新引用，不声称工作目录已切换；ahead／diverged 转独立集成 |
| 盘点 | 优先读取共享交接记录和待合并 PR，再查本批任务；固定分支、head、依赖、测试与去向 | 分类为待纳入、已纳入、明确排除、归属待确认；不能把所有旧分支默认合入 |
| 集成 | 在当前任务的集成授权范围内，从核实基线新建独立 worktree，按依赖顺序合入，解决技术冲突，冻结候选 | 不修改其他任务现场；产品／安全语义冲突先澄清；保存源 head 到集成提交的映射 |
| 候选验证 | 用户可见发布先更新 `release.json` 唯一 ID 和说明；按风险运行现有门禁 | 记录命令、候选 SHA／文件树、结果与真机缺口；失败先分类 |
| PR | 当前任务获推送授权后用 `npm run repo:push` 推送已提交任务并创建 PR；必需检查通过且获得合并授权后合并 | 核对 PR 精确 head、CI 与可合并状态；合并时匹配已审阅 head，不用管理员绕过保护 |
| main 核验 | 回取合并提交，在本机集成授权范围内快进干净 main；准备发布时等精确 main 最新完整 CI | PR CI 不替代精确 main CI；仅同步 Git 不声称本机服务或真机已验收 |
| 发布确认 | 准备完整 40 位 SHA、版本 ID、变更范围、CI、预检和未验证项，请用户确认本次发布提交 | 当前 main 改变后重新审阅并取得新目标确认；旧发布记录、脚本参数和本流程都不是确认 |
| 发布与回读 | 确认后只用 `node scripts/publish.mjs --sha <SHA>`，核对精确成功回执后独立 `npm run deploy:readback -- --sha <SHA>` | 分别取得 `DEPLOY_VERIFIED` 与独立 `READBACK_OK`；不从本地脏目录传代码到生产 |
| 对账与收尾 | 第二个不含部署配置的工作树更新发布记录和状态，文档检查、PR、CI，在相应授权范围内合并；再按已有清理规则核验资源 | 线上应用 SHA 保持本次已发布值；文档提交不触发再次部署；清理或保留均报告原因 |

### 避免重复与误合并

- **连接复用已有配置**：复用已验证的仓库 SSH 配置或现有认证。Git SSH 与 GitHub CLI API 认证分别核验，
  不为每条命令重建密钥或重复登录。GitHub 的 `ssh -T` 应结合认证成功提示判断，不能仅按非零退出码认定失败。
  网络／沙箱失败与密钥错误分开诊断；不输出 token 或私钥，不关闭主机校验。
  配置路径按部署文档复用，不把本机路径硬编码进仓库，也不向文档工作树复制部署配置。
- **先祖先、后补丁**：`git branch --no-merged` 只说明图关系，不等于任务未集成。
  已是 main 祖先的任务不重复合；squash／cherry-pick 结合 PR head、合并提交、文件树或 `git range-diff` 核对。
  `git cherry`、相同标题或相似 diff 只能辅助定位，不能独立证明所有功能已纳入或允许删除旧分支。
- **未提交内容先保留**：对归属不明且非本次必需的改动明确暂不纳入，继续处理已确认任务；
  不自动 stash、移动、暂存或重放旧补丁。它确实影响本批验收或用户要求纳入时，先确认范围再适配新基线。
- **验证针对冻结候选**：开发中定向测试，冻结后跑风险匹配门禁；相同文件树已通过且没有新证据时不重复本地全量。
  在有推送授权时，可让 PR CI 与本地验证同时运行，但本地必需验证未完成前不合并。
  纯知识库改动只跑文档检查；CI 按既有策略选择全量时正常等待，不临时修改白名单或跳过门禁。
- **等待复用同一进程**：用 `gh run watch <run-id> --exit-status --interval 30` 等待；
  工具返回控制权后保留同一会话，不重复开启 watcher。结束后核对最新 run、attempt、SHA 和完整汇总。
- **证据新旧分开**：操作前复核实时 main 和生产，其他任务可能已更新它们；历史状态页不是锁。
  文档对账提交领先应用版本是正常现象，不能因此产生第二次发布。

### 中断与失败续跑

接续时恢复本任务精确提交、PR／CI run、发布／回读证据，核对当前任务的授权记录和外部状态。
无法核实的授权或结果标为未知；不能因为相似任务过去获准而继续写入。共享交接登记沿用下文固定字段，
自动测试、PR、CI 和生产回执保存在现有载体，不再造一套“已完成”的真相来源。

| 已有证据／失败位置 | 下一步 |
| --- | --- |
| 本地端口 `EPERM`、下载或网络失败 | 记录环境失败并申请必要执行权限；重跑受阻验证，不改产品断言 |
| 冻结候选的必需测试失败 | 分类并修复，候选改变后重验；不把旧 SHA 成功结果挪给新 SHA |
| PR 已合并、main CI 未完成 | 找到该合并 SHA 的最新 CI 并继续等待；不重复建 PR 或合并 |
| 发布未进入切换，预检失败 | 处理明确原因；核实本次获批 SHA 与 main 后使用同一固定入口 |
| 已进入切换但回执不明 | 先独立回读，记录 `PRODUCTION_STATE_UNRESOLVED`；禁止盲目重发 |
| 已有 `DEPLOY_VERIFIED`，独立回读失败 | 同一 SHA 只重跑回读；linked worktree 的证据写入限制按 RELEASING.md 在精确发布克隆处理 |
| 已有 `READBACK_OK`，对账／文档 PR 失败 | 保存同一份脱敏证据，标记 `CONTEXT_SYNC_BLOCKED`；只继续对账，不再发布 |
| 对账已合并、清理保留／失败 | 只检查本批精确资源；活动目录、未知文件、忽略文件等按工具结果保留，不强删 |

最终报告包含实际完成的终点、代码／文档 SHA、验证与生产证据、未纳入内容和未完成项。
用户不需要手动选择 Git 命令；agent 负责在当前任务明确授权的范围内执行固定步骤。

## 分支与集成由 agent 管理

整条交付的阶段入口见上方[固定交付流程](#固定交付流程)；本节继续定义隔离、集成与授权边界。

### 开工隔离门槛

适用于代码、测试和文档写入。纯问答和只读调查无需创建。此门槛优先于后文的环境复用描述。

1. 修改前执行 `git status --short`、`git rev-parse --show-toplevel`、`git branch --show-current`、`git rev-parse HEAD` 和 `git worktree list --porcelain`。明确实际执行目录，不能以应用任务名称代替路径核验。
2. 仓库的共享主工作树是接手、本机集成与本机测试服务目录，默认只读，不直接编写改动。非 main 分支、干净工作树、自己刚打开会话均不构成独占证明。只有本会话先前创建/获分配的隔离 worktree，或可核实的本任务接续记录，才允许复用；禁止把另一个活动任务的 worktree 当成本任务环境。
3. 没有独占环境时，由 agent 核实当前本机 `main`；用户已要求同步 GitHub 时还要核实 `origin/main`。从选定且已记录的基线创建新的 `codex/<任务简名>` 分支与独立目录。目录选择当前权限允许的位置；必要时申请执行权限。Git linked worktree 的分支引用通常写入主仓库的公共 `.git`，因此“工作树可写”不等于“可创建分支”：创建前必须验证公共 Git 元数据可写。若创建失败是该权限边界，优先用受控授权完成一次分支/worktree 创建；若环境不允许授权，由协调器预创建分支后分配 worktree，或按下一节建立独占完整克隆；不能在 detached worktree 中直接改代码，也不能退回共享目录写入。
4. 进入新目录后重复核对真实路径、分支、HEAD 和状态。若应用提供的是 detached HEAD worktree，修改前先为其建立任务分支。随后向用户给出一条开工回执：`工作树：绝对路径；分支：名称；基线：SHA；归属：本任务新建/有证据复用`。
5. 之后所有编辑、依赖安装、构建、测试和 Git 命令都使用该绝对工作目录；不能仅改变一个 shell 的当前目录就假定其他工具也已切换。应用会话显示的目录可能仍是源项目，实际工具路径与 Git 核验结果才是证据。
6. 提交前再次核对路径、分支和差异归属，只提交本任务内容。收尾列出实际提交 SHA，不能只说“规则已写入”就算完成持久化。

### 本机环境准备与受限执行

- 新 worktree 不携带 `node_modules`。缺少开发工具时由 agent 在本任务目录执行
  `npm ci --include=dev --no-audit --no-fund`，然后重跑 `npm run repo:doctor -- --local`。
  不用临时 `npx` 下载替代锁定依赖，也不共享其他任务可变的 `node_modules`。
- `EPERM`、`EACCES`、DNS 失败及受限环境中的 keyring 读取失败，先按环境权限故障处理。
  用执行工具的受控提升权限重跑原操作；不要直接递归 `chmod` 公共 `.git`，也不要把
  受限环境中的 `gh auth status` 失败直接认定为令牌失效或反复要求用户登录。
- Git 操作需写公共 `.git` 和本工作树 Git 管理目录。工作树文件可写不代表 Git 元数据可写；
  `--local` 对两个目录进行实际写入探测。检查不会自动修改权限或分支。
- 获授权的提升权限仍不可用时，在允许的路径新建独占完整克隆作为隔离替代，并建立
  `codex/<任务>` 分支；核对基线，仅迁移本任务已确认差异。原工作树保留，不能删除或覆盖
  已有目录、未知改动、凭据或数据。此替代适用本节隔离门槛，不自动授予远端操作权限。
- 用户已授权的依赖准备、Git 提交、网络同步由 agent 执行。只有主机环境重试也证明
  凭据失效，或自动审批明确拒绝必要操作且无可行替代时，才向用户报告具体剩余动作。

示例命令由 agent 替换任务名、路径和核实后的基线后执行，用户无需输入：

```sh
git worktree add -b codex/task-name /private/tmp/quiet-room-task-name main
git -C /private/tmp/quiet-room-task-name rev-parse --show-toplevel
git -C /private/tmp/quiet-room-task-name branch --show-current
git -C /private/tmp/quiet-room-task-name rev-parse HEAD
git -C /private/tmp/quiet-room-task-name status --short
```

这是可审查的 agent 执行门槛，不是应用自动创建 worktree 的设置或禁止写入的系统沙箱。只有提交并集成这些指令后，新基线才会携带规则；旧任务和旧 worktree 必须单独读取更新后的入口，不能假定会自动刷新。

- 开工先核对 HEAD、分支、工作树改动和已有 worktree。当前已是本任务独占的 worktree/分支时直接复用；否则从核实过的基线自动建立独立 worktree 与 `codex/<任务简名>` 分支，重名时添加后缀。后续命令明确指定该 worktree，避免在多个会话共用的目录切分支。
- 本机开发基线默认采用核实过的本机 `main`。用户明确要求同步 GitHub，或当前电脑需要从 GitHub 接续另一台电脑的成果时，先核实 `origin/main`；网络无法核实必须说明远端状态未知。依赖尚未集成的任务时记录依赖提交，从该提交开始；不能自行混入其他开发分支。
- 未提交改动先确认归属；不得自动 stash、reset、移动、暂存或提交其他任务的修改。已有本任务改动可按精确差异迁移到隔离目录并核对，来源归属不明时只隔离处理明确属于本任务的部分。
- 开发任务完成风险匹配验证后提交本任务分支，并返回分支、基线 SHA、提交 SHA、验证证据、未验证项与依赖。用户已授权本机集成时，再按下节更新本机 `main` 并回读服务；用户明确要求 GitHub 同步时，才按远端交付一节推送和登记。暂存只使用明确路径或可核对的差异块，不使用无差别 `git add .`。纯问答不创建分支或提交。
- 单纯提出问题不默认授权合并到 main 或生产发布。用户说“把这些任务一起合并”“统一集成”或“合并发布”时，agent 自行发现对应任务的实际分支/提交并核对，不要求用户手工抄 SHA 或执行 Git 命令。只有任务归属确实无法确定时才询问缺失信息；不能仅凭相似分支名纳入代码。
- 集成使用独立 worktree 和集成分支，固定参与任务及其精确提交，按依赖顺序整合。选择合并或 cherry-pick 前检查提交祖先和已有补丁，避免重复引入；不修改开发会话的工作树。技术冲突在已有契约内解决；产品或安全语义冲突不得凭猜测裁决。
- GitHub 同步阶段验证最终组合后，按已有仓库规则创建 PR、核对 CI 并完成已授权合并；检查、保护规则或权限不满足时明确报告阻塞，不绕过。多个开发任务各自通过的测试不能替代最终组合验证。
- 合并和生产发布是不同动作。生产继续遵守 RELEASING.md：已有发布授权和精确目标提交确认后才能使用固定入口；agent 展示目标及证据供确认，用户不必自行查找提交号。发布成功后独立回读并对账。仅合并任务不会自动部署。
- 发布成功后按下节清理本批资源，无需用户再次提出清理要求；不满足条件的资源保留并记录原因。

以上是 agent 的操作规则，不是已经运行的后台调度器。不会自动创建其他会话或更改模型；并行仍须遵守任务授权与共享文件依赖约束。未合并的本页不会自动出现在从 main 新建的 worktree；过渡期间可读取源目录本页执行，不得为了携带规则复制整个脏工作树。

## 本机 main 与局域网验收

家里和公司分别运行独立的本机测试环境。本机 `main` 是当前电脑的局域网验收候选，不等于 `origin/main`，也不等于生产。完整状态分层、集成步骤、进程回读、通行密钥来源要求和跨电脑同步边界见[本机局域网测试与跨电脑同步](../workflows/local-lan-testing.md)。

### 有条件自动集成

2026-09-08 用户明确确认本规则：后续 Quiet Room 实施任务完成本任务提交和风险匹配验证后，
默认由 agent 集成本机 main、按需更新局域网服务并独立回读，无需逐次要求用户重复授权。
本条是用户确认的持续本机授权，优先于旧文档中“每次等待本机集成授权”的描述；
只分析、只出方案、暂不集成等当前任务的明确限制优先。单纯问答不触发集成。

- 只纳入归属明确、已完成且已提交的本任务精确候选；不得自动收拢其他旧分支、半成品或未确认需求。
- 同一电脑同时只有一个集成操作。使用公共 Git 目录下 `quiet-room-local-integration.lock` 目录的原子 `mkdir`
  取得互斥锁，记录当前任务、PID、基线和候选；占用时等待或报告。未知／遗留锁不得直接删除，先核实归属。
  锁覆盖 main 更新、必要重启、服务回读和对账；本任务完成后只释放自己持有的锁。此为 agent 执行规则，不是后台调度器。
- 锁内复核 main 的分支、HEAD、未提交状态与实际服务归属。脏 main 或归属不明改动使集成暂停；
  不自动 stash、reset、覆盖或提交他人内容。锁外完成候选验证时，锁内发现 main 已前进须重新检查组合。
- 有分叉时在独立集成 worktree 合并；语义明确的技术冲突自动解决。产品／安全契约冲突不得猜测，
  保留现场并询问。无文本冲突也要检查依赖、共享生命周期和行为影响，最终组合通过风险匹配验证后才快进 main。
- 记录合入前 main、任务候选、集成提交和验证证据。必要重启只作用于已确认的本机测试进程；
  当前已知正在进行真机验证或通话时先等待合适窗口，不打断活动验证。重启后检查目标代码与后端健康。
- 集成或回读失败只续跑失败阶段；不以强制回退 main、迁移／清空数据或重复生产发布来处理。
  本规则不授予 fetch、pull、push、PR、远端 main、生产发布或测试数据迁移权限。

1. 所有改动仍在独立任务 worktree 完成、验证和提交；共享本机 `main` 目录不得直接编写代码或文档。
2. 用户已授权本机集成时，先核对共享目录位于 `main`、工作树干净且固定候选 SHA。可快进时使用 `git merge --ff-only`；不能快进时转到独立集成 worktree 解决组合和冲突并复验，禁止覆盖用户改动。
3. 集成后核对本机 `main` 精确 SHA，并确认实际局域网前后端进程从该主工作树运行。前端回读目标代码、后端健康检查成功后，才能记录“本机服务已回读”。是否重启按变更类型与回读结果判断，不能仅因进程存在或页面可打开就写成已更新。
4. 通行密钥真机验收必须使用稳定、设备信任、证书主机名匹配的 HTTPS 来源，并记录设备、系统、浏览器、来源与通过范围。自动测试和服务回读不能替代真机结果。
5. 本机集成授权不包含 fetch、pull、push、PR、远端 main 或生产发布。每轮分别报告任务候选、本机 main、自动测试、本机服务、真机、GitHub 和生产状态。

## GitHub 远端交付与跨任务集成

实施任务按[持续远端交付授权](#持续远端交付授权)默认进入本节，通过 PR 与 CI 合并远端 main；禁止直接推送 main。生产发布独立确认。只分析、只出方案、不提交或不推送等明确限制优先。

1. 开发完成后，先在本任务工作树保存归属明确的任务提交，保证工作树干净，再获取最新 origin/main。记录本轮核实的主线 SHA；网络失败时标记主线未核实，不冒称已同步或已就绪。
2. 在本任务分支合入这次核实的主线；主线已是祖先时跳过。默认使用正常 merge，保留已推送的历史，不为同步主线强制推送或重写共享历史。发现冲突由原开发会话在本任务范围内处理；产品、安全语义不明确时保留阻塞，不替用户决定。
3. 即使 Git 没有文本冲突，也检查主线对本任务依赖、共享文件和验收的影响。按照最终组合运行风险匹配验证；文档用文档检查，代码通常 check，生命周期等按既有门禁。已经通过的无变化定向检查不机械重复；修复冲突造成的变化必须重新验证。记录测试所对应的候选 SHA 或精确工作树。
4. 提交并推送显式的本任务分支到 origin，回查远端 head 与本地候选精确一致后才写“已推送”。远端同名分支发生变化时先核对归属与新增提交，不强推覆盖。失败标记“本地完成、推送失败”，保留可恢复现场。
5. 交付时再次查询主线引用。如果与本轮验证基线不同，标记“主线已前进，待集成复核”；不要为了追逐持续变化的 main 无限同步和重跑。只有新的变化确实阻断本任务交付时才继续处理。
6. 登记任务、工作树、分支、起始基线、同步主线 SHA、精确候选 SHA、远端回查结果、变更文件、验证证据、未验证项、依赖与冲突提示。分支后续新增提交会使原登记过期，不自动进入已经冻结的批次。

### 共享交接登记

清单工具尚未实现时，由 agent 在公共 Git 目录（通过 git rev-parse --path-format=absolute --git-common-dir 定位）下 quiet-room-deliveries 保存一任务一 JSON。文件名使用任务分支 UTF-8 字节的 SHA-256 摘要，先写唯一临时文件再原子替换；同一任务只能由其负责会话更新。记录固定字段：version=1、task、branch、worktree、startBase、syncedMain、head、remoteHead、changedFiles、verification、unverified、dependencies、status、updatedAt。未知值明确标记，不填推测的通过结论。

status 使用 ready、needs_recheck、push_failed 或 blocked；ready 仅表示开发交接就绪，不代表真机通过或授权发布。登记为 ready 前必须核对远端 head 与候选一致。会话报告同样的摘要，记录中不得包含凭据、消息、原始日志或恢复材料。登记不产生产品提交，本机记录不会自动同步到其他电脑。该约定由 agent 执行，不是已运行的自动清单服务。

### 集成会话的职责

- 同批由一个集成会话负责。读取共享交接记录并重新核对 Git 与任务归属，不能盲信 JSON 的就绪状态。先固定参与任务和精确提交，后续新增提交进入下一批；确需补入阻断修复时重新冻结并验证。
- 与 main 的冲突尽量在开发交付前处理；尚未合并任务彼此间的冲突在集成分支按依赖顺序处理。不能为了提前消除冲突把其他任务的半成品擅自合入开发分支。
- 无文本冲突不等于行为兼容，仍检查共享状态、生命周期和安全契约，并验证最终组合。默认只为本批最终组合建立集成 PR；确需单独审查的任务另行安排。现有 CI 触发及精确 main 门禁不因该约定而跳过。
- 共享记录不含排他执行锁，尚不支持多个集成会话同时自动领取任务；不能把清单目录当作已实现的并发队列。持续后台集成与自动模型路由均未实现。

## 发布后资源清理

用户已授权将本批开发工作树和任务分支清理纳入发布收尾。由 agent 在独立生产回读与知识库对账完成后执行，不要求用户手动操作或重复授权；它不是发布脚本中的后台删除程序。只合并未发布的任务默认保留，除非用户明确要求提前清理。

固定机械核验入口为 `npm run tasks:cleanup -- --plan /绝对路径/plan.json`，默认只检查；agent 审阅结果后对同一计划添加 `--apply`。计划由 agent 根据已有交接与发布证据生成，用户不必填写。具体格式、信任边界、保留原因和续跑见[清理脚本说明](../workflows/task-cleanup.md)。脚本严格保留任何忽略文件和无法证明完整集成的 squash 改动；不能为通过检查把未经核实的确认项填成 true。

顺序为：`精确发布回执 → 独立回读成功 → 知识库对账 → 逐项核验 → 清理符合条件的本批资源 → 报告`。清理失败不改变已验证的生产结论，不回滚、不重发，只处理清理步骤。

### 必须同时满足的条件

- 范围已知：来自本批任务交接或创建记录的精确工作树路径、分支名和末端 SHA。不能按日期、名称前缀或“看起来旧”批量认领。共享主目录、main、其他任务资源及服务器发布目录、备份、部署配置不在本规则范围内。
- 成果已集成：核对最新远端 main 与对应已合并 PR，确认本批代码已进入发布版本。普通合并可检查提交祖先；squash/cherry-pick 必须核对 PR 原始 head、合并提交及完整改动映射，不能把“无祖先关系”直接认定为未合并或可丢弃。分支合并后新增的提交必须另行核实，有未集成内容就保留。
- 文件可丢弃：检查已暂存、未暂存和未跟踪内容；同时列出被忽略的文件路径，避免忽略的配置、附件、笔记或证据被工作树移除。已知可再生成的依赖/构建缓存不阻塞清理；未知内容、用户材料或未保存证据均保留。检查路径与状态即可，不读取凭据内容，不使用 git clean 清空现场。
- 证据已保存：分支与提交、PR、发布/回读及必要诊断记录已保存到不会随该工作树删除的持久位置。尤其检查位于该 worktree 专属 Git 管理目录内的回执，移除工作树会一并移除它们；只保存必要的脱敏证据，不复制部署凭据。未合并的知识库文档分支不清理。
- 无使用者：确认没有活动会话、构建、测试、开发服务器或后续任务依赖该工作树。无法确认就保留。当前执行会话实际依赖的工作树不得自行移除；在独立的集成/收尾工作树处理其他已结束任务，当前工作树标记为待后续清理，不为删掉自己创建无限收尾工作树。

### 执行与失败处理

1. 优先使用固定脚本完成以下机械检查与操作，不临时重写删除命令。执行前重新核对路径、分支末端 SHA、状态与工作树使用情况；发现变化就跳过该项。若工作树被锁定，保留并记录原因，不自动解锁。
2. 先用 `git worktree remove <精确路径>` 正常移除工作树，不使用 --force 或 rm -rf；再清理该任务分支。普通祖先已合并且满足上述条件时使用 `git branch -d <精确分支>`。
3. squash/cherry-pick 导致正常分支删除被拒绝时，不改用无条件强制删除。仅在改动已完整集成且末端 SHA 未变化的证据充分时，使用带旧 SHA 校验的 `git update-ref --no-deref -d refs/heads/<精确分支> <已核对SHA>` 删除引用；证据不足就保留。不得仅凭 -d 是否成功判断成果是否已集成。
4. 本批远端任务分支也可清理：须核对对应 PR 已合并、远端末端与已集成的任务 head 精确一致，且没有其他 PR 或任务依赖。删除请求必须以该末端 SHA 为条件（显式 force-with-lease 的删除校验），远端变化即停止；不得无条件删除或强推共享分支。已被平台删除则记录已不存在。
5. 删除后分别回查工作树登记、本地引用和远端引用，只报告实际确认的结果。网络或权限失败时保留待清理状态；已经完成的部分不重做，不扩大删除范围。

收尾用短表记录：`资源路径/分支 | 已清理/已不存在/保留/失败 | 原因或证据`。无需复制完整日志或每次新增审计文件，复用任务交付或已有发布记录。真机尚未验收不单独阻止已满足上述条件的清理；后续同问题反馈从最新核实基线新建修复分支，不能把清理成功写成真机验收通过。

## 无进展时如何处理

- 同一假设连续两次被证据否定，或主动诊断约 15–20 分钟没有新增证据：重新列出已排除原因、缺失证据和下一项可区分假设的实验。计时是检查点，不是放弃任务的期限；CI 等待不算主动诊断。
- 产品失败：修实现；夹具失败：修测试可移植性且保留产品断言；网络、下载、排队失败：处理基础设施并有限重试。没有完成分类前不同时改产品和断言。
- 根因推理明显超出当前配置时建议升级；缺少真机、权限或运行日志时优先补证据。不得声称已经切换模型，除非有设置成功的依据。
- 已通过检查只有因新变更、新失败或未解决风险才重跑。重跑说明触发原因和影响范围；最终候选仍须满足现有完整门禁。
- CI 等待和发布尽量交给现有固定命令，输出保留摘要与日志位置，错误时读取相关片段。发布切换结果不明时先独立回读，不盲目重发。

```text

基线 HEAD / 工作树归属：
验收：最多三项可观察结果
模型 / 强度：实际可核实值，否则未知

验证：定向命令 + 最终门禁 + 真机要求

```

用户发起常规修复只需提供问题与期望，录屏可选；固定流程和默认环境无需重复：

```text
问题：……
期望结果：……
```

交接时补充改动文件、已运行验证及其基线、失败分类、未验证项和下一步。不复制完整聊天或原始日志。后续独立任务只有在当前上下文已混杂或需要隔离执行时才另开，并沿用已授权目标。

## 前 5–10 个任务的试运行记录

每个任务交付时在回复中附一条短记录，优先复用 PR 或现有交付记录。用户统一收集对照；不自动创建监控、定时任务或第三方分析。

```text
类型 | 实际模型/强度 | 主动处理耗时 | 外部等待耗时 | token及统计口径 | 验收证据 | 额外全量次数/原因 | 返工情况
```

无法可靠取得的指标写“未知”。token 应注明是否包含缓存输入、推理和重试；账户额度百分比不是单任务 token，任务跨夜时长不是主动工作时长。后续反馈出现问题才更新返工情况，不在刚交付时推断未来没有返工。

按同类任务比较总成本、验收结果与返工，样本少时只作趋势判断。先消除无证据重试与重复验证，再决定是否降低模型或强度。没有实测前不承诺节省比例。
