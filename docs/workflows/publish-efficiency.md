# 发布效率与验证分级

2026-10-14 用户确认效率优先优化并授权验证、PR、CI及合并，要求不影响当日发布。
本规则将应用版本验证与发布工具验证分开，生产仍绑定用户确认的完整应用SHA。

## 评估影响范围与选择回归

每次冻结候选时，由任务负责人对照目标分支检查**整个差异**，沿改动入口找直接调用方、共享状态和相邻用户操作。逐项回答：谁会看到变化？成功、失败、重试或旧数据的行为是否改变？哪些入口、浏览器或环境共用这段代码？哪些已有用例能捕获本次故障？在需求记录或 PR 留一行结论，例如「中｜聊天键盘开合 → 输入框与历史滚动位置｜键盘模型单测、WebKit 聊天视口和连续性专项｜真机未测」。同时记录基线、候选 SHA、结果链接和未验证项。

| 评级 | 怎样决定 | 合并门禁 |
| --- | --- | --- |
| 低 | 只改操作文档，或修改局部呈现且能列全受影响的入口 | 运维文档走 docs。产品改动命中已登记专项时，验证改动点及直接使用它的界面 |
| 中 | 单一功能行为变化，能列全调用方、状态转换和相邻链路，成功与异常路径均有用例 | 发布工具白名单走 delivery。产品走匹配的 focused 专项，保留构建、单元／集成、文档、凭据扫描、依赖审计与双架构镜像检查 |
| 高或未知 | 影响关键边界、跨功能交互无法由一个专项覆盖，或不能说明哪些用例足够 | 候选走 full：全部浏览器分片、通话／TURN 及其余应用门禁。安全边界或影响无法界定时，本地另跑 `ensure check:full` 和对应专项 |

**必须全量**：认证／权限、应用锁、密钥、设备历史或成员纪元、隐私清理、持久化、数据库迁移、备份恢复、安全契约与 root helper。依赖／锁文件、运行环境、未登记产品路径、多个专项混合、无法验证差异或无可用覆盖，也一律 full。严格列出的发布工具／CI 配置使用 delivery 夹具验证。改动行数、文件扩展名或“仅 UI”不能降低行为风险。修复冲突、插入新提交或将多个需求组合后重新评级，检查最终组合覆盖；手动派发 CI 始终 full。

纯运维文档本地运行 `node scripts/check-docs.mjs`。交付工具另跑 `node scripts/check-delivery.mjs`，以隔离夹具验证 CI 身份、镜像架构与摘要、切换失败、回滚及独立回读。真实云权限由受保护的 doctor 预检核验。工具和记录的提交无需更新应用版本号。

**产品专项是显式选择。** 在本次改动的需求 README 独立一行写 `回归专项：<专项名>`，另写评估理由。CI 核对 PR、合并队列组合或 main 推送的完整差异。所有改动的需求记录须匹配同一专项，允许随带已登记的运维记录和版本说明。所有产品专项均跑构建、单元／集成、版本更新界面及上表的应用门禁。

| 专项名 | 可单独送验的范围 | 实跑的主要链路 |
| --- | --- | --- |
| `emoji` | 表情目录、搜索与目录单测 | Chromium 和 WebKit 表情选择器 |
| `keyboard` | 聊天键盘布局模型及其单测 | 聊天视口、聊天连续性、移动 Safari 反馈 |
| `chat-render` | 聊天输入框测量、发送后回复栏刷新判定、可见气泡渐变和本地日期分隔渲染 | 手机聊天滚动与渐变（Chromium／WebKit）、双引擎草稿与输入法、回复与滚动连续性、双引擎日期时间线、语言切换 |
| `feedback-copy` | 十份译文目录及 reviewed 中已登记的反馈表单、语言标签。只允许改已有键的译文值 | 各语言完整性与文本安全单测，Chromium 和 WebKit 语言切换、表单校验与提交 |
| `media-status` | `media-capsule.ts` 的状态胶囊呈现及 `media-upload.e2e.mjs` | 图片发送与接收（Chromium 和 WebKit）、视频上传、普通文件收发、隐藏与清理 |
| `message-date` | `message-date.ts` 的本地日期、时间格式及 `message-timeline.e2e.mjs` | Chromium 和 WebKit 的日期分隔、跨日与滚动锚点，以及语言切换、媒体时间显示、文件链路 |

例如修订反馈输入框译文可选 `feedback-copy`；同批若改恢复提示、增删键或修改 source 清单则全量。调整发送进度胶囊可选 `media-status`；同时改上传重试、对象 URL 生命周期或加密逻辑则全量。消息日期只覆盖呈现，消息排序、未读、历史持久化仍按完整应用验证。日期分隔模块可显式选择 `message-date` 或 `chat-render`，整批仍须落入同一专项。修改输入事件里的草稿检查点、发送队列、回复载荷或历史投影时回退全量。共享入口 `app.ts`、全局样式、产品／安全契约或其他未登记文件混入时均回退 full。

精确路径、允许修改的词条与浏览器命令共同维护在 `scripts/ci-scope.mjs`。扩充时附正常命中与越界回退测试，按 CI 同一入口 `node scripts/ci-scope.mjs journeys <专项名>` 实跑各消费者用例。高风险和覆盖不明的改动不声明专项。

main 选择 focused 前，还须找到上一个可核实的**完整应用 CI 基线**。只跨过最多八个仅含普通运维文档差异的第一父提交，核验精确提交最新成功 run／attempt 的完整应用证明。前一应用只有专项结果、历史或证明不可得时，本次回退 full，避免把多次局部验证累积冒充全量。

## 上线复用合并结果

1. 冻结发布批次时，比对**当前生产版本到候选**的累计功能和配置差异。多个独立合并若共同改变同一链路，补最终组合专项；出现上述全量条件且最终候选尚无全量证据，先取得精确候选的 full CI。把判定、目标环境、应用 SHA、版本、main CI 链接及 run／attempt、放行步骤、同轮镜像架构与摘要填进发布记录。
2. 发布器读取精确 main SHA 最新一次成功 run 和同一 attempt 的 `verify`。新流水线接受成功的 `Full application verification` 或 `Focused application verification`，后者仅证明专项范围。PR、队列、本地、docs 或 delivery 结果各自只证明对应阶段。历史应用沿用原精确 CI 协议。
3. 同一提交、同一经校验的镜像及测试前提仍成立，直接使用该产物，沿用合并证据。重建、镜像过期／摘要不符、配置或数据库状态漂移时停止切换，先明确差异、补相应验证并重新绑定证据；身份或影响不明则全量。更新的失败、取消或尚在运行的结果不能回退用旧绿。发布入口不自动派发回归。
4. 每个环境单独确认精确 SHA，照常预检、切换并做独立生产回读，核对版本、容器、HTTPS、存储及 WebSocket。回读失败只续跑回读。CI 链接不能作为生产健康或真机验收凭据。

## 准备、发布与接续

从已验证的工具版本执行，以下入口统一要求完整40位应用SHA与同一命名环境：

```sh
node scripts/publish.mjs --cloud --prepare --environment production --sha <完整应用SHA>
node scripts/publish.mjs --cloud --with-readback --environment production --sha <获批完整应用SHA>
node scripts/publish.mjs --cloud --resume <原工作流RunID> --with-readback --environment production --sha <同一应用SHA>
node scripts/publish.mjs --readback-only --environment production --sha <同一应用SHA>
```

- `--prepare` 只触发已有受保护工作流的doctor模式，验证真实云权限、CLI、helper、容量、来源、前版状态、正向祖先、合格应用CI和未过期镜像元数据；不下载大镜像、不切换、不安装helper、不修改RAM或业务数据。它不授予发布权，也不表示完整镜像已预载；发布时仍重验并下载校验。
- doctor先验证真实云命令通路，再检查应用CI，避免CI等待掩盖基础接入故障。已有生产环境审核照常保留。预检的容量和线上状态只是当时快照，不能取消切换前检查。
- `--with-readback` 在精确云回执核对后自动启动原有独立只读回读；回读仍使用本机SSH及命名环境，产物哈希／HTTPS／WebSocket与容器证据单独保存。失败只报告 `READBACK_REQUIRED`，只续跑 `--readback-only`，不再次切换。
- 同版本云回执以 `ALREADY_DEPLOYED_READBACK_REQUIRED` 进入回读，不伪造 `DEPLOY_VERIFIED`。
- 派发前将唯一请求ID及应用SHA保存到本任务Git元数据 `quiet-room-cloud-publish/`。响应丢失先按请求ID找到原工作流，之后 `--resume` 跟踪原RunID并读取精确回执；不提交第二个工作流，也不重跑云命令。失败或状态未知时仍检查原InvokeId并独立回读。
- 不带新增参数的旧入口保留原语义。正在运行的工作流、精确应用目标、已安装helper及其他任务工作树不由本次优化改写。

CI镜像清理额外保护活动发布工作流与最近三个成功doctor／deploy的应用候选，避免main前进立即淘汰已准备批次。
仍受GitHub七天自然到期限制；预检和发布都检查是否过期。候选列表不可核实时停止清理，不自动重跑应用CI或改发新SHA。
准备阶段是提前发现阻塞，不承诺镜像永久保留或零下载等待。

## 本地与云端验证分工（2026-10-29）

用户明确授权减少重复全量测试、保留安全检查且不影响运行中任务，范围见[交付发布效率V2](../requirements/2026-10-29-delivery-efficiency-v2/README.md)。本节规定本地执行策略；云端范围按上方分级执行。本地复用不能替代远端门禁。

- 普通功能、局部UI、跨页面、生命周期或附件的显示／交互修改：冻结后本地 `npm run delivery:evidence -- ensure check`，并按项目地图、复现与验收列出和执行受影响的浏览器专项。新回归须在本地通过；Safari问题保留相关WebKit或真机证据要求。不得只写“CI会测”而省掉本地受影响交互验证。必需的 PR CI 通过后不再为了本地全覆盖启动89个入口。
- 认证／应用锁授权、密码学、成员纪元、设备历史、恢复、密文与消息持久化、隐私清理、备份数据、服务端安全边界、root helper或无法界定影响的变化：保留本地 `ensure check:full` 和地图要求的安全／通话专项。按行为影响判断，不能因为补丁小、文件是CSS或名为UI而降低等级。可证明只涉及布局的修改与实际改变认证／锁定行为分开判断；不明确则高风险。
- 文档与发布工具继续按上方严格白名单；未知／混合改动的云端CI仍完整执行。CI不可用或缺失时不据本地定向验证合并、发布；完整本地验证也不能绕过远端必需检查。
- 默认 `ensure`，同一候选、同一命令、环境一致且最新结果成功时复用；`run`始终强制执行，须有环境损坏、新风险或主动调查等具体原因。较新失败／中断／脏树不回退旧绿。
- `verificationContent`绑定除严格运维文档白名单外的全部Git路径、模式和blob。只有这些文档变化才允许跨文档提交复用**本任务、同一工作树**的本地证据；原执行SHA和耗时保留。产品／安全契约、测试、工具、CI、依赖、未知文件和文档符号链接均使内容身份改变。旧记录没有此字段时仍仅精确提交复用；不跨命令推断覆盖，不改变完整CI或生产证据。
- 冻结后无关main更新进入下一批。确有冲突先核实应用／测试／依赖变化；纯运维文档合并可保留本地证据，PR新head的必需CI仍需通过。不开无限同步／重跑循环，不把已有源码证据伪称新提交的云端结果。

### 镜像下载缓存（显式启用）

新直接发布可使用 `node scripts/publish.mjs --cache-images --environment <环境> --sha <已确认完整SHA>`。旧命令与云端入口保持原行为；不修改在途发布、原RunID、候选或服务器helper。缓存功能须获批候选中包含新下载器；老候选继续其原发布代码。

固定入口仅向新隔离发布副本传入公共Git目录下的私有 `quiet-room-ci-image-cache-v1`。同机双环境使用相同架构和产物时复用下载；不同架构各自下载。每次仍实时核验最新合格应用 main CI、run／attempt、产物归属及未过期状态；缓存ZIP大小和SHA-256必须匹配GitHub认证元数据，解包后再走完整镜像manifest、平台、标签与归档校验，之后重验CI身份。缓存损坏失败关闭，不能凭本地manifest自证来源。缺少远端ZIP摘要或缓存达到4GiB上限时走原隔离下载，不自动删除其他发布的缓存文件。

此优化减少重复GitHub下载；各服务器仍单独传输、导入、备份、切换和回读，不承诺消除跨境网络或导入等待。保持生产单写者与各环境独立证据；不得并发生产切换以缩短等待。上线回读成功与文档收尾继续分别报告。

本次不修改CI工作流、并发组或取消策略；不取消、重跑或抢占其他任务的CI，不操作其他任务进程、工作树、依赖和候选。先独立验证和创建PR；合并前检查其他在途任务，若合并会取消其main CI或迫使其重新集成，保留本PR待后续合并并报告。

## V1 两批优化（2026-10-27）

用户确认[部署效率 V1](../requirements/2026-10-27-deploy-efficiency-v1/README.md)按两批实施、验证和 PR 合并；生产仍须确认最终完整提交。

- 第一批按 `scripts/browser-timings.json` 的已记录耗时均衡浏览器分片；数据只影响排班，不影响用例发现或断言。未知／无效耗时使用60秒估计，新增脚本仍执行；分片内保留原顺序，每个runner独立工作树，同树继续串行。主流程和全部专项、Chromium／WebKit轮数、通话／TURN、审计、双架构及完整verify门禁保留。
- `npm run delivery:evidence -- ensure <允许的npm脚本>`只复用本任务Git目录内**最新同命令**的成功记录；要求干净状态、Node/npm/系统架构、环境摘要、浏览器及依赖安装标识一致。提交与文件树相同或符合上方严格运维文档等价条件才适用。环境值只参与聚合哈希，不保存原文。旧记录缺少执行指纹、较新失败／中断、脏树或环境变化均重新执行。`run`始终强制执行，`summary`的`reusable`只表示本地同环境证据，不授权CI、合并、发布或真机结论；不跨工作树、不从其他命令推断覆盖。
- 本地必需验证可与PR CI并行；PR及合并后精确main完整CI均保留。通过的同一候选没有变化或新风险时不重复本地全量。等待复用已有RunID及watch进程，不重复派发；只读云准备使用既有`--prepare`，切换前仍重验容量、权限、线上状态、最新完整CI与镜像。
- 独立READBACK_OK后立即报告上线已验证；文档对账和资源收尾继续执行并另报终点。后置失败仍只续跑对应步骤，不重发。
- 第二批单独核实备份健康探针的实际时序和运行环境，保留原健康判定与启动宽限期后再优化等待。第一批不修改Compose、root helper、生产配置或线上应用。

本地复用是执行便利，不能证明依赖文件未遭手工篡改或替代独立安全审计；怀疑环境损坏时重新安装并使用`run`。浏览器调度、Compose或混合变化走完整应用CI，不扩大轻量白名单。

### 备份启动等待 V1（2026-10-27）

[部署效率V1第二批](../requirements/2026-10-27-deploy-efficiency-v1/README.md)显式设置备份启动期探针为10秒；原5分钟宽限期、稳态间隔和健康判定保留，配置后续发布才生效。
独立回读只在所有部署身份、镜像、来源、维护门、应用及TURN状态均匹配时，等待运行中备份的starting状态，每10秒只读观察，最长6分钟；后续样本仍重验全部前提。
实际healthy后才继续原有HTTPS、数据库／存储、公开及容器产物和新WebSocket验证。健康失败、探针丢失、连接失败或身份漂移立即停止，不继续轮询；超时保留失败证据，分类container-startup-timeout。
等待计入backup-readiness阶段，原始及最终容器状态不伪造；外层只读子进程限时8分钟。同SHA只续readback-only，等待或回读失败不能再次切换。
初始无备份探针的历史版本仍遵循原兼容；从starting变为无探针不算就绪。真实Docker CI单独验证时序及原探针拒绝过期／未来／失败记录，本机语法检查不替代该证据。

### 原有计时目标

分别报告“固定入口验证”“独立回读成功”“文档对账完成”。READBACK_OK后可报告上线成功，
文档对账继续在第二独立树处理；文档失败不会重发。正常条件下以确认后五分钟内完成切换和回读作为待实测目标，
不把本地专项耗时或小文件抽样外推为生产速度。沿用RELEASE_TIMING／READBACK_TIMING记录准备、传输、切换、回读与对账耗时。

本次交付不执行生产操作、不切换应用、不安装helper、不更改云权限；当日发布及独立回读证据由原发布任务拥有。
