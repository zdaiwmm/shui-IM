## 根因与实现

- 读取端把v2/v3载荷密文限制为2 MiB个base64url字符；写入没有对应约束。自动归档的待上传对象包含完整2 MiB附件分块，经原附件加密、编码、归档加密及保险库加密后约为5 MiB字符，可写入却读不回。
- 无效记录被读取为null，入口进入已有恢复页；变更保护比较null与内存记录，于是也可能报成跨窗口更新。双方各自自动备份同一附件即可分别遇到，不能仅凭此toast推断真的存在其他窗口。
- 原浏览器负例已复现：真实多分块PNG、真实服务、上传成功后中断，在旧实现失败于「Full-sized backup checkpoint must remain readable above the old limit」。尚未读取两台用户设备的实际记录，不能断言每台记录的实际状态。
- v2/v3加密载荷统一使用8 MiB字符硬上限，覆盖一个完整归档分块及元数据；v1保留原2 MiB上限，包装密钥、IV、KDF和目标空间校验不放宽。没有无上限解析、格式迁移、清除或密钥替换。
- 普通保存和MLS／消息／待发箱等原子写入共用加密前的UTF-8字节边界；计算包含AES-GCM的16字节标签及base64url膨胀，超限在打开写事务前拒绝，保留原持久记录。常规安装同时核对完整存储格式。
- 旧限制误拒但仍完整的密文可按原应用锁和AES-GCM认证直接打开，继续原备份任务，重试复用原对象ID。真实跨窗口陈旧写入仍拒绝。不保证实际损坏、缺失或丢失原解锁材料的数据可恢复。
