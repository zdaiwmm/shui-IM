## 确认行为与依据

1. 新消息胶囊位于输入框正上方、相对屏幕水平居中，显示 `↓ N 条新消息`，超过 99 显示 99+。阅读历史时不抢滚动；实时与入页／重连补拉的对方新聊天计入，旧历史分页和控制事件不计入。点击回到真正最新消息，实际可见后清除提示，保留键盘。
2. 最后十秒的锁定提示出现在新消息胶囊上方，两者拥有互不重叠的 44px 点击区，不改变消息列表或输入框布局。点击新消息按原有效操作规则延期；仅延期不改变阅读位置。弹窗、硬期限、隐私清理沿用原规则。
3. 原设备申请卡片在消息刷新及回到前台时复用节点，状态更新不反复移除／插入。批准仍要求原应用锁验证；设备上限错误使用既有 error toast，恢复卡片按钮。
4. 本人新设备进入第二个密室使用独立本机槽位并沿用本浏览器目录，保留第一密室设备身份和记录。两间已批准后 A→B→A、刷新／重入不重复授权或占用名额；三台设备限制、独立密钥、加入前历史边界保持。
5. 先用可控等待定位消息接入阻塞，只移除认证和加密状态以外的等待；不跳过校验、不提前宣称收到或已读。

设计依据为起始基线的 `PRODUCT.md`、`DESIGN.md`、`docs/design/mobile-visual-standard.md` 第 10/11 节，以及实际加载的 `chat-layout.css`、`idle-lock.css`、`room-polish.css`。沿用主题、字体、28px 提示表面及 44px 热区；不增加图片资产。设备安全契约由 `NEW_ROOM_ARCHIVES.md`、`CHAMBER_IDENTITY.md`、`SECURITY.md` 拥有。

## 诊断与验证

- 静态线索：消息渲染不保留设备申请卡片，异步重绘随后重新插入；目录接入获批后直接调用设备加入，遗漏独立槽位和原目录；消息同步等待完整成员处理，其中包含待发恢复等待。
- 定向验证：真实双／多浏览器 MLS 收发与离线恢复；原端申请卡片节点及几何；双密室往返、设备身份、原持久记录、真实设备上限；消息胶囊数量和布局、锁定与键盘、导航／隐私取消。
- 最终门禁：`npm run check:full`、文档检查和精确 PR 完整 CI。浏览器与物理 iPhone 证据分开。
- 定向证据：原实现的真实原端卡片在消息刷新时被移除，节点身份改变，原节点测量变化约514px。修复后真实三浏览器流程通过卡片节点／高度／滚动稳定、toast失败与重试、原锁批准、两密室多轮往返及刷新、设备身份保持和加入前历史隔离。
- 接收延迟实验：仅恢复旧版`await resumeOutbox()`后，在真实MLS重连中阻塞待发窗口HTTP请求，另一方消息等待超过5秒，实验失败；恢复修复后，同一请求保持阻塞时约90ms收到消息。仅证明此阻塞被解除，不代表生产时延或所有网络情况。实时、重连补拉、重复帧及回到底部清除的实链路计数通过。
- Chromium组件用例通过明暗、99+、独立44px热区、锁定出现／消失布局稳定及320／390键盘／1440桌面双栏居中。新增桌面用例最初误用document滚动，未实际滚动桌面列表；改为产品的实际滚动所有者后通过，未放宽可见性或几何断言。
