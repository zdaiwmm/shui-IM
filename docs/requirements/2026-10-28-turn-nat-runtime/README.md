## 根因与约束

- `::` 通配拒绝已修复并发布，但真实 NAT 场景仍将公网中继地址解码为本机 `172.26.1.2`，随后被172私网拒绝项拦截。相同镜像的隔离配置复现：公网普通地址允许，自己的公网映射地址403；日志仅取合成实验，明确显示被检查的是本机私网地址。云端端口和监听地址正确，拒绝发生在发出媒体包之前。
- 本机别名仅能访问既有中继端口。新主机已安装持久 UFW 出站保护，位于 loopback／established 放行之前：仅对 TURN UID65534 和本机私网目标生效，保留3478／5349的客户端控制响应，数据仅允许 UDP49160–49200 相互通信，其他本机目标拒绝。内网其他地址、回环和元数据拒绝继续由 coturn 执行，TCP relay保持关闭。真实内核测试已确认允许本机中继 UDP、拒绝非中继 UDP 与私网 TCP。
- Docker 在 UFW 之后启动；策略库只添加 `mijiu.cloud` realm 的本机别名，保存在镜像已有的 `/var/lib/coturn` 数据卷，已有数据库及 UFW 文件已另存。未添加用户账户、认证密钥或日志。原自用服务器没有这些变更。
- 运行配置更新未被当前启动方式采用：仓库显式替换了镜像入口，二进制默认数据库位置不是该持久卷。新增 `userdb=/var/lib/coturn/turndb` 让它实际读取该库；不依赖镜像入口的隐含参数。官方支持[持久策略库](https://github.com/coturn/coturn/blob/4.18.0/README.turnserver)，Compose正常重建[保留挂载卷](https://docs.docker.com/reference/cli/docker/compose/up/)。应用备份不自动包含 TURN 策略库；全新主机恢复必须先建立端口保护，再重建本机别名策略。
