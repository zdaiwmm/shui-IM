# 个人12词身份、邀请密室与共同恢复 · V2

状态：需求方向已确认，交互设计待确认；只更新原型及流程，不代表正式实现。对应[可视流程图](flow.html)及[可交互原型](prototype/index.html)。

## 创建与邀请加入

```mermaid
flowchart TD
  A[首页：创建密室] --> K{身份来源}
  K -->|全新| G[生成12词助记词：保存并核对]
  K -->|已有| I[导入本人已有12词助记词]
  G --> P[设置本机日常解锁保护]
  I --> P
  P --> W[A直接进入待加入聊天页]
  W --> L[复制邀请，通过原有渠道发给B]
  L --> B[B打开有效邀请：不消耗邀请]
  B --> BI[B生成并核对12词，或导入本人12词]
  BI --> BP[设置本机保护；已有可用身份则复用]
  BP --> J[B点击进入并提交本次加入请求]
  J --> C[A聊天页临时显示本次验证码]
  C --> T[A通过原有可信渠道确认B，并另行告知验证码]
  T --> V[B输入验证码]
  V --> Q{本次身份、设备、请求和验证码均有效？}
  Q -->|是| CHAT[双方进入同一密室，开放端到端加密会话]
  Q -->|错误| RETRY[提示核对；达到尝试上限则重新申请]
  RETRY --> V
  J -->|A拒绝或B取消或超时| END[未加入、不授予会话权限]
  END -->|有效邀请仍可重试| J
  CHAT --> USED[邀请和验证码失效；不保存到消息历史]
```

- 原型演示值为无效助记词及模拟验证码。正式目标为BIP39英文12词；密钥生成和验证不在本次实现范围。
- 验证码绑定受邀身份、设备、密室及单次请求，短期单次有效；不能用其他申请的码加入。原型建议有效期5分钟、最多5次输入错误，参数待设计确认。
- 邀请链接不能直接授予聊天权限；预览、打开不占用参与者名额。验证码仅在A本机临时卡片显示，不推送给B，不纳入聊天历史、备份或通知。
- 不提供用户搜索、公开公钥或资料、好友申请和好友列表。A仍需通过其原有渠道判断联系人身份，验证码并不能独立证明现实身份。

## 日常进入与新设备恢复

```mermaid
flowchart TD
  E[日常打开：中性遮罩，无空间或未读提示] --> U[显式进入本机解锁]
  U --> M[解锁后直达当前聊天]
  M --> S[右上设置]
  S --> LIST[空间列表：切换已有空间，保留测试入口]
  S --> SAFE[保险箱：保留原创建者权限]
  M --> LOCK[锁定或隐私清理，立即回到中性入口]
  N[新设备：首页恢复密室] --> WORDS[本人12词在本机验证]
  WORDS --> PROTECT[设置本机日常解锁保护]
  PROTECT --> DIR[恢复本人身份及未关闭的密室目录]
  DIR --> REQ[选择旧密室，请对方批准本次设备]
  REQ --> OK{对应参与者确认且设备授权完成？}
  OK -->|是| HISTORY[进入所选密室，恢复本人有效备份的历史]
  OK -->|拒绝、取消、过期| NO[不得读取历史或收发消息，可重新请求]
  DIR --> CLOSED[已关闭密室不自动出现；主动走共同恢复]
```

- 聊天为主页面；没有底部导航、左上返回或桌面常驻空间侧栏。次级页面的返回/取消放在页面底部；右上只有少量设置、锁定入口。
- 当前隐藏额外创建空间入口，保留多空间数据与原逻辑；不是硬性限定同一身份只能有一个空间。未来付费权限不在本期。
- 遮罩不代替认证，不能保证浏览器、外层WebView或操作系统不留下痕迹。原型只表现手动锁定后的UI，不验证真实后台锁定策略。

## 关闭与双方共同恢复

```mermaid
flowchart TD
  OPEN[已加入的密室] --> CLOSE[任意一方在设置选择关闭密室]
  CLOSE --> OWN[本机验证操作者本人12词助记词]
  OWN --> CHECK{身份与目标密室权限匹配？}
  CHECK -->|否| FAIL[不关闭，保留当前密室]
  CHECK -->|是| HIDE[关闭：双方入口移除，停止消息和通话]
  HIDE --> REVOKE[旧邀请、加入请求和设备待批请求失效]
  HIDE --> KEEP[保留服务端加密数据、个人身份和保险箱原权限]
  KEEP --> NEW[同一身份可以创建新密室，使用新的会话密钥和邀请]
  KEEP --> START[主动选择恢复已关闭密室]
  START --> AWORD[第一方在自己的设备验证本人助记词]
  AWORD --> SELECT[选择原密室并确认发起同一恢复请求]
  SELECT --> SHARE[通过原渠道将本次恢复邀请交给原参与者]
  SHARE --> BWORD[第二方在自己的设备验证自己的助记词]
  BWORD --> BOTH{双方身份证明与同一请求有效且均确认？}
  BOTH -->|是| AGAIN[原密室重新出现在双方入口，恢复有权限的历史]
  BOTH -->|拒绝、撤回、超时、身份不符| STAY[保持关闭；旧证明不可复用]
```

- “关闭密室”是可共同恢复的状态，不是永久删除；不承诺清除已有截图、导出或离线副本。
- 从普通助记词恢复、空间列表或历史备份都不能绕过共同恢复。第一方单独验证成功时密室仍关闭。
- 不收集两人的助记词：双方在各自设备验证自己的助记词，正式实现由服务端核验绑定同一请求的签名/证明，不接收助记词明文。
- 原型建议共同恢复请求15分钟有效；拒绝、取消或超时使该请求失效，重新发起需再次验证本人身份。
- 恢复邀请仅对原参与者有效；不会邀请第三人替换原来的另一方。保险箱原创建者权限不扩大。
- 两端离线副本的真实失效时点、旧设备保留/撤销、关闭后保险箱独立入口、密钥重建与防回滚等需在正式实施方案中验证，原型不证明其安全实现。

## 旧空间迁移

```mermaid
flowchart LR
  O[已解锁的原设备或原恢复流程] --> A[核验旧空间本人原有参与权限]
  A --> B[逐个绑定本人个人身份]
  B --> W[等待另一方在其设备完成绑定]
  W --> V[验证双方绑定与原角色]
  V --> R[原空间转为个人身份下的密室]
  R --> H[逐空间保留历史、独立权限和保险箱创建者]
```

双方未绑定完时旧空间继续可用；多个旧空间分别保留，不合并历史或改变原角色。二维码/旧恢复码兼容需要保留原恢复流程，不能仅凭个人助记词取得旧权限。
