## 2. 产品目标与既定边界

这是已有信任关系的两个人寻找更私密聊天场所的产品。邀请用于确认“谁进入这间密室”，个人身份用于延续和恢复；不是重新建立社交关系。

| 事项 | 本期规则 |
| --- | --- |
| 首次使用 | 创建/打开有效邀请后自动准备本机身份，尽快进入聊天；无资料填写、钱包导入或安全配置前置 |
| 身份 | 自动生成英文12词助记词；不公开资料、公钥搜索、用户发现或好友列表 |
| 加入 | B在待激活聊天中主动获取验证码，A通过原有可信渠道核对并告知，B在原页4格激活 |
| 密室数量 | 保留已有多空间架构、数据与创建逻辑；隐藏额外创建入口，不加“身份只能有一间”的底层限制 |
| 测试入口 | 设置保留空间列表与已有空间切换 |
| 关闭 | 任一原参与者验证本人助记词后关闭，移除双方日常入口并停止通信；保留服务端加密数据 |
| 共同恢复 | 双方分别在自己的设备验证自己的助记词、确认同一请求后恢复原密室 |

## 3. 创建、加入与身份确认

### 3.1 A创建

首页点击创建密室 → 加载 → 待加入聊天。内部在本机生成12词和个人身份，创建独立设备密钥及待加入密室。已有可用本机身份复用；已有应用锁仍须原验证，不因新邀请被绕过。

加载描述对应真实任务完成，不显示编造的加密百分比、安全评分或故意延长等待。已有身份显示“读取匿名身份”，不误导为重新生成。创建失败保留同一创建意图；重复点击、断网重试和迟到回执不得重复分配身份或密室。发现前次服务端已创建时先核对并接续。

A聊天首屏主任务是复制邀请。邀请未完成前不开放消息/通话。保护引导在其下方，只展示当前一步；可暂缓，不覆盖复制按钮。

### 3.2 B打开邀请

有效链接 → 本机身份准备加载 → 自动进入待激活聊天。链接预览、打开或身份准备完成都不占参与者名额、不向A出验证码、不授予消息/历史/保险箱权限。

系统消息：“密室尚未激活，向邀请人获取本次验证码，验证后就能开始聊天。”点击“获取验证码”才生成加入请求。此时A聊天显示本次4位码，B系统卡片变为4格输入和“激活密室”。未验证前没有真实消息输入框，也不下载旧消息或建立可读会话。

失效、已使用、已关闭或非本产品链接显示明确错误与底部返回；不能静默创建另一间密室，也不能把参与者邀请解释为新增设备邀请。打不开时B联系A重发。

### 3.3 如何确认是想邀请的人

验证码证明的是对本次请求的授权，不能独立证明现实身份。A须在双方原来的可信聊天或通话中确认B；不根据网页自报昵称、头像或“匿名公钥”判断是谁。

建议A与B先核对同一个申请编号，再转告本次码。两端卡片均展示编号，B将编号通过原渠道告知A，可避免把陌生请求的码误发给B。编号只是定位请求，不能替代验证码或作为权限凭证；正式编号应随机且不暴露用户数量。

验证码必须绑定密室、邀请版本、B个人身份公钥、B设备公钥/密钥包、申请ID和有效期。成功时原子地确认同一申请、消耗码和邀请并激活成员；断网后可查询同一申请结果，不能重复加入或产生两个B。

建议参数：4位数字、5分钟有效、每请求最多5次错误。另需对密室/邀请/身份/设备及网络来源累计限速与冷却；重开请求不能清零猜码预算。A可拒绝、撤销或换邀请；一项申请不能把另一项申请的验证码当作正确码。并发请求的选择规则见第10节。

A端验证码只在授权邀请设备的临时卡片内显示，不发给B、不写聊天历史/备份/通知/日志。服务端不得给邀请持有者返回正确答案；存储采用受保护校验材料，发送给A的显示材料也需访问控制。验证码不作为会话加密密钥。

## 4. 聊天主页与四步保护

### 4.1 层级与日常入口

聊天页是主页。顶部背景连续，右上仅在线胶囊与设置，不占整行标题栏，不设左上返回、底部导航或常驻空间列表。在线状态仅基于已认证连接，不等于已读、送达或本人正在看。未激活时显示“等待加入/待激活”，不因B仅打开链接就向A泄露B在线。

胶囊仅给原创建者保留既有保险箱入口；另一方只有状态展示。手动锁定在设置。锁定入口不显示联系人、密室存在、未读数或历史预览。通知默认不展示私密内容；邀请链接的外部预览使用中性标题，不含身份、验证码或会话状态。

遮蔽层降低入口暴露，不替代认证，不承诺删除浏览器历史、系统任务缩略图、剪贴板、截图或外层App记录。不增加第三方统计、会话回放、远程脚本或错误内容上报。

| 1 应用锁 | 聊天后配置通行密钥或本机密码 | 成功后才承诺可解锁的本机加密持久化；系统取消/失败留在当前步，不自动降级 |
| 2 入口遮蔽层 | 开启中性入口 | 可明确选择暂不开启，记录为已选择但未启用，随后可更改 |
| 3 自动锁定 | 选择离开页面、闲置1/5分钟或暂不 | 需已有应用锁；不延后撤销、关闭、敏感操作和真实生命周期的硬锁边界 |
| 4 保存助记词 | 主动查看并按序保存12词 | “我已保存”确认；可选本机随机核对3词，失败不阻塞聊天 |

聊天内每次仅突出当前未完成一步，显示第几步及完成数；完成返回聊天后展示下一步，不连续强制跳页。“稍后再设”收起本次提示，设置始终保留四项入口；重开/解锁时可继续未完成步骤。设置中允许按需配置，已完成项目不重复要求。

暂缓不是已经保护：未设应用锁时不能假装本机已安全持久化；未保存助记词时不能承诺换设备可恢复。当前建议是临时会话，仅在页面内保留解锁能力，离开/刷新前给明确丢失风险提示；不能为省步骤把明文密钥或可自动解锁的长期密钥放入浏览器存储。该生命周期仍待第10节确认。

### 4.3 助记词展示与输入

助记词只在本人主动保存/查看时展示，不混入普通聊天消息。已设应用锁时，建议先用原本机验证方式做新鲜验证再展示；取消、失焦/离开、锁定、切身份或过期均清除展示与输入。原型新增该模拟门槛，展示60秒后隐藏；真实系统提示及输入法行为尚未验证。

12词按序号展示；恢复/关闭/共同恢复使用12个编号输入格，支持一次粘贴。本机检查词数、词表、校验和和身份记录；格式正确但不属于本产品身份也不自动注册。三词抽查只检查本机备份操作，不是服务端认证，也不能证明12词全部可靠保存。

默认不自动复制、不自动下载、不上传截图/图片；用户自行保存的位置由用户控制。自动填充、拼写检查、输入记录关闭，剪贴板与系统输入法风险须说明，页面无法保证清除所有系统级副本。不要把真实词输入原型。

## 5. 加密方案与“不上传私钥”的边界

以下是拟定安全契约，不是已实现协议或安全审计结论。12词采用BIP39英文词表、128位安全随机熵及校验和；词数本身不证明产品实现安全。[BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)

### 5.1 密钥分工

| 材料 | 用途与所在地 | 服务端允许持有 |
| --- | --- | --- |
| 12词、原始熵、种子 | 本机生成/输入，恢复个人身份；本机受保护保险库或临时内存 | 不允许明文、密文、哈希口令形式上传，不进入恢复包/日志/URL |
| 个人签名与解包私钥 | 本机从种子按用途隔离派生；认证个人操作/解开本人历史备份密钥封套 | 不允许上传，包括加密后的私钥副本；只上传必要公钥与绑定请求的签名 |
| 设备签名/ECDH/MLS私有材料 | 每设备独立安全随机生成；消息、设备批准及MLS状态 | 新协议不上传私钥或私有状态备份；服务端仅公钥、公开密钥包和协议密文 |
| 会话内容密钥 | MLS内部随机与棘轮演进，本机使用/持久化 | 不上传明文，不直接由助记词或4位验证码作为静态聊天密钥 |
| 历史备份数据密钥 | 独立随机生成，本机加密有效历史；可用专用个人解包公钥形成密钥封套 | 仅允许密文历史与加密数据密钥封套，不能夹带任何身份/设备私钥 |
| 本机保险库主密钥、WebAuthn PRF、密码 | 本机解锁与数据保护，和个人签名/备份用途隔离 | 不上传；本机密码不作为服务器账号密码 |
| 加密密室目录 | 记录本人可恢复密室、角色和备份定位；用独立目录密钥加密 | 密文、随机定位符、必要版本与访问校验材料 |

身份公钥负责认证和签名，不能仅靠公钥加密就把接收者变成授权参与者。新设备导入同一助记词后仍生成全新设备密钥，经对方批准后加入；不得复用旧设备ID、MLS发送棘轮、计数器或从同一助记词重建相同设备私钥。保留当前MLS协议及独立设备上限，算法、域分离标识、签名规范化、请求格式和库版本在实现前专项冻结，不在原型里手写密码学。

现有MLS提供会话密钥演进；身份恢复不等于获得过去所有消息密钥。独立历史备份会增加可恢复性，也扩大助记词泄漏时历史受影响的范围，必须作为明确产品取舍，不能继续泛称历史不可恢复。[RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html)

### 5.2 一次认证的数据流

本机生成/读取助记词 → 本机派生对应用途私钥 → 对带用途、目标密室、身份、设备、请求ID、版本、一次性挑战和到期时间的数据签名 → 只发送公钥/签名/允许的公开参数 → 服务端核验绑定、权限、时效及防重放 → 返回最小结果。服务端不接收助记词来“帮忙验证”，不存其哈希当登录口令。

关闭、绑定旧空间、设备恢复和共同恢复使用不同用途标识，证明不得跨操作复用。服务端原子检查关闭版本/成员版本，拒绝旧签名、过期证明和客户端自报权限。目录取回必须有本人证明/高熵访问能力，不能通过公开公钥枚举他人的使用关系；名字、预览、历史索引在加密目录内。签名能验证内容未被修改，不能单独证明服务端没有返回较旧的合法版本；防回滚需要本机/对方可信版本锚或经审阅的机制。双方原设备全丢且没有可信锚时，不能假称已证明目录是最新状态。

### 5.3 现有恢复包不能直接沿用

代码事实：当前[cloud-backup.ts](../../../src/lib/cloud-backup.ts)的`checkpoint()`复制整个Vault，保留设备的ECDSA/ECDH私钥，只删除MLS私有包等字段；`stageEnvelope()`再把该检查点加密上传。当前服务器看不到私钥明文，但密文中确实含设备私钥。

因此，新需求若按“任何私钥，即使加密也不上云”执行，就不能把12词简单转换为QR4恢复码，再原样复用旧QR3恢复包。旧QR4目录可参考其多空间能力，但云端内容必须换为严格字段白名单的新格式：个人/设备公开绑定、加密历史、必要密钥封套与完整性元数据；不序列化整个Vault，也不备份旧设备认证私钥或MLS状态。

新设备通过本人助记词证明身份、对方批准全新设备，再本机解开有效历史备份；不通过下载旧设备私钥冒充旧设备。旧QR3/QR4包的只读兼容、停止写入、迁移验证和旧能力停用必须单独设计。既有历史包已存在这一事实不能改写为“从未上传私钥”；新协议的承诺需明确切换范围。这是正式实施前的阻断项。

### 5.4 浏览器能保证什么

可设为可验收要求的是：正常应用数据路径不发送任何身份/设备私钥，服务端请求/日志/备份没有这些材料，本机静态存储仅有受保护密文。不能保证已被恶意脚本、浏览器扩展、输入法或系统控制的解锁设备绝不泄漏；把密钥设为不可导出，也不能阻止被控制页面调用签名/解密能力。需要代码审查、依赖锁定、CSP/TLS、无第三方脚本及实际数据路径验证共同落实。[W3C Web Crypto](https://www.w3.org/TR/WebCryptoAPI/#security-considerations)、[OWASP浏览器存储建议](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#storage-apis)

网站服务器若发送恶意的第一方前端，也可能窃取本机正在生成/输入的助记词；TLS、CSP和“不上传”代码约定不能单独防住这一点。受信任版本分发、构建/发布审查和前端完整性属于安全边界，网页版本不能承诺抵御已控制前端发行的攻击者。

本机锁定时同步移除敏感DOM，作废异步所有者并清理可清理的密钥/输入引用；不能承诺JavaScript字符串、浏览器堆、系统交换区或所有剪贴板副本已被物理擦除。根身份泄漏按身份失窃处理，仅改本机密码不足以恢复身份安全；本期无完整换根协议，不声称可无损换助记词。

## 6. 恢复、关闭与历史

### 6.1 新设备恢复未关闭密室

完整12词在本机验证 → 取回并校验本人加密目录 → 展示本人未关闭密室 → 为所选密室请求对方批准全新设备 → 授权及MLS成员变更完成后进入。未批准不能读旧消息、发送、通话或进入保险箱。拒绝、取消、过期、设备上限、备份冲突给明确重试/处理入口。

助记词只证明本人身份，不能冒充对方。目录或历史包被服务端替换、回滚、截断时必须验证签名/版本/上下文，不能相信包内自报角色。恢复保留旧设备、替换旧设备或达到三台上限时的取舍，在批准页明确；不能静默撤销一台不相干的设备。

### 6.2 关闭

设置 → 关闭当前密室 → 提示影响 → 本机验证本人完整12词 → 提交绑定当前关闭版本的一次操作。没保存时先引导保存，再返回关闭确认；取消不改变状态。

服务端确认后停止该密室的消息、通话、历史读取与设备加入，失效旧邀请、验证码、未完成设备/恢复申请及关联通知能力，推送生命周期事件使在线端移除入口；重新联网/切回前台必须先核验关闭状态再展示。其他密室和个人身份保留。

关闭不调用永久删除接口，不删除保留密文和原保险箱数据。离线且已解锁的旧设备无法被即时远程擦除；已保存的历史、截图、导出不能收回。关闭成功必须有服务端回执，断网时显示“尚未关闭，等待联网确认”，不能先假报双方已关闭。

### 6.3 双方共同恢复已关闭密室

一方主动进入共同恢复 → 在自己的设备验证本人助记词 → 查找原参与密室 → 确认并发本次恢复邀请 → 原另一方在自己的设备验证自己的助记词并同意。两份证明必须绑定同一密室、原双方身份、关闭版本、请求ID、目标设备和期限；建议15分钟有效。

两份证明及所需设备授权/MLS状态均有效后，才原子转为可用，恢复双端入口。第三人不可替代原参与者，不能将双方词交给一人/同一设备。单方验证、单方导入身份、历史导入、日常解锁或旧客户端均不能重开。

拒绝/撤回/过期/一方缺少助记词/密室版本已改变，保持关闭。重复提交返回同一结果；新请求作废旧证明。确认前再次关闭、新设备并发恢复或双方都换设备，必须核对同一最终设备集合和成员版本，不能靠两个布尔值开启旧访问能力。

### 6.4 历史恢复的真实范围

| 可用材料 | 恢复结果 |
| --- | --- |
| 原可用设备仍保留本机历史 | 共同恢复后可继续展示其已有且有权阅读的本机历史 |
| 有完整、有效的本人加密历史备份 | 授权后恢复备份覆盖的记录；核对数量、连续区间、附件完整性与删除投影 |
| 只有助记词与服务器聊天密文，无对应历史密钥/备份 | 可恢复身份/密室，不能凭空解出旧消息；明确显示未找到可恢复历史 |
| 上传中断/部分备份 | 仅恢复已验证部分，标明范围与缺失，不假报全部历史已找回 |
| 附件块或保险箱备份缺失 | 文本与附件结果分别说明，保险箱仍限原创建者 |

保留服务器数据不等于数据永不清理、永久可恢复或已备份；配额、保留期、双方历史备份是否默认开启，需要单独确认。已删除消息不能被旧备份重新显示。原型新增“无可用历史副本”模拟，呈现密室恢复成功但历史不可恢复的结果。

“双方共同恢复”当前确认的是产品授权流程。若要承诺即使服务端失陷，单方持有助记词也无法解开云端旧历史，需要经过审阅的双人密钥封套/门限方案；只在数据库写两次批准不足以提供该密码学保证。保留历史私钥/备份密钥的旧设备仍无法远程剥夺。此强度与第10节一起确认，不在设计稿假装已解决。

## 7. 旧空间、多空间与保险箱

旧空间仅由原设备先解锁，或先走旧恢复授权，再证明原角色并绑定本人个人身份。不能拿新助记词绕过旧空间权限。每个旧空间分别迁移；一方已绑定时旧功能继续可用，不能强制替对方绑定或先合并历史。

双方绑定后仍是原两人密室，不创建同角色重复成员，不自动合并相同两人之间的旧空间；多个旧空间分别保留原历史和备份归属。旧QR3/QR4迁移须先验证新目录和历史回读，再按确认的兼容策略停用旧能力，禁止一边清除旧恢复材料一边声称迁移成功。

空间列表留在设置，不出现在日常入口。关闭的密室从普通列表排除，主动证明本人身份后才进入共同恢复列表。额外创建入口隐藏，不删除底层能力、不通过前端判断增加全局单空间硬限制；结束全部当前密室后可用同一身份创建新密室。新密室用全新邀请、随机会话材料和独立MLS状态，不能复活旧邀请或带入旧历史。

保险箱始终跟随原密室创建者权限。B加入、双方绑定、换设备或共同恢复均不能改变角色；不得从在线胶囊给B一个可取得数据的入口。关闭保留其密文，恢复仍按原角色和有效备份范围处理。

### 关键异常与竞争

- 网络：离线创建/请求/验证/关闭/恢复不假报成功；请求超时后先查同一操作结果，重试不重复创建/激活/消费证明。
- 生命周期：刷新、关闭WebView、切后台、系统权限弹窗、锁定、场景重置后，迟到结果不能展示秘密或写入新身份；应用锁取消不等于配置完成。
- 邀请：预览不申请；窃取链接不等于获准；A拒绝可重发；旧版本、已加入、已关闭或设备邀请类型不符均失败关闭。
- 并发：双标签创建、多个B请求、两端同时关闭/恢复、同角色多设备批准采用版本与幂等键；无“双B”、无旧批准覆盖新关闭。
- 密钥：12词格式正确但身份未知、词序/校验和错、输入被取消、身份泄漏和旧设备失窃均有独立结果；服务器错误不得回显用户输入。

## 10. 在家继续确认的关键问题

这些问题影响安全与数据承诺，不能由原型走通来替代决定。建议可作为下轮讨论起点：

1. **未配置应用锁前怎样保管身份？** 建议临时会话，离开前提醒设置应用锁或保存助记词；刷新/关闭后可能丢失未保管身份。若要求不配置也能无感跨刷新使用，需要另选本机保管方案并明确其暴露风险。
2. **“私钥不上服务器”的严格范围与旧兼容？** 建议新协议禁止任何身份/设备私钥以明文或密文上云，改造旧恢复包；旧QR3/QR4只读兼容窗口、迁移完成后的旧能力停用与已有密文处理需确认。不能同时承诺无任何私钥密文留服务器又原封不动保留旧备份格式。
3. **共同恢复是产品门禁还是密码学双人控制？** 建议先明确要防普通误操作/单方重开，还是还要防服务器被控制后的单方解密。后者必须另行设计并审阅双人密钥封套，不能用4位验证码、两个签名标记或简单拼接助记词代替。
4. **历史要保证到什么程度？** 建议身份目录必要备份与历史备份分开告知；历史仍按本人明确开启的有效备份恢复。若要默认全部历史可恢复，需确认默认备份、保留期、配额、关闭时未上传内容的处理及安全代价。
5. **多个加入请求如何选择？** 建议同一邀请只处理一项待确认请求，A可拒绝并换邀请；B通过原渠道报告申请编号。正式限速/冷却参数及恶意占位处理在协议设计中冻结。
