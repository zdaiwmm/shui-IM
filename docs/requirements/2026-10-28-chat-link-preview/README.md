## 已确认需求范围

用户需要类似所提供 Telegram 截图的网页预览卡片，触发点在输入阶段。

1. 输入或粘贴完整网页网址后，短暂停顿自动获取信息，无需先发送消息。
2. 输入区显示网站名、标题及关闭按钮。关闭卡片保留链接文字；删除网址收起预览，更换网址更新预览。
3. 发送后的消息保留文字和可点击链接，并显示网站名、标题、摘要及可用配图；支持底部大图、右侧缩略图、无图文字卡片。
4. 获取失败不阻止发送。预览服务在消息发送前获得待预览网址，不接收其余聊天正文；发送出的卡片文字和图片随消息加密。
5. 点击卡片在新标签页打开网页，保留原聊天页。正文网页链接沿用同一打开方式。
6. 本轮先做原型和流程图。用户明确允许静态图，替代本轮默认的可交互原型；该例外不授予正式实施、合并或生产发布权限。

## 现状与实现约束

- 基线 `src/app.ts` 的 `createMessageElement()` 及 `clearMessageTextSelection()` 用 `textContent` 绘制消息；没有正文网页链接识别或卡片。
- `src/lib/types.ts` 的 `TextPayload` 与 `src/lib/message-payload.ts` 的严格白名单尚不支持链接卡片字段。正式实施需要定义加密卡片载荷、旧客户端协商及可用图片传输方式，不能只拼接 HTML。
- `server/index.mjs` 的 CSP 仅允许本站连接与本站／blob／data 图片；当前没有网页信息预览服务。正式实施不能通过开放任意远程脚本或直接嵌入网页来代替预览。
- `SECURITY.md` 定义聊天密文、服务端不接收明文消息与回复预览等现有边界。发送前网址抓取是本需求已讨论的数据边界；未来实施必须明确有限例外、网络隔离和日志策略，避免把“正文仍加密”误写为“预览服务看不到网址”。
- `desktop/macos/Chamber.swift` 当前将用户点击的外部 HTTP(S) 链接交给默认浏览器，同源新窗口另有原窗口加载规则。用户的新标签要求在浏览器／PWA与原生容器中都需要分别核实；本轮只展示静态目标。

- 基线的 `DESIGN.md` 中 Intent and palette、Surfaces and typography、Chat and keyboard space，以及 `docs/design/mobile-visual-standard.md` 的配色、字体、间距、输入和聊天章节。
- `src/design-tokens.css` 为共享变量，`src/design-system.css` 的 16px／22px 消息正文、16px 气泡圆角及 44px 操作目标为依据；`src/room-polish.css` 与 `src/chamber-refinements.css` 核对浮动状态胶囊、设置入口、连续输入底色。
- 原型使用真实共享 token 与现有 `src/assets/chat-pattern.svg`；没有导入应用入口、业务组件或 Service Worker。消息气泡、浅色绿色和经典深色紫色遵循项目基线。发送图标取自既有 `src/lib/voice-audio.ts`，其余图标为 Lucide 静态路径（ISC）。
- 原型只展示本需求受影响区域。顶部状态胶囊、连续深色发送渐变位置、键盘与桌面窗口为必要的静态背景示意，不作为这些既有功能的新视觉规范或真实设备证据。
- 按仓库最小检索规则核对相关篇章，不因通用设计 Skill 默认要求而通读所有产品／设计历史；没有改写 PRODUCT／DESIGN 或正式移动规范。新增组件设计仍待本轮确认。

以下为便于完整审阅补充的 V1 建议细节，尚未获正式实施确认：

- 每条消息默认预览首个有效网页链接，不增加多卡选择器。
- 关闭后，相同草稿网址不因继续输入而反复生成；改成不同网址重新获取。
- 抓取过程中发送只发送文字；发送时固定当前快照，晚到结果不补改已发消息。
- 失败提供重试和关闭；没有可用信息时不阻止发送。摘要最多三行，输入区标题最多两行。图片尺寸与标题长度均需有界。
- 接收端只展示随密文到达的预览内容，不自动访问原网页或远程图片。
- 只预览公开 HTTP(S) 网页；站内邀请、设备加入、恢复能力链接及带账号密码的地址不自动抓取。服务端防内网访问、DNS／重定向／图片边界、超时／大小／并发限制，以及日志与缓存策略须在正式实施前明确。
