## 方案与观察标准

使用真实本地服务器、应用、MLS 和 IndexedDB，全部为一次性合成身份与消息。测试观察器仅暴露应用实例；网络屏障只延迟指定发送端接收的真实 ack、本人 message 或包含该消息的 sync，不改帧内容，不替代服务器接收、签名、加密或持久化。

在 Chromium 与桌面 WebKit 各比较：

1. 服务器已接收、确认延迟但不取消：释放后正常落盘，后续双向消息可解密。
2. 密文已落盘但尚未提交：通过实际删除入口取消，刷新后无补发，后续双向消息可解密。
3. 服务器已接收、确认与本人回传延迟：通过实际删除入口取消，再释放原回传。
4. 同上，但丢弃旧连接回传并刷新，由真实服务器重新同步。

问题成立条件：确认服务器真实接收、对端真实解密、取消真实持久化后，释放或重新同步导致完整性错误、同步停止、取消项复活或重复发送。正常对照必须先通过；环境和夹具失败另行分类，不视为产品缺陷。记录本机隐藏、待发存储、历史水位、服务器计数和后续收发；不以取消推断已接收内容可撤回。

### 失败历史与一次夹具修正

- 最初启动被本机监听权限 `listen EPERM 127.0.0.1` 阻断，未到产品验证；通过正式执行审批续跑原本地命令，没有改产品。
- 首轮已完成 Chromium 四场景，结果见 `initial-results.json`；WebKit 正常对照在“水位必须与发送前完全相等”的夹具断言停止（2 不等于 1）。真实控制事件可以先于目标推进水位，因此 V1.1 改为核验目标确实不在持久历史且水位小于目标真实服务器序号，仍完整验证目标未被消费。仅一次针对性修正后重跑两引擎全部八场景。
- 首轮 fatal 后应用释放 session，因此其 `localHidden=false`、`finalCursor=null` 等空运行时字段不能代表持久状态。V1.1 在失败后通过正常本机自动包装独立解锁并只读回读，不安装运行会话、不接网络；最终结果确认隐藏仍为 true、水位停在目标之前。首轮原始结果不改写，以上限制明确保留。

### 定位与下一步边界

取消路径位于 `src/app.ts:11515` 与 `src/lib/vault.ts:2951`，原子删除待发及保留隐藏投影。`src/app.ts:6097` 的本人消息回传却必须从该待发记录取得原 envelope 与 payload；记录被取消删除后进入 `fatalSecurityError`（`src/app.ts:16720`），不能推进连续历史。服务器去重及接收路径 `server/index.mjs:1703`、`:1749` 正常，回传确为已提交消息。这是取消与已提交消息对账所需材料之间的生命周期冲突，不是服务器重复接收。

建议下一步只修复该冲突：取消仍阻止后续发送并保留本机隐藏；已经提交但结果未知的消息保留独立加密核验材料，供认证回传完成正常落盘，不能把它重新当成可发送工作。MLS 不回滚、完整性检查不跳过、设备与历史权限不变。持久格式、旧客户端／回退时不复活取消项的兼容策略须在修复方案中明确；不进行大范围发送重构或备份优化。已被旧版本删除的核验材料不能据此承诺自动找回。

修复验收至少保留上述全部时序与对照，并增加结果未知时的重连／刷新及后续 MLS 收发回归；届时按风险运行正式门禁。本轮没有修复、提交、推送、PR、CI 或生产操作，没有运行完整产品门禁；当前仅为诊断脚本及结果，不能直接加入通过门禁。
